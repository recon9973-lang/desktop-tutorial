# VEO 웹 접근성 — WCAG 2.2 AA 감사 기록

VEO 콘솔은 분석가가 하루를 보내는 화면이고, 공개 도구는 병원 원장이 자기 사업에 대한
진단을 읽는 화면입니다. 두 사람 모두 이 화면을 쓸 수 있어야 합니다.

이 문서는 **점검한 것**, **고친 것**, **아직 남은 것**, 그리고 **자동 검사로는 확인할 수
없어 사람이 스크린 리더로 직접 확인해야 하는 것**을 구분해 적습니다. 마지막 구분이 이
문서의 핵심입니다. "자동 검사를 통과했다"와 "VoiceOver로 쓸 수 있다"는 다른 문장이고,
여기서 섞이지 않습니다.

- 대상: `apps/web/**`, `packages/ui/**`
- 기준: WCAG 2.2 Level AA
- 감사 시점의 상태: `@veo/web` 166 tests, `@veo/ui` 154 tests 통과

---

## 1. 이 감사가 실제로 확인할 수 있는 범위

테스트는 vitest + jsdom에서 돕니다. 이 환경의 한계를 먼저 적어 둡니다.

| 확인 가능 | 확인 불가 |
| --- | --- |
| 역할(role), 접근 가능한 이름, `aria-*` 관계 | 실제 스크린 리더가 읽어 주는 문장과 순서 |
| Tab 순서, 포커스가 어느 요소에 있는지 | 포커스 표시가 **보이는지** (jsdom은 CSS를 적용하지 않음) |
| 라이브 영역이 마운트되어 있는지 | 라이브 영역이 실제로 **읽히는지** |
| `tokens.css` 값으로 계산한 명암비 | 반투명·이미지 위 텍스트의 합성 명암비 |
| 스타일시트에 감소된 모션 대안이 있는지 | 그 대안이 실제로 동작하는지 |

명암비만은 예외적으로 실제 브라우저(Chrome)에서 `getComputedStyle`로 다시 측정해
교차 검증했습니다. 아래 수치는 두 방법이 일치합니다.

## 2. 발견해서 고친 결함

### 2.1 SC 1.4.11 비텍스트 명암 — 컨트롤 테두리가 보이지 않았음

`--veo-color-border-strong`는 텍스트 입력과 secondary 버튼의 **테두리**입니다. 컨트롤의
경계는 1.4.11이 3:1을 요구하는 대표적인 대상인데, 실제 값은 그 절반 수준이었습니다.

| 토큰 | 테마 | 이전 | 이후 | 배경 |
| --- | --- | --- | --- | --- |
| `--veo-color-border-strong` | light | `#a3c6d6` · **1.81:1** | `#5c8ea6` · **3.57:1** | `--veo-color-surface` |
| `--veo-color-border-strong` | light | `#a3c6d6` · **1.68:1** | `#5c8ea6` · **3.31:1** | `--veo-color-bg` |
| `--veo-color-border-strong` | dark | `#2c5b74` · **2.13:1** | `#4a86a4` · **3.90:1** | `--veo-color-surface` |
| `--veo-color-border-strong` | dark | `#2c5b74` · **2.58:1** | `#4a86a4` · **4.73:1** | `--veo-color-bg` |

`--veo-color-border`(카드 외곽선, 상단바 아래 선)는 **일부러 그대로 두었습니다.** light
1.38:1 / dark 1.47:1입니다. 1.4.11은 "사용자 인터페이스 **구성 요소**를 식별하는 데
필요한" 시각 정보에 적용되고, 카드 외곽선은 그 안의 내용이 이미 완전히 읽히는 장식
경계입니다. 이 판단은 `packages/ui/src/tokens.contrast.test.ts` 주석에 함께 적혀 있어,
누군가 다시 검토할 때 "빠뜨렸다"와 "판단했다"를 구별할 수 있습니다.

### 2.2 SC 1.4.11 — 상태 칩의 실루엣이 신호 역할을 못 하고 있었음

`StatusChip.module.css`는 주석으로 "모든 상태가 아이콘 모양 · 테두리 실루엣 · 한국어
라벨 세 가지 신호를 각각 가진다"고 선언하고 있었습니다. 그런데 실루엣을 그리는 테두리가
자기 배경 대비 1.30–1.95:1이라 **보이지 않았습니다.** 코드가 주장하는 것을 사실로 만들기
위해 테두리 값을 올렸습니다.

| 토큰 | light 이전 → 이후 | dark 이전 → 이후 |
| --- | --- | --- |
| `--veo-status-pass-border` | `#a9dcc1` 1.31:1 → `#38855c` **3.85:1** | `#1d6242` 1.95:1 → `#3a9767` **3.93:1** |
| `--veo-status-warning-border` | `#e5c98d` 1.40:1 → `#9d7020` **3.83:1** | `#6d4d14` 1.83:1 → `#ab8129` **3.97:1** |
| `--veo-status-fail-border` | `#eab2ad` 1.49:1 → `#bd524a` **5.80:1** | `#742c26` 1.62:1 → `#c05a4f` **4.06:1** |
| `--veo-status-na-border` | `#c9d2d8` 1.30:1 → `#6d7d88` **3.61:1** | `#2c4a5a` 1.46:1 → `#5f8291` **3.33:1** |
| `--veo-status-unknown-border` | `#c3cae9` 1.35:1 → `#6e77ab` **3.58:1** | `#333c73` 1.51:1 → `#6b76b5` **3.62:1** |

`--veo-status-fail-border`는 `TextField`의 오류 상태 테두리이기도 해서, 색상 팔레트가
아니라 컨트롤 경계로도 3:1을 넘어야 합니다(light 4.70:1 / dark 3.59:1 on surface).

실제 Chrome에서 다시 측정한 다섯 칩:

| 상태 | 모서리 | 선 | 텍스트/배경 | 테두리/배경 |
| --- | --- | --- | --- | --- |
| PASS | 999px (알약) | solid 1px | 6.87:1 | 3.85:1 |
| WARNING | 6px (둥근 사각) | solid 1px | 5.70:1 | 3.83:1 |
| FAIL | 3px (각진 사각) | solid **2px** | 5.80:1 | 5.80:1 |
| NOT_APPLICABLE | 999px (알약) | solid 1px | 6.90:1 | 3.61:1 |
| UNKNOWN | 10px | **dashed** | 7.28:1 | 3.58:1 |

다섯 개의 모서리·선 스타일이 모두 다르고, 아이콘 모양 다섯 개가 모두 다르며, 한국어
라벨 다섯 개가 모두 다릅니다. 색을 지워도 상태를 읽을 수 있습니다.

### 2.3 SC 2.4.1 건너뛰기 링크가 포커스를 옮기지 않았음

`<main id="veo-main">`에 `tabindex`가 없었습니다. 프래그먼트 링크는 스크롤만 옮기고
포커스는 그대로 두므로, "본문 바로가기"를 누른 뒤 Tab을 누르면 **방금 건너뛴 내비게이션으로
되돌아갑니다.** 링크가 아무것도 하지 않은 것과 같습니다.

- `<main id="veo-main" tabIndex={-1}>` — 공개 레이아웃, 콘솔 레이아웃, `ConsoleOutage` 세 곳 모두
- id는 `components/SkipLink.tsx`의 `MAIN_LANDMARK_ID` 하나에서만 나옵니다. 링크와 대상이
  따로 놀 수 없습니다
- `#veo-main:focus`의 아웃라인은 끕니다. 페이지 전체를 3px 테두리로 두르는 것은 정보가
  아니라 소음이고, 실제 조작 요소는 각자 포커스 표시를 유지합니다

건너뛰기 링크 자체는 `:focus-visible`이 아니라 `:focus`로 나타나게 바꿨습니다. 이 링크는
키보드로만 도달하고, 브라우저가 어떤 포커스를 "visible"로 분류하지 않기로 하면 **포커스는
가 있는데 화면 밖에 있는 링크**가 되기 때문입니다.

### 2.4 SC 2.4.3 포커스 순서 — 제출 버튼이 눌린 순간 포커스가 사라졌음

`Button`의 `busy`가 `disabled`를 함께 걸고 있었습니다. 자기 손가락 밑의 버튼이
`disabled`가 되면 브라우저는 그 요소를 탭 순서에서 빼고 포커스를 `<body>`로 떨어뜨립니다.
결과를 기다리는 사람이, 아무 안내 없이 페이지 맨 위로 던져집니다.

- `busy`는 이제 `aria-busy` + `aria-disabled`만 설정하고 요소는 계속 포커스를 유지합니다
- 클릭은 `Button` 안에서 삼킵니다 — `aria-disabled`가 장식이 되지 않도록
- 진짜로 사용할 수 없는 컨트롤(`<Button disabled>`, API 미연결)은 그대로 `disabled`입니다

### 2.5 SC 3.3.1 오류 식별 — 오류 요약이 없었음

`LoginForm`은 첫 번째 잘못된 **필드**로 포커스를 옮기고 있었습니다. 두 필드가 모두
비어 있으면 스크린 리더 사용자는 문제 하나만 듣고, 그것을 고쳐 다시 제출해야 두 번째
문제를 알게 됩니다. 그리고 로그인이 거절된 경우에는 옮길 필드 자체가 없어서, 포커스가
제출 버튼에 남고 메시지는 위에서 읽히지 않은 채 있었습니다.

- `FormError`가 오류 요약이 되었습니다: `role="alert"` + `tabIndex={-1}` + 문제 목록(`<ul>`)
- 제출 실패 시 요약으로 포커스가 갑니다. 요약은 폼 앞에 있으므로 Tab 한 번이면 첫 필드입니다
- 포커스 이동은 커밋 이후(`useEffect`)에 일어납니다. 핸들러 안에서 바로 옮기면 React가
  아직 메시지를 써넣기 전이라, 빈 영역에 포커스가 가서 "아무것도 아닌 것"으로 읽힙니다
- 필드별 메시지는 그대로 유지됩니다(`aria-describedby`, `aria-invalid`). 요약은 추가된
  층이지 대체가 아닙니다

### 2.6 SC 4.1.2 — 어느 화면을 보고 있는지 어디에도 표시되지 않았음

공개 헤더와 콘솔 사이드바 모두 현재 페이지를 표시하지 않았습니다. 시각적으로도,
프로그램적으로도 없었습니다. 콘솔 사이드바를 Tab으로 훑는 사람은 아홉 개 영역 중
어디가 열려 있는지 알 방법이 없었습니다.

- `components/NavLink.tsx` — `aria-current="page"` + `data-current`
- 표시는 색이 아닙니다: 사이드바는 왼쪽 세로 막대 + 굵기, 헤더는 밑줄 + 굵기
- 경로 일치는 세그먼트 단위입니다. `/console/projects`는 `/console/projects/42`에서
  현재이지만, `/console/scoring-versions`는 `/console/scoring`에서 현재가 아닙니다
  (단순 `startsWith`가 틀리는 지점)

### 2.7 SC 1.3.1 — 제목 구조

두 가지를 고쳤습니다.

1. **권한 없음 화면에 제목이 하나도 없었습니다.** 콘솔의 아홉 페이지는 자기 `<h1>`을
   포함해 본문 전체를 `PermissionGate`로 감쌉니다. 권한이 없으면 그 전부가 렌더링되지
   않으므로, 거절된 사용자에게는 제목이 0개인 페이지가 갑니다. `PermissionDenied`가
   이제 `<h1>`을 렌더링합니다(인라인 사용을 위해 `headingLevel`로 낮출 수 있음).
2. **콘솔 사이드바의 `<h2>`가 페이지 `<h1>`보다 앞에 있었습니다.** 사이드바는 문서상
   `<main>`보다 먼저 오므로, 제목 목록을 훑는 사람이 만나는 첫 제목이 h2였습니다.
   내비게이션 랜드마크는 이미 이름을 갖고 있어 이 제목은 아무 일도 하지 않았습니다.
   `<p id>` + `aria-labelledby`로 바꿔, 보이는 라벨이 곧 접근 가능한 이름이 되게 했습니다.

### 2.8 SC 4.1.1 — 중복될 수 있는 id

`UserMenu`가 `id="veo-user-menu-roles"`를 하드코딩하고 있었습니다. 이 컴포넌트는 서버
컴포넌트라 `useId`를 쓸 수 없으므로, `aria-labelledby` 대신 `aria-label="역할"`로
바꿨습니다. 콘솔 상단바에 조직 전환기가 붙어 계정 메뉴가 둘이 되는 순간 터질 결함이었고,
그 상황을 테스트가 지키고 있습니다.

### 2.9 SC 1.4.10 리플로우 — 400% 확대에서 가로 스크롤

1280px 뷰포트를 400% 확대하면 320 CSS px입니다. `.gridTwo`의
`repeat(auto-fit, minmax(320px, 1fr))`는 컨테이너가 320px보다 좁아지면 320px 트랙을
그대로 만들어 페이지를 옆으로 밀어냅니다.

Chrome에서 320px 폭으로 실측:

| 페이지 | 수정 전 규칙 적용 시 `scrollWidth` | 수정 후 |
| --- | --- | --- |
| `/tools/geo` | **344px** (뷰포트 320px — 가로 스크롤 발생) | **320px** |

- `minmax(min(320px, 100%), 1fr)` — 트랙이 컨테이너보다 넓어질 수 없게
- `.legendRow` / `.definitionList`는 640px 이하에서 단일 열로 접힘

확인한 공개 페이지 전부가 320px에서 가로 스크롤 없음: `/`, `/tools/seo`, `/tools/geo`,
`/tools/naver-keyword`, `/login`, `/results/[token]`.

### 2.10 SC 1.4.1 — ScoreCard 점수 낭독

점수는 레이아웃 때문에 `<span>72.4</span><span>／ 100점</span>`으로 쪼개져 있어 스크린
리더가 "72.4 슬래시 100점"처럼 읽습니다. 보이는 글자는 `aria-hidden` 처리하고
"100점 만점에 72.4점" 한 문장을 따로 제공합니다. `data-veo-score-state="scored|unmeasured"`도
붙여, "측정 불가"가 색만으로 구분되지 않는다는 것을 테스트가 확인할 수 있게 했습니다.

## 3. 점검했고 이미 올바른 상태였던 것

감사는 결함 목록만큼이나 "확인했고 문제없음"도 기록해야 합니다.

- **텍스트 명암비**: light/dark 두 테마에서 앱이 실제로 쓰는 모든 전경/배경 조합이
  4.5:1 이상. 가장 아슬아슬한 쌍은 dark의 `--veo-color-secondary` on `--veo-color-surface`
  **4.76:1**입니다. 팔레트를 손댈 때 가장 먼저 깨질 지점입니다
- **폼 라벨**: `TextField`는 항상 보이는 `<label htmlFor>`. placeholder를 라벨로 쓰지 않음
- **오류 연결**: `aria-describedby`가 오류를 힌트보다 **먼저** 가리킴 — 이미 한 번 들은
  안내보다 고쳐야 할 내용이 먼저
- **`aria-invalid`**: 유효한 필드에는 아예 없음(`false`를 붙이지 않음)
- **랜드마크**: banner / navigation(이름 있음) / main / contentinfo
- **아이콘**: 모든 장식 SVG가 `aria-hidden` + `focusable="false"`. 의미는 옆의 텍스트가 운반
- **아이콘 전용 컨트롤 없음**: `UserMenu`의 요약은 `aria-label="계정 메뉴: {이름}"`,
  `Avatar`의 이니셜은 장식이고 이름은 시각적으로만 숨김
- **`<details>` 기반 계정 메뉴**: 키보드로 열리고 JavaScript 없이 동작. 포커스 트랩 없음
- **로그아웃**: 평범한 form POST. JavaScript 없이 동작
- **감소된 모션**: 무한 반복 애니메이션은 두 개(Button 스피너, Skeleton 셰이머)뿐이고
  둘 다 `prefers-reduced-motion: reduce`에서 꺼짐. `--veo-duration-*` 토큰도 0ms가 됨
- **`<html lang="ko">`**
- **확대**: `viewport`에 `maximum-scale`이나 `user-scalable=no` 없음
- **`Skeleton`**: `role="status"` + `aria-live="polite"` + `aria-busy`

| `apps/web/src/components/a11y.test.tsx` | 건너뛰기 링크·main 랜드마크·`aria-current`·권한 없음 화면의 `<h1>` |
| `apps/web/src/app/(public)/login/LoginForm.test.tsx` | 오류 요약이 포커스를 받고 모든 문제를 한 번에 나열하는지 |

명암비 검사표의 각 행에는 **어느 요소가 그 조합을 만드는지**가 적혀 있습니다. 아무도
가리킬 수 없는 행은 없는 행보다 나쁩니다. 검사가 꼼꼼해 보이게 만들면서 실제로는
아무것도 확인하지 않기 때문입니다.

## 5. 자동 검사로 확인하지 못한 것 — 사람이 해야 하는 확인

**아래 항목은 아직 확인되지 않았습니다.** 자동 검사가 통과했다는 사실이 이 항목들에
대해 말해 주는 것은 없습니다.

### 5.1 스크린 리더로 직접

- [ ] **VoiceOver (macOS/Safari) + NVDA (Windows/Firefox)** — 두 조합 모두. 하나에서
      동작하는 것이 다른 하나에서 동작한다는 뜻이 아닙니다
- [ ] 로그인 실패 시 오류 요약이 **실제로 낭독되는지**. `role="alert"`에 포커스를 옮기는
      조합은 리더에 따라 두 번 읽히거나 한 번도 안 읽힐 수 있습니다. 특히 요약이 비어
      있다가 채워지는 전환
- [ ] `Skeleton`의 "불러오는 중"이 실제로 들리는지
- [ ] 상태 칩의 `title` 속성(판정 의미)은 **마우스 호버로만** 나옵니다. 키보드로도,
      대부분의 스크린 리더로도 도달하지 않습니다. 범례가 있는 화면에서는 `<dd>`가
      의미를 텍스트로 제공하지만, 범례 없이 칩만 있는 화면이 생기면 이건 결함이 됩니다
- [ ] `ScoreCard`가 `aria-label`(구역 이름)과 `<h3>`로 제목을 두 번 말하는 것이
      실제로 얼마나 거슬리는지
- [ ] 한국어 화면을 한국어 음성으로 들었을 때 `veo.seo.readiness 1.0.0` 같은 영문
      토큰이 어떻게 읽히는지

### 5.2 키보드로 직접

- [ ] 주소창에서 Tab 한 번 → 건너뛰기 링크가 **눈에 보이게** 나타나는지.
      규칙(`.veo-skip-link:focus { transform: translateY(0) }`)이 브라우저에 전달되는
      것까지는 확인했지만, 실제로 나타나는 장면은 확인하지 못했습니다
- [ ] 제출 중 버튼이 `disabled`가 되지 않는다는 것은 확인했지만, **그래서 포커스가 실제로
      유지되는지**는 확인 못 했습니다. jsdom은 `disabled` 설정 시 blur를 재현하지 않아
      원인(요소가 계속 활성)만 검증했고 결과(포커스 유지)는 검증하지 못했습니다
- [ ] 콘솔 전 화면 Tab 순회 — 키보드 함정이 없는지, 순서가 시각적 순서와 맞는지
- [ ] `UserMenu`를 연 뒤 Escape로 닫히지 않습니다(`<details>` 기본 동작). 의도된
      단순함이지만 실사용에서 답답한지 확인 필요
- [ ] 포커스 표시가 모든 배경 위에서 **보이는지**. 계산상 6.48–8.26:1이지만, 어두운
      카드 위 어두운 버튼 같은 조합은 눈으로 봐야 합니다

### 5.3 확대·확대율

- [ ] 브라우저 확대 200% / 400%를 **실제로** 걸었을 때. 위 실측은 뷰포트 폭을 줄여
      계산한 것이고, 확대는 폰트 렌더링과 서브픽셀 반올림이 함께 달라집니다
- [ ] 텍스트만 200% 확대(SC 1.4.4)
- [ ] 콘솔 화면(로그인 필요)의 320px 리플로우. 공개 화면만 실측했습니다

### 5.4 그 밖

- [ ] Windows **고대비 모드 / forced-colors**. 상태 칩의 모서리 반경과 선 스타일은
      살아남지만 배경 틴트는 사라집니다. 이때 다섯 상태가 구별되는지
- [ ] 색각 이상 시뮬레이션(1형·2형·3형)으로 다섯 상태 칩과 현재 페이지 표시
- [ ] `--veo-color-secondary` on dark surface **4.76:1** — 기준을 0.26 넘습니다.
      실제 화면에서 읽기 힘든 정도인지 눈으로
- [ ] 실제 저시력·전맹 사용자와의 사용성 테스트. 위 항목을 전부 통과해도 이것을
      대신하지 못합니다

## 6. 알면서 남겨 둔 것

- **`--veo-color-border`(1.38:1 / 1.47:1)** — 2.1 참조. 장식 경계로 판단했습니다.
  카드 외곽선이 상태나 조작 가능성을 나타내게 바뀌면 이 판단은 무효가 됩니다
- **`StatusChip`의 `title` 속성** — 5.1 참조
- **`Card`가 제목이 있을 때 `region` 랜드마크가 됨** — 카드가 많은 화면에서는 랜드마크
  목록이 길어집니다. 위반은 아니지만 소음입니다
- **`packages/ui`에 자체 감소된 모션 규칙이 없음** — 무한 애니메이션 두 개는 각자
  대응하지만, 짧은 색상 전환(130ms)은 `apps/web/globals.css`의 전역 규칙에 의존합니다.
  `@veo/ui`를 다른 앱에서 쓰면 그 앱이 같은 규칙을 갖고 있어야 합니다
- **자동 접근성 검사 라이브러리(axe-core 등) 미도입** — devDependency 추가 자체는
  허용 범위지만, pnpm에서는 루트 `pnpm-lock.yaml`을 함께 고쳐야 하고 그 파일은 이
  작업의 수정 범위 밖입니다. 도입하려면 `INTEGRATION_REQUEST.md`를 통해 루트 소유자의
  승인이 필요합니다. 다만 jsdom에서는 axe의 `color-contrast` 규칙이 동작하지 않으므로
  (CSS가 적용되지 않음) 얻는 것은 구조 규칙이고, 그 부분은 위 테스트가 직접 단언합니다

## 7. 다시 검사하는 법

```bash
# 명암비 + 모션 + 컴포넌트 접근성
pnpm --filter @veo/ui test

# 페이지 골격 접근성
pnpm --filter @veo/web test

# 전체
pnpm -r test
```

색 토큰을 바꾸면 `tokens.contrast.test.ts`가 바뀐 쌍의 실제 수치를 실패 메시지에
그대로 출력합니다. 새 색 조합을 화면에 도입하면 그 쌍을 검사표에 **추가해야** 합니다.
검사표에 없는 조합은 검사되지 않습니다.
