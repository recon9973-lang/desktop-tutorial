# 통합 요청 — 백업/복구·부하 담당

이 디렉터리와 `infra/load/`, `docs/operations/runbook-*.md`,
`apps/api/tests/operations/` 를 맡은 사람이 남깁니다.
아래는 **다른 사람 영역이라 직접 고치지 않은** 것들입니다.

---

## 1. Redis — 큐 백로그 회복이 검증되지 않은 채로 남아 있습니다

**요청 대상**: 인프라 / 배포 담당

**상황**: "생산을 멈추면 백로그가 빠지는가, 아니면 멈춰 버리는가" 는 이 저장소에서
한 번도 측정된 적이 없습니다. 개발 머신에 Redis 가 없고, `VEO_BROKER_URL` 이 없으면
Celery 는 eager 모드로 떨어져 아무것도 큐에 들어가지 않습니다.

kombu 의 인프로세스 `memory://` 전송을 대체재로 시도했다가 **측정으로 탈락시켰습니다**:
실제 Celery 워커(스레드 2, 태스크 5ms, `acks_late` 켜고 끄고, `polling_interval` 5ms)로
60건 중 15초 동안 16–18건만 소비하고 42–44건이 남은 채 진전이 멈췄습니다.
테스트하려는 바로 그 조건에서 멈추는 전송으로는 그 조건을 검증할 수 없습니다.

**필요한 것**: 스테이징이나 CI 에 Redis 인스턴스 하나. 전용 DB 인덱스면 충분합니다.

**그러면 바로 됩니다** (하네스는 이미 있습니다):

```bash
VEO_LOAD_BROKER_URL=redis://<host>:6379/1 \
  .venv/bin/python infra/load/run.py --only queue --produce 2000
```

`VEO_LOAD_BROKER_URL` 은 `VEO_BROKER_URL` 과 일부러 분리했습니다. 같은 변수를 쓰면
로컬 워커를 띄워 둔 사람이 실제 잡이 도는 브로커에 2000건을 붓게 됩니다.
하네스는 시작 전에 대상 큐가 비어 있는지 확인하고, 아니면 거부합니다.

**Redis 가 생겨도 이 하네스만으로는 여전히 검증 안 되는 것**:
워커 사망 후 재전달(visibility timeout), 워커 프로세스 여러 개 사이의 prefetch 분배,
브로커 연결 단절/재접속, dead-letter 로의 실제 흐름.
이건 별도 카오스 테스트가 필요합니다.

## 2. 발행된 점수 명세에 캐시가 없습니다 (성능)

**요청 대상**: `apps/api/src/veo/scoring/` 담당

→ **[`infra/load/INTEGRATION_REQUEST.md`](../load/INTEGRATION_REQUEST.md)** 에
전문이 있습니다. 측정값, 원인(`spec.py` 의 요청당 YAML 파싱 + 스키마 검증),
그리고 고칠 때 밟기 쉬운 함정 두 가지(테스트가 프로세스 도중에 명세 루트를 바꾼다는 것,
DB 불변성이 디스크 파일까지는 보장하지 않는다는 것)까지 정리되어 있습니다.

여기에 두 번 적지 않는 이유는 단순합니다 — 같은 내용이 두 군데 있으면 한쪽만
고쳐지고, 나중에 읽는 사람은 어느 쪽이 맞는지 알 수 없게 됩니다.

한 줄 요약: `GET /api/scoring/specs` 가 **32 req/s** (p99 1176 ms) 입니다.
같은 조건에서 PostgreSQL 을 때리는 `GET /api/projects` 가 230 req/s 입니다.
병목은 DB 가 아닙니다.

## 3. 백업 자동화 훅 (열려 있는 질문)

**요청 대상**: 배포 / 스케줄러 담당

`infra/backup/backup.sh` 는 지금 사람이 손으로 돌리는 물건입니다. 운영에서 매일
도는 무언가에 붙어야 하는데, 그 "무언가" 가 무엇인지(cron / k8s CronJob / 관리형
PostgreSQL 의 자동백업)를 아직 모릅니다.

- **관리형 PostgreSQL(RDS/Cloud SQL)을 쓴다면**: DB 덤프는 그쪽 자동백업에 맡기고,
  이 스크립트는 **답변 객체 저장소** 와 **검증(복구 훈련)** 용도로만 남기는 게
  맞습니다. 그 경우 `runbook-backup-restore.md` §2 를 그렇게 다시 쓰겠습니다.
- **자체 운영이라면**: WAL 아카이빙(§2.5)이 필요하고, 그건 이 머신에서 검증할 수
  없었습니다.

어느 쪽인지 알려 주시면 런북의 "검증 안 됨" 줄을 줄일 수 있습니다.

## 4. `aws` CLI / 오브젝트 스토리지 자격증명

**요청 대상**: 인프라 담당

`runbook-backup-restore.md` §2.4 의 오프사이트 업로드 절차는 이 머신에 `aws` CLI 가
없어 **실행해 보지 못했습니다.** 백업이 로컬 디스크에만 있으면 그 디스크를 잃는
사고에는 아무 도움이 안 됩니다.

버킷과 최소 권한(`s3:PutObject`, `s3:GetObject`, 해당 프리픽스 한정)을 주시면
절차를 실제로 돌려 보고 런북의 해당 표시를 지우겠습니다.
