# 런북: 자격증명 교체

대상: 외부 제공자 API 키, `VEO_JWT_SECRET`, 데이터베이스 비밀번호,
객체 스토리지 액세스 키.

두 가지 상황을 나눠 다룹니다.

- **정기 교체** — 예정된 작업. 무중단으로 진행합니다.
- **긴급 교체(유출 대응)** — 사고. 속도가 우선이며 짧은 중단을 감수합니다.

---

## 0. 판단 기준: 언제 유출로 보는가

아래 중 하나라도 해당하면 **유출로 간주하고 §3 으로 갑니다.**

- 커밋 이력에 자격증명이 들어갔다 (지웠어도 마찬가지)
- 로그·오류 메시지·모니터링 화면에 평문으로 찍혔다
- 채팅·이슈·문서·스크린샷에 붙여졌다
- 퇴사자 또는 접근 권한이 없는 사람이 열람할 수 있었다
- 제공자로부터 비정상 사용 알림을 받았다

**"아마 괜찮을 것 같다"는 판단은 하지 않습니다.** 교체 비용은 몇십 분이고,
유출된 키를 방치한 비용은 상한이 없습니다.

> 커밋된 비밀은 **삭제로 해결되지 않습니다.** 이력·포크·클론·CI 캐시·
> 코드 검색 인덱스에 남습니다. 유일한 대응은 **폐기 후 재발급**입니다.

---

## 1. 원칙

1. **새 자격증명을 먼저 만들고, 그다음에 옛것을 폐기합니다.**
   순서를 뒤집으면 그 사이가 그대로 장애 구간이 됩니다.
2. **제공자가 다중 키를 지원하면 겹치는 구간을 만듭니다.**
   신규 발급 → 배포 → 동작 확인 → 구 키 폐기.
3. **폐기까지가 교체입니다.** 새 키를 넣고 옛 키를 살려두면 아무것도
   해결되지 않습니다. 유효한 키가 하나 더 떠다닐 뿐입니다.
4. **교체 후 반드시 실제 호출로 확인합니다.** 설정이 반영됐는지가 아니라
   제공자 응답이 오는지를 봅니다.
5. **VEO 는 키가 없으면 UNKNOWN 을 보고합니다.** 교체 중 잠깐 비어도
   잘못된 숫자를 내보내지는 않습니다. 이 설계 덕분에 교체가 안전합니다.

## 2. 정기 교체

### 주기

| 자격증명 | 주기 | 비고 |
|---|---|---|
| 외부 제공자 API 키 | 12개월 | 제공자 정책이 더 짧으면 그쪽을 따름 |
| `VEO_JWT_SECRET` | 6개월 | §2.2 의 중단 영향 확인 |
| DB 애플리케이션 계정 비밀번호 | 6개월 | |
| 객체 스토리지 액세스 키 | 6개월 | |
| 담당자 이탈 시 | 즉시 | 그 사람이 접근 가능했던 전부 |

### 2.1 외부 제공자 키 (네이버·구글·OpenAI 등)

```
1) 제공자 콘솔에서 새 키를 발급한다. 구 키는 아직 지우지 않는다.
2) 비밀 보관소(운영)에 새 값을 넣는다.
      VEO_NAVER_SEARCHAD_API_KEY / VEO_NAVER_SEARCHAD_SECRET_KEY
      VEO_NAVER_DATALAB_CLIENT_ID / VEO_NAVER_DATALAB_CLIENT_SECRET
      VEO_OPENAI_API_KEY
      VEO_GOOGLE_PAGESPEED_API_KEY
      VEO_GOOGLE_SEARCH_CONSOLE_CREDENTIALS_JSON
3) api 와 worker 를 재시작한다. 설정은 lru_cache 로 캐시되므로
   재시작 없이는 새 값이 적용되지 않는다.
4) 확인:  GET /providers  →  해당 제공자가 ENABLED 인지
5) 실제 호출이 성공하는지 스캔을 한 건 돌려 확인한다.
6) 제공자 콘솔에서 구 키를 폐기한다.   ← 이걸 빼먹으면 교체가 아니다
7) 폐기 후 24시간 동안 오류율을 본다. 놓친 사용처가 있으면 여기서 드러난다.
```

`VEO_NAVER_SEARCHAD_*` 는 3개(키·시크릿·고객ID)가 모두 있어야 `ENABLED` 가
됩니다. 하나만 바꾸면 조용히 `DISABLED_NO_CREDENTIAL` 로 떨어지고, 지표는
UNKNOWN 이 됩니다. 세 값을 항상 함께 확인하세요.

### 2.2 `VEO_JWT_SECRET`

**교체하면 발급된 모든 토큰이 무효가 되고 전원 재로그인해야 합니다.**
서명 키가 바뀌면 기존 서명을 검증할 수 없기 때문입니다.

```
1) 새 값 생성:  openssl rand -hex 32
2) 사용자가 적은 시간대를 고른다.
3) 보관소에 반영하고 api 를 재시작한다.
4) 로그인 → 토큰 재발급 → 보호된 API 호출까지 확인한다.
```

중단 없이 하려면 이전 키로도 검증을 허용하는 구간이 필요합니다
(검증 키 목록 지원). 현재 설정에는 그 구조가 없으므로
**지금은 재로그인을 동반한 교체만 가능합니다.** 무중단이 필요해지면
`INTEGRATION_REQUEST.md` 로 요청을 올립니다.

### 2.3 데이터베이스 비밀번호

애플리케이션 계정과 마이그레이션 계정을 분리해 두었다면 하나씩 진행합니다.

```sql
ALTER ROLE veo WITH PASSWORD '<새 비밀번호>';
```

```
1) 보관소의 VEO_DATABASE_URL 을 갱신한다.
2) api, worker 를 순차 재시작한다(한 번에 전부 내리지 않는다).
3) 확인:  GET /health, 잡 하나 실행
4) 로그에 접속 문자열이 평문으로 찍히지 않는지 확인한다.
   (infra/monitoring/logging.md §3.1 — URL 안에 비밀번호가 들어 있다)
```

### 2.4 객체 스토리지 액세스 키

```
1) 새 액세스 키 쌍을 발급한다(구 키 유지).
2) VEO_S3_ACCESS_KEY_ID / VEO_S3_SECRET_ACCESS_KEY 갱신 후 재시작.
3) 리포트 내보내기를 한 건 돌려 업로드·서명 URL 다운로드를 확인한다.
4) 구 키를 비활성화한다. 곧바로 삭제하지 말고 며칠 비활성 상태로 둔다
   (놓친 사용처가 있으면 오류로 드러난다).
5) 문제가 없으면 삭제한다.
```

## 3. 긴급 교체 (유출 대응)

속도가 우선입니다. 겹침 구간을 포기하고 **먼저 끊습니다.**

### 3.1 즉시 (0~15분)

```
1) 유출된 자격증명을 제공자 콘솔에서 즉시 폐기한다.
   → 이 시점부터 해당 지표는 UNKNOWN 으로 나간다. 정상이며 의도된 동작이다.
   → 잘못된 숫자가 나가는 것보다 모른다고 하는 게 낫다.
2) 사고 기록을 연다: 발견 시각, 발견 경위, 대상, 노출 범위·기간.
3) 노출 경로를 차단한다.
     - 공개 리포지터리면 비공개 전환
     - 로그면 해당 로그 스트림 접근 제한
```

### 3.2 조사 (15~60분)

```
4) 제공자 콘솔에서 그 키의 사용 이력을 확인한다.
   낯선 IP, 비정상 호출량, 우리가 안 쓰는 엔드포인트 호출이 있는가.
5) 노출 시작 시점을 특정한다.
     git log -S '<비밀값의 일부>' --all --source
   (실행 후 셸 이력을 지운다: history -c)
6) 같은 값이 다른 곳에도 쓰였는지 확인한다.
   재사용된 비밀은 하나가 뚫리면 전부 뚫린 것으로 본다.
```

### 3.3 복구 (1~4시간)

```
7) 새 자격증명을 발급하고 보관소에 반영한다.
8) 전 서비스 재시작 후 GET /providers 로 ENABLED 확인.
9) 실제 스캔 한 건으로 종단 확인.
10) gitleaks 를 전체 이력에 다시 돌려 남은 비밀이 없는지 본다.
```

### 3.4 사후 (24~72시간)

```
11) 어떻게 들어갔는지 원인을 적는다. "실수였다"는 원인이 아니다.
    실수가 커밋까지 갈 수 있었던 구조가 원인이다.
12) 재발 방지 조치를 실제로 넣는다.
      - CI 의 gitleaks 잡을 필수 검사로 지정  (.github/workflows/ci.yml)
      - 로컬 pre-commit 훅에도 동일 스캔 추가
      - .gitignore 에 .env 계열이 확실히 들어 있는지 확인
13) 고객 데이터 접근 정황이 있으면 고지 의무를 판단한다.
```

## 4. 하지 말아야 할 것

- **자격증명을 채팅·이슈·PR 코멘트·스크린샷에 붙이지 않습니다.**
  붙인 순간 §3 의 대상이 됩니다.
- **`.env` 를 커밋하지 않습니다.** `.gitignore` 에 들어 있지만,
  `git add -f` 로 강제 추가하는 실수가 실제로 자주 일어납니다.
- **환경 간에 자격증명을 공유하지 않습니다.**
  스테이징 키로 운영 데이터를 건드릴 수 있으면 그건 분리가 아닙니다.
- **테스트·예시 파일에 진짜 같은 가짜 키를 쓰지 않습니다.**
  진짜인지 아닌지 판단하는 데 시간이 들고, 그 시간이 사고 대응을 늦춥니다.
  `.env.example` 의 모든 제공자 값이 비어 있는 이유입니다.
- **폐기를 미루지 않습니다.** "일단 새 키로 돌려놓고 나중에 지우자"가
  가장 흔한 실패입니다.

## 5. 교체 기록

교체할 때마다 남깁니다: 날짜, 대상, 사유(정기/긴급), 담당자,
구 키 폐기 완료 여부, 확인 방법.

폐기 완료 칸이 비어 있는 기록은 **미완료 작업**입니다.
