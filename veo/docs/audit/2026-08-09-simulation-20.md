### 이 시뮬레이션의 한계 — 먼저 적는다

**1장짜리 공개 진단 경로를 썼다.** 콘솔 진단은 최대 200장을 크롤하지만, 이 실행은
페이지 한 장만 본다. 그래서 **여러 장을 비교해야 하는 검사 6개는 구조적으로 측정
불가**였다(§2-C). 도달 범위가 0.80~0.82 에 묶인 이유가 그것이다.

**내가 1차 실행에서 두 가지를 틀렸다.** 그대로 적는다:

| 무엇 | 결과 | 고친 방법 |
|---|---|---|
| GEO 점수를 `payload.score` 에서 찾음 | GEO 10건이 전부 `None` 으로 기록됨 | GEO 는 `payload.readiness` 다 |
| 하위 페이지를 링크 순서대로 첫 번째로 고름 | `rss.php` · `manifest.json` · `sitemap.php` · 깨진 주소를 재서 20점대가 나옴 | 자산·피드·사이트맵을 걸러내고 본문 페이지를 고름 |

**두 번째가 특히 위험했다.** 20점대 점수가 나왔고, 그 숫자만 보면 "사이트가 엉망" 으로
읽힌다. 실제로는 **내가 사람이 안 읽는 파일을 대상으로 삼은 것**이다. 아래 표는 전부
고친 뒤 다시 돌린 값이다.

## 5. 발견과 수정 방안 — 우선순위 순

### P0 · 우리 제품의 오탐 — 한글 도메인을 외부 도메인으로 본다

**증상.** 더바른한의원이 `seo.canonical.not_cross_domain` CRITICAL 로 **점수가 40 에
상한 처리**된다. 홈·하위 두 건 모두.

**[실측] 실제 태그:**

```html
<link rel="canonical" href="https://더바른한의원.kr">
```

사이트는 `xn--9m1bm0ji9bd0qotax68d.kr` 로 서비스된다. 그리고 —

```
'xn--9m1bm0ji9bd0qotax68d.kr'.encode().decode('idna')  ->  '더바른한의원.kr'
같은 도메인인가: True
```

**같은 도메인이다.** punycode 는 한글 도메인의 표기일 뿐이다.

**원인.** `seo/parsing/urls.py:49`

```python
def host_of(url: str) -> str:
    return (urlsplit(url).hostname or "").lower()   # IDNA 정규화가 없다
```

한쪽은 유니코드 호스트, 다른 쪽은 punycode 호스트로 들어와 문자열 비교에서 갈린다.

**수정 방안.** `host_of()` 에서 호스트를 **ASCII(punycode)로 정규화**한 뒤 돌려준다.

```python
def host_of(url: str) -> str:
    host = (urlsplit(url).hostname or "").lower()
    if not host:
        return host
    try:
        return host.encode("idna").decode("ascii")
    except UnicodeError:
        # 인코딩 못 하는 호스트는 있는 그대로 둔다 — 지어내지 않는다.
        return host
```

**막는 시험**을 함께 둔다: `same_site("https://xn--9m1bm0ji9bd0qotax68d.kr/",
"https://더바른한의원.kr/")` 이 참이어야 한다.

**영향.** 이 오탐 하나가 거래처 한 곳의 점수를 **40(취약)** 으로 묶고 있다. 상한이
풀리면 실제 점수가 드러난다(해제 후 재측정 필요 — 지금 값은 상한에 잘린 값이라 진짜
점수를 나는 모른다).

**⚠ 이 수정은 거래처가 보는 점수를 바꾼다.** 사장님 승인 뒤에 적용한다.

### P1 · 코리아H병원 — 모바일에서 확대를 막고 있다 (상한 60)

**[실측] 실제 태그:**

```html
<meta name="viewport" content="width=device-width,initial-scale=1,
      minimum-scale=1,maximum-scale=1,user-scalable=no">
```

`user-scalable=no` 와 `maximum-scale=1` 이 **사용자의 확대를 금지**한다. 접근성 실패이고,
`https_or_mobile_failure` 상한 60 을 건다.

**수정 방안** — 거래처 사이트에서 한 줄:

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

`maximum-scale` 과 `user-scalable` 을 **지운다.** 다른 항목을 아무리 고쳐도 이것
전에는 60 을 못 넘는다.

### P1 · LCP — 10건 중 9건 실패

`seo.perf.lcp_lab` 이 거의 전부에서 실패한다. 가장 큰 요소(대개 첫 화면 이미지)가
늦게 그려진다는 뜻이다.

**수정 방안 (효과 순):**

1. 첫 화면 이미지에 `fetchpriority="high"` 와 정확한 `width`·`height`
2. 첫 화면 이미지를 `loading="lazy"` 에서 **빼기** (첫 화면에 lazy 를 걸면 늦어진다)
3. WebP·AVIF 로 바꾸기 — `seo.perf.modern_image_format` 도 함께 풀린다
4. 웹폰트를 `font-display: swap` 으로

거래처마다 원인이 다를 수 있어, **한 곳을 골라 고친 뒤 재측정해서 효과를 확인**하고
나머지에 적용하는 순서를 권한다.

### P2 · GEO 구조화 데이터가 화면과 다르다 — 10건 중 6건 BLOCKER

`geo.sd.matches_visible_content`. 구조화 데이터에 적은 상호·주소·전화·평점이 화면에
보이는 것과 다르다. AI 답변 엔진은 **둘이 다르면 둘 다 못 믿는다.**

**수정 방안.** 구조화 데이터의 `name`·`telephone`·`address` 를 **화면 바닥글에 실제로
적힌 글자와 한 글자까지 같게** 맞춘다. 특히 전화번호 표기(`02-1234-5678` vs
`0212345678`)가 자주 어긋난다.

이것은 **우리가 방금 만든 「홈페이지에서 불러오기」와 같은 자료를 본다** — 그 화면에서
후보로 뜨는 값이 곧 구조화 데이터에 있는 값이라, 화면 값과 대조하기 쉽다.

### P2 · GEO 직접 답변 문단이 없다 — 6/10

`geo.extract.direct_answer_present`. 질문에 바로 답하는 2~3문장 문단이 없다.

**수정 방안.** 주요 페이지마다 제목 바로 아래에 **질문형 제목 + 그 아래 2~3문장 요약**
을 둔다. AI 답변 엔진이 그대로 인용할 수 있는 모양이다.

### P3 · 측정 방법의 한계 — 6개 검사가 구조적으로 안 잡힌다

§2-C 의 6개는 1장 경로에서 못 잰다. **이 보고서의 SEO 점수는 그만큼 덜 잰 값**이고,
도달 범위 0.80 이 그 사실을 말한다.

**수정 방안.** 거래처 평가는 **콘솔 진단(크롤 경로)** 으로 한다. 무료 진단(1장)은 영업
도구이지 평가 도구가 아니라는 것을 화면에서도 더 분명히 하는 것이 좋다.

# 8. 2차 — P0 을 고치고 다시 쟀다 (같은 날)

사장님 지시: *"고치고. SEO GEO 점수 편차가 너무 많은데, 다시 시뮬레이션 돌려줘."*

## 8-A. 고친 것

`registrable_domain()` 이 호스트를 punycode 로 맞춘 뒤 비교한다
(`seo/parsing/urls.py`, 새 함수 `to_ascii_host`). `host_of` 가 아니라 여기를 고른 이유는
**이 함수를 지나는 비교가 셋**이기 때문이다:

```
seo.canonical.not_cross_domain    canonical 의 외부 도메인 판정   (상한 40)
detection/citations.py            AI 답변 인용의 자사 도메인 대조
same_site                         전반
```

인용 쪽이 특히 컸다 — 자사 도메인 인용은 **그것만으로** 확신도를 확정선 위로 올리는
신호라(가중치 0.95), 한글 도메인을 못 맞추면 **실제로 인용된 노출이 검수 대기로
사라진다.** SEO 만 고치고 끝났으면 그쪽은 남았을 것이다.

시험: `tests/seo/test_idn_hosts.py` 16개. 오탐을 막는 것과 **진짜 외부 도메인은 여전히
갈라내는 것**을 함께 지킨다.

## 8-C. 편차 — 사장님 지적이 맞다. 원인을 특정했다

같은 20회를 두 번 돌린 값을 대조했다.

```
GEO  10건   두 번 다 소수점까지 동일          편차 0.00
SEO  8건    최대 4.63점 움직임               평균 1.65
```

**GEO 는 흔들리지 않고 SEO 만 흔들린다.** 움직인 검사를 뽑아 보니 전부 하나의 무리였다:

```
seo.perf.lcp_lab    FAIL    -> 통과
seo.perf.tbt_lab    WARNING -> 통과
seo.perf.cls_lab    WARNING -> 통과
```

**전부 `seo.perf.*_lab`** — Lighthouse 가 실제로 페이지를 열어 시간을 재는 항목이다.

### 그런데 짧은 간격으로 재면 흔들리지 않는다

**[실측]** 같은 주소를 연달아 5번씩, 2사이트 x 2축 = 20회:

| 사이트 | 축 | 최저 | 최고 | 폭 | 표준편차 |
|---|---|---:|---:|---:|---:|
| 베놈애드 | SEO | 85.53 | 85.53 | **0.00** | 0.00 |
| 베놈애드 | GEO | 81.10 | 81.10 | 0.00 | 0.00 |
| 굿투어 | SEO | 76.06 | 76.06 | **0.00** | 0.00 |
| 굿투어 | GEO | 69.32 | 69.32 | 0.00 | 0.00 |

연속 5회는 **소수점 세 자리까지 같다.** 그런데 같은 굿투어가 20분 전에는 **83.21**
이었다. 폭이 **7.15점**이다.

### 왜 그런가 — 우리 캐시가 아니다

**[실측]** 우리 성능 캐시는 **진단 하나 안에서만** 산다. 전역 캐시가 아예 없고,
`tests/seo/test_perf_cache.py` 가 그것을 강제한다. 그 파일 머리글:

> "진단과 진단 사이에는 재사용하지 않는다. … 옛 값을 돌려주면 고쳤는데 점수가 그대로인
> 화면을 보게 되고, '고쳐도 안 바뀌네' 라는 잘못된 결론에 이른다."

5회는 **각각 다른 서비스 객체**로 돌렸으므로 우리 쪽에 공유 상태가 없다. 그래서 구글을
직접 불러 봤다:

```
PSI 직접 호출 1회차   performance_score 0.69
PSI 직접 호출 2회차   performance_score 0.69     (4초 뒤, 완전히 같음)
```

**구글이 같은 응답을 돌려준다.** 시간이 지나 구글이 Lighthouse 를 다시 돌리면 값이
바뀌고, 그 변화가 우리 점수에 그대로 들어간다.

### 정리하면

```
편차의 원인    성능(lab) 측정 — 구글이 언제 다시 재느냐에 달렸다
우리 코드      원인이 아니다 (같은 입력에 같은 출력)
GEO            영향 없음 (성능 항목이 없다)
관측된 폭      같은 사이트에서 최대 7.15점
```

## 8-D. 수정 방안 — 편차

### 가. 소수점을 없앤다 (작음, 지금 할 수 있음)

지금 화면에 **85.53** 처럼 소수점 두 자리가 나간다. 그런데 재현 가능한 폭이 ±7 이다.
**없는 정밀도를 파는 것**이고, 거래처가 "0.5점 올랐다" 를 개선으로 읽으면 우리가
거짓말을 한 것이 된다.

점수를 **정수로** 내고, 옆에 폭을 적는다 — 예: `78점 (성능 측정 특성상 ±5 흔들립니다)`.

### 나. 성능 항목을 여러 번 재서 중앙값을 쓴다 (중간)

Lighthouse 는 한 번 재면 흔들린다. 같은 URL 을 3회 재서 중앙값을 쓰면 폭이 줄어든다.
**대가는 PSI 호출 3배**다. 무료 한도(하루 25,000)에는 여유가 있지만 진단 시간이 늘어난다.

### 다. 추이는 같은 조건끼리만 비교한다 (이미 원칙으로 있음)

ADR 0010 이 *"비교는 조건이 같을 때만"* 이라고 못박아 두었다. 성능 항목이 흔들리는
동안에는 **"지난달 대비 +3점" 같은 문장을 만들지 않는다.** 지금 그런 문장을 만드는
자리가 있는지 확인이 필요하다.

### 라. 근본 — field(CrUX)로 옮긴다 (지금은 불가)

실사용자 값(CrUX)은 28일 누적이라 흔들리지 않는다. 그런데 §6 에서 본 대로 거래처
사이트들은 **CrUX 데이터가 없다.** 방문자가 늘기 전에는 못 쓴다.

**추천 순서: 가 → 다 → 나.** `가` 는 오늘 할 수 있고 거짓 정밀도를 즉시 없앤다.
