# 거래처별 항목 적용 — 조사·설계 기획서

**작성** 2026-08-07 · **상태** 결정 대기 (구현 착수 전)
**계기** 사장님 지시 — *"업체별 맞춤 항목으로 변동 가능성이 있는 것들은 변동해서 측정하고,
다른 항목이 없다고(쇼핑몰이 아닌데 장바구니가 없는 것처럼) 점수가 깎이는 일은 없어야 함.
업체별 구분 적용을 해서 실제 사용 가능하도록 구성하는 것이 맞게 보임."*

이 문서의 모든 숫자는 **운영 DB 실측**이다. 추정은 [추정]으로 표시한다.

---

# 1. 먼저 — 걱정하신 것은 이미 해결돼 있다

`쇼핑몰이 아닌데 장바구니 항목으로 깎이는` 일은 **일어나지 않는다.** 직접 계산해서 확인했다.

| 그 항목의 상태 | 총점 | 대가 |
|---|---|---|
| 통과 | 100.00 | — |
| **해당없음 (N/A)** | **100.00** | **0점** |
| 못 잼 (UNKNOWN) | 98.94 | −1.06점 |
| 실패 (전 페이지) | 98.94 | −1.06점 |

명세의 정책이 그렇게 적혀 있고 그대로 동작한다.

```yaml
not_applicable: EXCLUDE_FROM_DENOMINATOR      # 해당 없으면 분모에서 뺀다
unknown:        SCORE_AS_ZERO_KEEP_IN_DENOMINATOR
```

**그러므로 이 과제는 "깎이는 것을 막는 일"이 아니다.** 실제 과제는 아래 셋이다.

# 3. 발견한 문제 셋

## 문제 ① — B·C 갈래가 분모에서 빠져 **비교가 깨진다** ⚠️ 가장 중요

B와 C는 *"이 사이트에 해당 없음"*이 아니다. *"우리가 아직 못 잼"*이다. 그런데 A와
똑같이 분모에서 빠진다.

영향 범위는 **영역 셋, 20점**이다 — 전체 120점의 **16.7%**.

```
검색엔진 연동   10점   ← 통째로 빠짐
관측·성과        5점   ← 통째로 빠짐
오프페이지       5점   ← 통째로 빠짐
─────────────────────
              20점 / 120점
```

실제 진단 기록에서 이 세 영역은 **아예 나타나지 않는다**(영역 6개만 채점됨).

**지금은 사고가 안 난다.** 거래처 8곳 전부 서치콘솔 미연결이라 **모두 같은 분모**를
쓰기 때문이다. 그런데 **한 곳이라도 연결하는 순간 깨진다**:

```
A병원  서치콘솔 연결함    → 100점 만점으로 채점 (연동 항목 포함)
B병원  서치콘솔 미연결    → 100점 만점으로 채점 (연동 항목 제외)

두 점수를 나란히 놓고 "A가 더 낫다"고 말할 수 없다. 잣대가 다르다.
```

특허 문서가 지적한 **"미측정을 분모에서 빼면 역설이 생긴다"**가 여기서 실제로
기다리고 있다. 다만 문서의 처방("전부 분모 유지")은 갈래 A까지 깎으므로 쓸 수 없다.

## 문제 ② — 사람이 고칠 방법이 없다

`해당없음` 판단은 **전부 수집기 자동**이다. 거래처 표(`sites`)의 칸은 넷뿐이다.

```
origin · display_name · is_primary · crawl_settings
                                     ↑ 업종·유형·기능 유무 칸이 없다
```

자동 판정이 틀려도 손댈 자리가 없다. 예를 들어:

* 예약 기능이 **곧 붙을** 병원 → 지금 없다고 N/A인데, 대행사는 그걸 **과제로 잡고 싶다**
* 게시판을 **일부러 안 쓰는** 의원 → 영원히 N/A인데 매번 목록에 뜬다
* 지점이 여러 곳인데 **한 곳만** 예약을 받는 경우

## 문제 ③ — 진단이 대행사의 **작업 지시서**가 되지 못한다

지금 판정은 사이트의 *현재 상태*만 말한다. 대행사가 실제로 필요한 것은
**"이 거래처에서 우리가 할 일인가"**다.

```
지금        "구조화 데이터가 없습니다"            → 그래서 뭘 해야 하나?
필요한 것   "구조화 데이터 — 우리 담당 · 이번 달 작업" 또는
            "구조화 데이터 — 병원 개발사 담당 · 요청 보냄" 또는
            "구조화 데이터 — 이 거래처는 계약 범위 밖"
```

명세에 `remediation_owner`(담당: 개발자/마케터/원장) 칸이 이미 있는데
**거래처별로 바꿀 수 없다.**

# 4. 실무 시나리오 — 병원 마케팅 대행사

설계가 실제로 쓰이는 장면 다섯.

| # | 장면 | 지금 | 필요한 것 |
|---|---|---|---|
| 1 | 신규 거래처 등록 | 주소만 넣고 진단 | 업종·규모·기능 유무를 한 번 입력 |
| 2 | 첫 진단 결과 검토 | 59개 전부 나옴 | "이 거래처엔 해당 없음" 표시 후 목록에서 접기 |
| 3 | 원장이 "우린 예약 안 받아요" | 반영 불가 | 그 항목 끄고 **이유·시각·누가**를 남김 |
| 4 | 서치콘솔 권한 받음 | 자동 반영 | 반영 + **점수 잣대가 바뀌었음을 화면에 표시** |
| 5 | 월간 리포트 발송 | 전 항목 기준 | 계약 범위 안의 항목만 · 범위 밖은 별도 안내 |

**3번이 남용의 문이다.** 여기서 규율이 없으면 점수가 장사 도구로 전락한다.

# 5. 설계 대안

## 대안 1 — 거래처에 "업종 유형"만 붙인다 (가장 가벼움)

```
sites 표에 site_profile 칸을 더한다
  업종        치과 · 한의원 · 병원 · 여행 · 기타
  기능 유무   예약 ☐  쇼핑 ☐  게시판 ☑  다국어 ☐
```

수집기가 이 값을 참고해 N/A를 정한다.

| 좋은 점 | 나쁜 점 |
|---|---|
| 입력이 한 번, 화면이 단순 | 유형이 안 맞는 거래처가 반드시 생긴다 |
| 남용 여지가 작다 | 항목 단위 조정 불가 |
| 구현 작음 | 유형을 늘리는 일이 끝없이 생긴다 |

## 대안 2 — 항목 단위 예외 목록 (가장 정확)

```
site_check_overrides 표
  site_id · check_id · 결정(해당없음/담당변경/보류)
  이유(필수) · 정한 사람 · 정한 시각 · 만료일
```

| 좋은 점 | 나쁜 점 |
|---|---|
| 어떤 상황도 표현 가능 | **남용의 문** — 불리한 항목을 다 끄면 100점 |
| 이유·이력이 남아 감사 가능 | 거래처마다 관리 부담 |
| 담당자 지정까지 한 번에 | 화면이 복잡해진다 |

## 대안 3 — 둘을 겹친다 (권고)

```
1층  업종 유형        기본값을 정한다 (대안 1)
2층  항목 단위 예외   기본값을 덮어쓴다 (대안 2)
3층  수집기 자동      위 둘이 말이 없을 때 지금처럼 판단
```

**순서가 중요하다.** 사람이 명시한 것이 자동보다 우선하고, 항목 단위가 유형보다
우선한다. 어느 층에서 정해졌는지를 판정마다 기록한다.

# 6. 남용을 막는 규율 — 이것이 설계의 절반이다

점수는 우리가 파는 물건이다. **끌 수 있으면 반드시 꺼진다.** 방어를 먼저 정한다.

## 6-1. 끌 수 없는 항목을 정한다

```
관문 영역(색인 차단) 4개 항목은 어떤 이유로도 끌 수 없다
  · HTTP 상태 정상
  · meta robots 색인 허용
  · robots.txt 크롤 허용
  · JS 렌더링 일치

이유: 이 넷이 실패하면 검색에 존재하지 않는다.
     "해당 없음"이라는 말이 성립하지 않는다.
```

## 6-2. 끄면 점수가 오르지 않게 한다 ⭐ 핵심

**항목을 끄는 것은 분모에서 빼는 것이지 점수를 주는 것이 아니다.** 그런데 실패하던
항목을 끄면 분모가 줄어 **점수는 오른다.** 이것이 남용의 실제 이득이다.

세 가지 처리 중 하나를 골라야 한다.

| 안 | 방식 | 점수 | 평가 |
|---|---|---|---|
| **가** | 끈 항목은 분모에서 빼되, **끄기 전 점수를 상한으로 건다** | 안 오름 | 남용 이득 0. 구현 중간 |
| 나 | 끈 항목 수를 화면에 병기만 한다 | 오름 | 약함. 화면은 안 보고 숫자만 본다 |
| 다 | 끄는 데 승인자를 둔다 | 오름 | 사람이 막는다. 8곳일 땐 되지만 80곳이면 형식이 된다 |

**권고: 가 + 다.** 숫자로 이득을 없애고, 승인 기록도 남긴다.

## 6-3. 반드시 남기는 것

```
누가 · 언제 · 왜 · 언제까지
```

이유는 **자유 서술 필수**다. 목록에서 고르게 하면 아무거나 고른다.
만료일은 기본 **6개월** — 한 번 끈 것이 영원히 남지 않게 한다.

## 6-4. 리포트에 반드시 쓴다

거래처에 나가는 리포트에 이 문장이 들어가야 한다.

```
이 진단은 59개 항목 중 52개로 채점했습니다.
제외된 7개는 아래에 이유와 함께 표시했습니다.
```

**빼놓고 안 밝히면 그것은 거짓말이다.**

# 7. 문제 ①(비교 가능성)의 처방 — 별개로 정해야 한다

거래처별 예외와 **다른 문제**다. 섞지 않는다.

| 안 | 방식 | 평가 |
|---|---|---|
| **가** | 갈래 B·C를 `해당없음` 대신 **`보류`** 라는 새 상태로 | 분모에서 빼되 **"우리가 못 잰 것"**임이 기록에 남는다. 화면·리포트에서 구분 표시 |
| 나 | 지금처럼 두고 화면에만 표시 | 지금 상태. 두 거래처를 비교할 때 여전히 위험 |
| 다 | 분모에 넣고 0점 처리 | 거래처 잘못이 아닌 걸로 깎는다. 사장님 지시와 반대 |

**권고: 가.** `해당없음`을 두 가지 뜻으로 쓰는 것이 문제의 뿌리다.

```
해당없음 (N/A)    이 사이트에는 그런 것이 없다        → 분모 제외 · 정상
보류 (PENDING)    우리가 아직 잴 준비가 안 됐다        → 분모 제외 · 경고 표시
못 잼 (UNKNOWN)   재려 했는데 실패했다                → 분모 유지 · 0점
```

그리고 **점수 옆에 측정 범위를 항상 병기한다** — 이미 계산하고 있는 값이다.

```
79.7점  (59개 중 52개 기준 · 측정범위 88%)
```

# 8. 권고안 요약

| 순위 | 할 일 | 크기 | 이유 |
|---|---|---|---|
| **1** | `보류` 상태 신설 + 측정 범위 병기 | 중 | 비교 가능성. **지금 안 하면 거래처가 늘수록 손해** |
| **2** | 거래처 표에 업종·기능 칸 (대안 1) | 소 | 자동 판정의 정확도가 바로 오른다 |
| **3** | 항목 단위 예외 + 남용 방어 (대안 2·3) | 대 | 실무에 필요하나 규율 설계가 절반 |
| 4 | `remediation_owner` 거래처별 변경 | 중 | 작업 지시서가 된다 |

**1번을 먼저 하는 이유** — 2·3번은 거래처가 8곳인 지금 안 해도 굴러간다. 1번은
서치콘솔을 **한 곳이라도 연결하는 순간** 문제가 되고, 그때는 이미 쌓인 점수들이
서로 다른 잣대로 매겨진 뒤다.

# 9. 사장님 결정이 필요한 것

```
① 항목을 끌 수 있게 할 것인가 · 남용 방어는 '가+다' 안으로 할 것인가
② 끌 수 없는 항목(관문 4개)을 그대로 둘 것인가
③ 예외의 기본 만료를 6개월로 할 것인가
④ 업종 분류를 어떻게 나눌 것인가 — 지금 거래처: 한의원·병원·여행
⑤ 리포트에 제외 항목을 밝히는 문구를 넣을 것인가
```

**⑤는 넣는 것 외에 다른 답이 없다고 본다.** 나머지는 판단 사항이다.

# 10. 이 문서의 검증 상태

```
[실측]  판정 분포 2,207건 · N/A 이유별 집계 · N/A 0점 손실 · 영역 20점 제외
[실측]  거래처 8곳 전부 서치콘솔 미연결
[설계]  대안 1·2·3 · 남용 방어 3안 · 만료 6개월
[추정]  없음
```

**⚠️ 대안의 구현 크기(소·중·대)는 감이며 실제로 재보지 않았다.**
