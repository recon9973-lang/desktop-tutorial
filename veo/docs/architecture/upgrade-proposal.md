# VEO 전수조사와 업그레이드 제안

작성 2026-07-30 · 대상 명세 1.6.0 · 배포 커밋 `e4419dc`

이 문서는 셋으로 되어 있습니다. **1부**는 코드베이스를 실제로 재고 프로파일한 결과,
**2부**는 제품 방향 제안, **3부**는 화면 제안입니다. 추측한 것과 측정한 것을 구분해
적었고, 측정한 값에는 어떻게 쟀는지를 함께 남겼습니다.

## 1부 · 전수조사

### 1.1 규모 — "20만 줄" 은 생성물을 포함한 숫자입니다

| 구분 | 줄 | 파일 |
|---|---:|---:|
| API 소스 | 60,306 | 234 |
| API 테스트 | 41,247 | 186 |
| 웹 소스 | 8,499 | 73 |
| UI 패키지 | 2,426 | 28 |
| 채점 명세(YAML) | 5,138 | 8 |
| **사람이 쓴 코드 합** | **117,616** | **529** |
| 생성물(`schema.d.ts`, `openapi.json`) | 24,521 | 2 |

테스트가 소스의 **68%** 입니다. 이 비율은 유지할 값어치가 있습니다 — 이번 주에만
채점 규칙의 실제 결함 세 가지(연동 항목이 분모를 흔들던 것, 스키마 없으면 배점이
사라지던 것, 구조화 데이터 대조의 오탐)를 테스트와 실측이 잡았습니다.

`TODO`·`FIXME` 주석은 **0개**입니다. 미룬 일을 주석에 숨겨 두지 않았다는 뜻이고,
실제로 미뤄 둔 것들은 명세 변경 이력에 사유와 함께 적혀 있습니다.

### 1.2 성능 — 병목은 채점이 아니라 수집입니다

측정 방법: `cProfile` 로 20회 반복, 4페이지 픽스처. 명세 로딩·정규식 컴파일은 예열로 제외.

| 구간 | 시간 |
|---|---:|
| 채점 1회 전체 (57항목) | **3.0 ms** |
| ├ HTML 파싱 (5문서) | 3.0 ms 중 1.2 ms |
| ├ 본문 중복 비교(shingle) | 1.1 ms |
| └ 나머지 55개 검사 | 0.7 ms |
| **실제 사이트 수집 (7페이지)** | **2.0 초** (페이지당 0.29초) |

**채점은 수집의 1/700 입니다.** 채점기를 최적화할 이유가 없습니다.

수집은 직렬입니다:

```python
# apps/api/src/veo/seo/crawl.py:84
documents = tuple(self._fetch(url) for url in targets)
```

콘솔 상한이 `console_max_urls_per_scan = 20` 이므로 최악 **약 6초**. 지금은 견딜 만하지만,
아래 2부에서 제안하는 "사이트 전체 크롤"(수백 페이지)로 가면 이 줄이 곧 벽이 됩니다.

**다만 그냥 병렬로 바꾸면 안 됩니다.** 대상은 고객의 서버이고, 20개 요청을 한꺼번에
던지면 우리가 진단하러 가서 부하를 주는 셈입니다. `HostBudgetGuard` 가 이미 호스트별
예산을 재고 있으므로, 그 안에서 **동시 3~4개 + 호스트별 간격**이 맞는 절충입니다.
6초 → 약 2초가 되고 예의도 지킵니다.

### 1.3 견고성 — 무작위 시나리오 3,400회에서 예외 0

이번 검수에서 돌린 것:

| 축 | 규모 | 결과 |

| 전체 스위트 × 해시시드 10종 | 3,830 × 10 | 실패 0 |

| 강제 극단 상황 | 14종 | 위반 0 |

무작위 조합은 픽스처 10 × 연동 부분집합 × HTML 훼손 15종(head 제거·빈 문서·태그 잘림·
제어문자·5,000자 title·300단 중첩·이모지 서로게이트) × 상태코드 8종 × 압축 헤더 5종 ×
페이지 수 × 로케일 3종을 섞은 것입니다.

### 1.4 남아 있는 것

**~~막힌 기능 — 팀으로 못 씁니다.~~ (2026-07-30 정정)**

이 문단은 **틀렸습니다.** `docs/operations/release-checklist.md` 의 "API 가 아직 없다"

우리가 모릅니다.

**GEO 관측이 비어 있습니다.** 제품 이름이 `SEO · GEO` 인데 GEO는 준비도만 있고 실제
AI 답변 관측이 없습니다. 아래에서 다룹니다.

## 2부 · 업그레이드 방향

### 2.1 지금의 위치

경쟁 도구(NXT)와 실측 비교 — 같은 사이트(`chamsarang1075.com`):

| | NXT | VEO |
|---|---|---|
| 점수 | 69점 | 83.4점 |
| 항목 수 | 24 | **57** |
| 만점 기준 | 항목 가중합 | **100점 고정** |
| 못 잰 항목 표시 | 없음 | 6개, 이유까지 |
| 수정 방법 | 없음 | 항목마다 예시 코드 |
| 배점 근거 공개 | 없음 | 명세 파일 + 체크섬 |

**우리가 이미 앞선 것**은 판정의 투명성입니다. 점수마다 명세 버전·체크섬·계산 과정이
붙고, 못 잰 항목은 왜 못 쟀는지가 남습니다. 이건 경쟁 도구가 흉내내기 어려운 자산입니다 —
설계에서부터 그렇게 만들어야 하기 때문입니다.

**뒤진 것**은 범위입니다. 우리는 여전히 "받은 URL 몇 장" 만 봅니다.

### 2.2 제안 — 우선순위 순

#### ① ~~다중 사용자 · 역할~~ — 완료 (2026-07-30)

엔진에는 이미 있었고 화면만 없었습니다. `/console/team` 을 만들어 닫았습니다 —
팀원 목록, 초대(1회용 링크 발급), 초대 재발송, 역할 변경, 계정 비활성.

남은 것: 담당자별 업체 배정과 "누가 무엇을 언제 고쳤는지" 는 아직 없습니다.

#### ② 사이트 전체 크롤 + 병렬 수집

지금은 사람이 URL을 손으로 넣습니다. sitemap과 내부 링크를 따라 자동으로 넓히고,
1.2에서 말한 대로 호스트 예산 안에서 병렬화합니다. 이게 되면 지금 늘 측정 불가인
항목들(내부 링크 도달성·중복 본문·클릭 깊이)이 실제로 측정되기 시작합니다.

#### ③ GEO 관측 — 제품 이름의 절반을 채우는 일

리서치에서 확인한 것: 2026년 GEO 도구 시장은 **AI 답변 안에서의 인용·언급을 추적**하는
쪽으로 정리됐습니다. Profound 같은 도구는 ChatGPT·Perplexity·AI Overviews 등 10여 개
엔진을 봅니다.

주목할 연구 결과가 하나 있습니다 — 2026년 논문에 따르면 Perplexity·SearchGPT·Gemini의
**인용은 같은 질문을 반복해도 크게 흔들립니다.** 한 번 재고 "노출됨/안 됨" 이라고
보고하는 도구는 정밀해 보이지만 틀린 그림을 줍니다.

이건 VEO의 방법론과 정확히 맞습니다. 우리는 이미 신뢰도와 측정 범위를 점수와 분리해
보고합니다. **"같은 질문 N회 반복, 인용률 ±범위, 표본 수"** 로 내보내면, 단발 측정으로
확언하는 경쟁 도구보다 정직하면서 더 유용합니다. 준비도(GEO Readiness)와 관측(Observation)을
절대 섞지 않는다는 기존 원칙도 그대로 지켜집니다.

#### ④ 헤드리스 렌더링

②를 하면 크롤 비용이 커지므로, 주요 페이지에만 선별적으로 렌더러를 붙입니다.
`js_render_parity` 가 실제로 측정되기 시작하고, 지연 로딩 검사의 정확도도 올라갑니다.

#### ⑤ 추이와 회귀 알림

이력은 이미 저장하고 있습니다. 여기에 **"지난번 통과했는데 이번에 실패한 항목"** 을
따로 뽑아 주면 됩니다. 이미 `RECURRED`·`regression_count` 를 기록하고 있으므로 화면만
붙이면 되는 일입니다.

## 3부 · 화면 제안

### 3.1 지금 화면의 실제 문제 — 측정값

브라우저에서 실제로 렌더해 잰 값입니다.

| | |
|---|---:|
| 상세 보기 페이지 높이 | **6,476 px = 화면 7.2개** |
| 항목 수 (전부 접힌 상태) | 44 |
| 전부 펼쳤을 때 추정 높이 | 약 13,500 px |
| **필터·정렬·검색 UI** | **0개** |
| 심각도 분포 | 치명 3 · 심각 7 · 중요 15 · 경미 19 |

**대비는 문제가 아닙니다.** 본문 텍스트 대비를 전부 재 봤고 최저 8.13:1 로 기준(4.5:1)을
크게 넘습니다. 색을 손댈 필요는 없습니다.

문제는 **구조**입니다:

1. **7화면을 스크롤해야 전체가 보이는데, 좁힐 방법이 하나도 없습니다.** 44개 중 실패는
   5개인데 그 5개를 찾으려면 눈으로 훑어야 합니다.
2. **가장 중요한 신호가 가장 조용합니다.** 심각도(치명/심각/중요/경미)가 오른쪽 끝에
   흐린 회색 작은 글씨입니다. 통과한 경미 항목과 실패한 치명 항목이 같은 무게로 보입니다.
3. **점수를 볼 방법이 숫자뿐입니다.** 영역별 점수가 `27.6 / 31.25` 같은 텍스트 행이라,
   어느 영역이 무겁고 어디서 잃었는지 한눈에 안 들어옵니다.

### 3.2 리서치가 말하는 방향

2026년 대시보드 설계에서 반복해 나오는 것:

- **"우선순위 먼저, 설명은 그다음, 원자료는 요청할 때만."** 2020년경에는 위젯을 많이
  얹는 것이 가치라고 봤지만 지금은 반대입니다.
- **차트보다 잘 만든 표.** 밀도 높은 표로 돌아가는 흐름입니다. Linear가 예로 자주 인용되는데,
  36px 행 높이·키보드 우선·장식 최소로 밀도를 올리면서도 어수선하지 않습니다.
- **신호등(양호/주의/위험) 3단계.** 고객이 이해 못 하는 복잡한 점수 체계를 피하라는 조언이
  반복됩니다.
- **매일 쓰는 도구는 다크 우선**, 가끔 보는 업무 대시보드는 라이트 우선.
- **역할별 화면.** 로그인하는 사람이 같은 일을 하지 않습니다.

VEO에 그대로 적용되는 조언입니다. 직원 콘솔은 매일 쓰는 도구(다크 우선·밀도), 업체에
보내는 리포트는 가끔 보는 문서(라이트 우선·설명 우선)입니다. 이미 `간소화`/`상세` 로
나눠 둔 것이 이 방향과 맞습니다.

### 3.3 구체적 제안

#### A. 항목 목록을 표로 — 그리고 좁힐 수 있게

카드 44장을 **밀도 높은 표**로 바꿉니다. 행 하나에 상태·제목·영역·심각도·배점 영향.
행을 누르면 지금처럼 근거와 수정 방향이 펼쳐집니다.

그 위에 **필터 한 줄**을 둡니다:

```
[ 전체 44 ] [ 실패 5 ] [ 주의 4 ] [ 측정 불가 6 ]      영역 ▾    심각도 ▾    🔍
```

숫자가 붙은 칩을 누르면 바로 좁혀집니다. 지금 없는 것 중 가장 아쉬운 기능이고,
만들기도 가장 쉽습니다.

#### B. 심각도를 왼쪽으로, 색과 굵기로

오른쪽 끝 흐린 글씨 대신 **행 왼쪽에 4px 색 띠**를 둡니다. 치명·심각은 붉은 계열,
중요는 주황, 경미는 회색. 색만으로 전달하지 않도록 글자도 함께 둡니다(기획서 §12.1).

훑을 때 "어디가 아픈가"가 눈으로 먼저 들어옵니다.

#### C. 영역별 점수를 막대로

```
크롤링·색인 가능성    ████████████████░░░░  27.6 / 31.25
온페이지 시맨틱       ██████████████████░░  18.3 / 18.75
콘텐츠·정보구조       ███████████░░░░░░░░░  10.9 / 18.75   ← 여기서 가장 많이 잃음
```

막대 길이는 배점에 비례시켜 어느 영역이 무거운지도 함께 보이게 합니다.

#### D. 맨 위에 "오늘 할 일 3개"

`improvements` 는 이미 실제 산식으로 점수 상승폭을 계산합니다. 상위 3개만 크게 띄우고
나머지는 접습니다. 리서치가 말하는 "우선순위 먼저"가 이것입니다.

#### E. 왼쪽에 목차 고정

7화면을 오가려면 현재 위치와 이동 수단이 필요합니다. 영역 이름을 세로로 세워 두고
현재 보는 곳을 표시합니다.

#### F. 업체 전달용 인쇄/PDF

`간소화` 보기를 A4로 인쇄했을 때 깨지지 않게 합니다. 대행사가 고객에게 보내는 것이
실제 사용 흐름인데 지금은 그 경로가 없습니다.

### 3.4 제안하는 순서

| 순서 | 항목 | 근거 |
|---|---|---|
