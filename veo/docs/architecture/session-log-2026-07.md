# 작업 기록 — 2026년 7월 29~30일

명세 1.2.0 → 1.6.0, 콘솔 화면 셋, 그리고 그 과정에서 잡은 결함들.

이 문서는 **무엇을 왜 그렇게 했는지**를 남긴다. 코드는 스스로 무엇을 하는지 말하지만
왜 그렇게 되었는지는 말하지 않고, 특히 **틀렸다가 고친 것**은 코드에 흔적이 남지 않는다.
반년 뒤 "이건 왜 이렇게 되어 있나" 에 답하기 위한 기록이다.

---

## 1. 핵심 알고리즘 — 점수는 어떻게 나오는가

### 1.1 산식

```
penalty_i       = 심각도계수 × 상태배수 × 적용비율 × 신뢰도
category_budget = 채점된 항목들의 심각도계수 합
category_score  = 100 × max(0, 1 − Σpenalty / budget)
overall         = Σ(category_score × weight) / Σ(점수를 이루는 영역의 weight)
caps            = overall 을 위에서 누른다. 상한이 점수를 올리는 일은 없다.
gates           = 점수 옆에 표시만 한다. 숫자를 바꾸지 않는다.
```

| 심각도 | 계수 | | 상태 | 배수 |
|---|---:|---|---|---:|
| BLOCKER | 1.00 | | FAIL | 1.0 |
| CRITICAL | 0.60 | | WARNING | 0.5 |
| MAJOR | 0.30 | | PASS | 0.0 |
| MINOR | 0.10 | | UNKNOWN | (아래) |
| INFO | 0.00 | | NOT_APPLICABLE | 분모에서 제외 |

**숫자는 모두 `packages/scoring-specs` 의 발행 명세에만 있다.** 검사기 코드에는 하나도
없고, 그것을 지키는 검사가 있다 — 명세의 모든 숫자를 바꿔 넣고 관측이 하나도 안 움직이는지
확인한다(`test_collector_contract.py`).

### 1.2 절대 평가 — 이 판의 핵심 변경

`UNKNOWN` 은 **심각도 계수를 예산에 더한 채 그만큼 벌점을 받는다.** 못 잰 이유가 우리
쪽이든 대상 쪽이든 얻지 못한 점수는 얻지 못한 것이다.

예외는 `NOT_APPLICABLE` 하나뿐이다 — "이 대상에는 그 항목이 존재하지 않는다" 는 뜻이지
"없다" 가 아니다. 페이지네이션이 없는 사이트에 페이지네이션 검사를 0점으로 매기면 없는
결함을 지어내는 것이다.

한 번도 재지 못한 대상은 0점이 아니라 **측정 불가**다. 사이트를 가져오지 못한 것과
사이트가 나쁜 것은 다른 사실이다.

### 1.3 분모 고정

**점수를 이루는 영역만으로 100이어야 하고, 그 분모는 고객 상태에 따라 움직이지 않는다.**

이 원칙을 세 번에 걸쳐 배웠다. 세 번 다 같은 실수였다 — 분모가 움직였다.

| 판 | 무엇이 분모를 흔들었나 | 결과 |
|---|---|---|
| 1.1.0 이전 | `UNKNOWN` 이 예산에서 빠짐 | 20점어치를 못 잰 사이트가 **91.8점** (실제 59.1) |
| 1.3.0 이전 | 연동 영역이 통째로 해당 없음 | **연결할수록 불리** — 안 하는 편이 유리 |
| 1.4.0 이전 | 구조화 데이터 없으면 12.5점 면제 | **만들수록 불리** — 안 만드는 편이 유리 |

셋 다 진단 도구가 만들면 안 되는 유인이다. 해법은 같다 — 잴 수 없는 영역은 **애초에
점수의 일부가 아니라고 명세에 적고**(`contributes_to_score: false`), 나머지로 100을 만든다.

### 1.4 연동 게이트

검사마다 `availability` 를 둔다.

| 값 | 뜻 | 배점 |
|---|---|---|
| `SELF_SERVICE` | VEO 가 스스로 잰다 | 포함 — 못 쟀다면 **우리가** 안 한 것 |
| `CUSTOMER_GRANTED` | 사이트 소유자가 권한을 줘야 | 제외 + 무엇을 연결하면 되는지 표시 |
| `PAID_PROVIDER` | 유료 데이터원 필요 | 제외 + 위와 같음 |

뒤의 둘은 연동 전까지 `NOT_APPLICABLE` 이 되고 **"이 진단의 배점 밖"** 구역에 사유와
함께 남는다. 아직 요청하지도 않은 권한 때문에 고객 점수가 낮아지면 안 된다.

때문이다 — 그 구간에 있다는 것은 첫 갱신 시도가 이미 실패했다는 신호다. 남은 기간은
`now` 가 아니라 **수집 시각** 기준으로 잰다. 며칠 전 자료를 다시 채점할 때 값이 달라지면
안 된다.

## 3. 화면

### 3.1 항목별 판정 (`ScanReport` · `CheckExplorer`)

경쟁 도구(NXT)는 판정 옆에 무엇을 보고 그렇게 판정했는지 보여주는데, 우리는 상태와
`seo.onpage.heading_hierarchy` 같은 식별자만 찍었다. 직원이 그 줄을 보고 할 수 있는
일이 없었다.

정작 그 근거는 수집기가 이미 만들고 있었다 — `observed_value` 에 페이지별 관측값이
담기는데 API 스키마에 자리가 없어 경계에서 버려졌다. **새로 재지 않고 버리지 않게** 했다.

지금 구조:

```
SEO 기술 준비도          점수·등급·구간표·상한
100점까지 — 개선 할 일    상위 3개 크게, 나머지 접기
영역별 점수              배점 비례 막대 (31.25점 영역이 12.5점 영역보다 길다)
항목별 판정              [전체 44][실패 13][주의 10][측정불가 6][통과 10]
  └ 5개 테마로 그룹핑
     └ 각 항목: [상태칩] 제목 ....... 심각도   ← 왼쪽 4px 색 띠
        펼치면 → 이렇게 판정한 근거 / 어떻게 고치나
측정하지 못한 항목
이 진단의 배점 밖         연동 필요 10개
근거와 출처              명세 버전·체크섬·근거 건수
```

`details`/`summary` 를 쓴다 — 자바스크립트 없이 열리고, 키보드로 다룰 수 있고, 브라우저의
페이지 내 검색이 **닫힌 내용까지** 찾아 준다. 직접 만든 토글은 셋 다 잃는다.

### 3.2 팀원 관리 (`/console/team`)

엔진에는 이미 전부 있었다 — 목록·초대·재발송·역할 변경·계정 비활성. **없던 것은 화면
하나**였다.

정한 것들:
- **초대 메일을 보내지 않는다.** 엔진이 1회용 링크를 돌려주고 관리자가 직접 전달한다.
- **링크를 자동으로 지우지 않는다.** 한 번 닫으면 다시 볼 수 없다(토큰은 해시로만
  저장된다). 그때는 재발송뿐이라, 관리자가 직접 닫을 때까지 남긴다.
- **자기 자신은 손대지 못한다.** 관리자가 스스로를 내리면 조직에 관리자가 남지 않고,
  그때는 DB 를 직접 손대는 것 말고 방법이 없다.
- **계정 삭제 버튼이 없다.** 비활성으로 충분하고, 지우면 그 사람이 실행한 진단의
  "누가 측정했는가" 가 함께 사라진다.
- 역할 이름 아래에 그 역할이 할 수 있는 일을 적는다 — 이름만 보고는 고를 수 없다.

### 3.3 세션

접근 토큰 15분 · 갱신 토큰 14일. 갱신은 `proxy.ts` 에서 한다 — Next.js 는 서버
컴포넌트가 쿠키를 고치는 것을 막으므로, 응답을 만들기 전에 도는 그 자리가 쿠키를 얹을
수 있는 유일한 곳이다. 로그아웃은 **두 쿠키를 모두** 지운다(갱신 토큰을 남기면
로그아웃을 눌렀는데 다시 들어가진다).

## 5. 이번에 잡은 결함

내가 만든 것과 원래 있던 것을 섞지 않고 적는다.

### 채점

| 결함 | 어떻게 드러났나 |
|---|---|
| UNKNOWN 이 분모에서 빠져 91.8점 | 사용자 지적 |
| 연동 영역이 분모를 흔듦 | 사용자가 "배점 수정했나" 물음 |
| 구조화 데이터 없으면 12.5점 면제 | 20조합 불변식 점검 |
| `WebPage.name` 오탐 — 제대로 만든 사이트가 실패 | **실제 사이트 측정** |
| doctype 검사가 구조화 데이터 영역에 있었음 | 명세 검토 |

### 화면

| 결함 | 어떻게 드러났나 |
|---|---|
| 배점 밖 영역이 "측정 불가" 로 섞여 표시 | **렌더해서 봄** |
| 빈 관측값이 이름만 남은 줄로 그려짐 | **렌더해서 봄** |
| 막대가 `flex-grow` 라 항상 전체를 채움 | **픽셀을 잼** |
| 팀원 관리가 `/api` 를 빠뜨려 전부 404 | **배포 후 사용자가 봄** |
| 초대자가 자기 아이디를 모른 채 로그인 화면에 | 사용자 질문 |
| 세션 15분 — 갱신 토큰을 버리고 있었음 | 사용자 지적 |
| `middleware.ts` / `proxy.ts` 충돌로 빌드 실패 | **배포 후 사용자가 봄** |

**패턴이 보인다.** 테스트가 잡은 것보다 **실제로 그려 보고·재 보고·배포해 보고** 잡은
것이 많다. 특히 마지막 둘은 사용자가 발견했다 — 그래서 §7 의 조치를 넣었다.

| 조치 | 막는 것 |

CI 에 **웹 작업이 아예 없었다** — 웹은 타입체크조차 돌지 않았다. 그게 근본 원인이다.
