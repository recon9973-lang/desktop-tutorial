# 작업 기록 — 2026년 7월 29~30일

명세 1.2.0 → 1.6.0, 콘솔 화면 셋, 그리고 그 과정에서 잡은 결함들.

이 문서는 **무엇을 왜 그렇게 했는지**를 남긴다. 코드는 스스로 무엇을 하는지 말하지만
왜 그렇게 되었는지는 말하지 않고, 특히 **틀렸다가 고친 것**은 코드에 흔적이 남지 않는다.
반년 뒤 "이건 왜 이렇게 되어 있나" 에 답하기 위한 기록이다.

## 1. 핵심 알고리즘 — 점수는 어떻게 나오는가

### 1.1 산식

```
penalty_i       = 심각도계수 × 상태배수 × 적용비율 × 신뢰도
category_budget = 채점된 항목들의 심각도계수 합
category_score  = 100 × max(0, 1 − Σpenalty / budget)
overall         = Σ(category_score × weight) / Σ(점수를 이루는 영역의 weight)
caps            = overall 을 위에서 누른다. 상한이 점수를 올리는 일은 없다.
gates           = 점수 옆에 표시만 한다. 숫자를 바꾸지 않는다.
```

| 심각도 | 계수 | | 상태 | 배수 |
|---|---:|---|---|---:|
| BLOCKER | 1.00 | | FAIL | 1.0 |
| CRITICAL | 0.60 | | WARNING | 0.5 |
| MAJOR | 0.30 | | PASS | 0.0 |
| MINOR | 0.10 | | UNKNOWN | (아래) |
| INFO | 0.00 | | NOT_APPLICABLE | 분모에서 제외 |

**숫자는 모두 `packages/scoring-specs` 의 발행 명세에만 있다.** 검사기 코드에는 하나도
없고, 그것을 지키는 검사가 있다 — 명세의 모든 숫자를 바꿔 넣고 관측이 하나도 안 움직이는지
확인한다(`test_collector_contract.py`).

### 1.2 절대 평가 — 이 판의 핵심 변경

`UNKNOWN` 은 **심각도 계수를 예산에 더한 채 그만큼 벌점을 받는다.** 못 잰 이유가 우리
쪽이든 대상 쪽이든 얻지 못한 점수는 얻지 못한 것이다.

예외는 `NOT_APPLICABLE` 하나뿐이다 — "이 대상에는 그 항목이 존재하지 않는다" 는 뜻이지
"없다" 가 아니다. 페이지네이션이 없는 사이트에 페이지네이션 검사를 0점으로 매기면 없는
결함을 지어내는 것이다.

한 번도 재지 못한 대상은 0점이 아니라 **측정 불가**다. 사이트를 가져오지 못한 것과
사이트가 나쁜 것은 다른 사실이다.

### 1.3 분모 고정

**점수를 이루는 영역만으로 100이어야 하고, 그 분모는 고객 상태에 따라 움직이지 않는다.**

이 원칙을 세 번에 걸쳐 배웠다. 세 번 다 같은 실수였다 — 분모가 움직였다.

| 판 | 무엇이 분모를 흔들었나 | 결과 |
|---|---|---|
| 1.1.0 이전 | `UNKNOWN` 이 예산에서 빠짐 | 20점어치를 못 잰 사이트가 **91.8점** (실제 59.1) |
| 1.3.0 이전 | 연동 영역이 통째로 해당 없음 | **연결할수록 불리** — 안 하는 편이 유리 |
| 1.4.0 이전 | 구조화 데이터 없으면 12.5점 면제 | **만들수록 불리** — 안 만드는 편이 유리 |

셋 다 진단 도구가 만들면 안 되는 유인이다. 해법은 같다 — 잴 수 없는 영역은 **애초에
점수의 일부가 아니라고 명세에 적고**(`contributes_to_score: false`), 나머지로 100을 만든다.

### 1.4 연동 게이트

검사마다 `availability` 를 둔다.

| 값 | 뜻 | 배점 |
|---|---|---|
| `SELF_SERVICE` | VEO 가 스스로 잰다 | 포함 — 못 쟀다면 **우리가** 안 한 것 |
| `CUSTOMER_GRANTED` | 사이트 소유자가 권한을 줘야 | 제외 + 무엇을 연결하면 되는지 표시 |
| `PAID_PROVIDER` | 유료 데이터원 필요 | 제외 + 위와 같음 |

뒤의 둘은 연동 전까지 `NOT_APPLICABLE` 이 되고 **"이 진단의 배점 밖"** 구역에 사유와
함께 남는다. 아직 요청하지도 않은 권한 때문에 고객 점수가 낮아지면 안 된다.

때문이다 — 그 구간에 있다는 것은 첫 갱신 시도가 이미 실패했다는 신호다. 남은 기간은
`now` 가 아니라 **수집 시각** 기준으로 잰다. 며칠 전 자료를 다시 채점할 때 값이 달라지면
안 된다.

## 3. 화면

### 3.1 항목별 판정 (`ScanReport` · `CheckExplorer`)

경쟁 도구(NXT)는 판정 옆에 무엇을 보고 그렇게 판정했는지 보여주는데, 우리는 상태와
`seo.onpage.heading_hierarchy` 같은 식별자만 찍었다. 직원이 그 줄을 보고 할 수 있는
일이 없었다.

정작 그 근거는 수집기가 이미 만들고 있었다 — `observed_value` 에 페이지별 관측값이
담기는데 API 스키마에 자리가 없어 경계에서 버려졌다. **새로 재지 않고 버리지 않게** 했다.

지금 구조:

```
SEO 기술 준비도          점수·등급·구간표·상한
100점까지 — 개선 할 일    상위 3개 크게, 나머지 접기
영역별 점수              배점 비례 막대 (31.25점 영역이 12.5점 영역보다 길다)
항목별 판정              [전체 44][실패 13][주의 10][측정불가 6][통과 10]
  └ 5개 테마로 그룹핑
     └ 각 항목: [상태칩] 제목 ....... 심각도   ← 왼쪽 4px 색 띠
        펼치면 → 이렇게 판정한 근거 / 어떻게 고치나
측정하지 못한 항목
이 진단의 배점 밖         연동 필요 10개
근거와 출처              명세 버전·체크섬·근거 건수
```

`details`/`summary` 를 쓴다 — 자바스크립트 없이 열리고, 키보드로 다룰 수 있고, 브라우저의
페이지 내 검색이 **닫힌 내용까지** 찾아 준다. 직접 만든 토글은 셋 다 잃는다.

### 3.2 팀원 관리 (`/console/team`)

엔진에는 이미 전부 있었다 — 목록·초대·재발송·역할 변경·계정 비활성. **없던 것은 화면
하나**였다.

정한 것들:
- **초대 메일을 보내지 않는다.** 엔진이 1회용 링크를 돌려주고 관리자가 직접 전달한다.
- **링크를 자동으로 지우지 않는다.** 한 번 닫으면 다시 볼 수 없다(토큰은 해시로만
  저장된다). 그때는 재발송뿐이라, 관리자가 직접 닫을 때까지 남긴다.
- **자기 자신은 손대지 못한다.** 관리자가 스스로를 내리면 조직에 관리자가 남지 않고,
  그때는 DB 를 직접 손대는 것 말고 방법이 없다.
- **계정 삭제 버튼이 없다.** 비활성으로 충분하고, 지우면 그 사람이 실행한 진단의
  "누가 측정했는가" 가 함께 사라진다.
- 역할 이름 아래에 그 역할이 할 수 있는 일을 적는다 — 이름만 보고는 고를 수 없다.

### 3.3 세션

접근 토큰 15분 · 갱신 토큰 14일. 갱신은 `proxy.ts` 에서 한다 — Next.js 는 서버
컴포넌트가 쿠키를 고치는 것을 막으므로, 응답을 만들기 전에 도는 그 자리가 쿠키를 얹을
수 있는 유일한 곳이다. 로그아웃은 **두 쿠키를 모두** 지운다(갱신 토큰을 남기면
로그아웃을 눌렀는데 다시 들어가진다).

## 5. 이번에 잡은 결함

내가 만든 것과 원래 있던 것을 섞지 않고 적는다.

### 채점

| 결함 | 어떻게 드러났나 |
|---|---|
| UNKNOWN 이 분모에서 빠져 91.8점 | 사용자 지적 |
| 연동 영역이 분모를 흔듦 | 사용자가 "배점 수정했나" 물음 |
| 구조화 데이터 없으면 12.5점 면제 | 20조합 불변식 점검 |
| `WebPage.name` 오탐 — 제대로 만든 사이트가 실패 | **실제 사이트 측정** |
| doctype 검사가 구조화 데이터 영역에 있었음 | 명세 검토 |

### 화면

| 결함 | 어떻게 드러났나 |
|---|---|
| 배점 밖 영역이 "측정 불가" 로 섞여 표시 | **렌더해서 봄** |
| 빈 관측값이 이름만 남은 줄로 그려짐 | **렌더해서 봄** |
| 막대가 `flex-grow` 라 항상 전체를 채움 | **픽셀을 잼** |
| 팀원 관리가 `/api` 를 빠뜨려 전부 404 | **배포 후 사용자가 봄** |
| 초대자가 자기 아이디를 모른 채 로그인 화면에 | 사용자 질문 |
| 세션 15분 — 갱신 토큰을 버리고 있었음 | 사용자 지적 |
| `middleware.ts` / `proxy.ts` 충돌로 빌드 실패 | **배포 후 사용자가 봄** |

**패턴이 보인다.** 테스트가 잡은 것보다 **실제로 그려 보고·재 보고·배포해 보고** 잡은
것이 많다. 특히 마지막 둘은 사용자가 발견했다 — 그래서 §7 의 조치를 넣었다.

  알리지만, 그 줄이 의도한 차단이 실제로 안 걸린 것까지 연결해 보지는 않는다.
- **수집 페이지가 적으면 측정 불가가 많다.** 한 장만 보면 내부 링크·중복 본문·클릭
  깊이를 판단할 수 없다. 위의 "사이트 전체 크롤" 이 해결한다.
- **성능은 PageSpeed·CrUX 연동이 없으면 4개 항목이 측정 불가다.** 우리 키로 재는
  항목이라 배점에 남고, 그만큼 점수가 내려간다 — 의도한 동작이다.

# 이어서 — 2026년 7월 30일 후반

사이트 전체 크롤, 병렬 수집, 그리고 그 과정에서 **실측이 잡은 결함 다섯**.

이 판의 성격은 앞 판과 다르다. 앞 판은 만든 것을 기록했고, 이 판은 **재 보니 틀려
있던 것**을 기록한다. 새로 만든 기능보다 실측이 드러낸 결함이 더 중요했다.

## 1. 사이트 전체 크롤

### 1.1 없던 것

콘솔 진단은 넘겨받은 주소만 가져왔다. 발견 로직이 없어서 직원이 주소를 하나하나
입력해야 했고, 그래서 실제로는 한두 장만 보게 됐다. 사이트를 봐야 판정되는 여덟
항목이 어떤 사이트를 재도 측정 불가였다 — 못 잰 항목은 분모에 남은 채 0점이므로
(ADR 0016), **우리가 수집을 안 만든 탓에 모든 고객의 점수가 내려가고 있었다.**

`seo/discovery.py` 를 새로 두고 세 경로로 찾는다.

| 경로 | 무엇 |
|---|---|
| `SEED` | 사람이 지정한 주소 |
| `SITEMAP` | 사이트가 스스로 선언한 목록. index 는 한 단계 따라간다 |
| `LINK` | 내부 링크. 넓이 우선 기본 3단계 |

발견을 수집과 나눈 이유는 **네트워크 없이 시험 가능해야** 하기 때문이다. 사이트맵
본문과 HTML 문자열만 주면 어떤 주소가 나오는지 결정된다.

**대상 robots.txt 를 지킨다.** SEO 엔진이 robots.txt 를 *평가*하는 것과 VEO 가 그것을
*지키는* 것은 다른 일이다. 진입 URL 과 사람이 지정한 주소만 예외 — 시킨 일이지 우리가
넓힌 범위가 아니다.

### 1.2 부분 실패

전에는 404 한 장이 진단 전체를 502 로 만들었다. **사이트가 클수록 진단이 실패할 확률이
올라가는** 구조였다. 이제 진입 페이지 실패만 치명적이고, 나머지는 사유와 함께 결과에
남는다. "몇 장을 보려 했고 몇 장을 봤는가" 가 곧 그 진단의 신뢰도다.

### 1.3 병렬

25장에 11.5초였다. 거의 전부 기다리는 시간이고 직렬이라 하나씩 기다렸다. 동시 4개로
**4.9초**. 이 숫자는 우리 속도가 아니라 **대상 서버가 한순간에 받는 부하**이므로
`console_crawl_concurrency` 로 따로 두었고, 한 시간 총량은
`console_target_host_limit_per_hour` 가 별도로 막는다.

결과 순서는 frontier 순서로 되돌린다. 먼저 끝난 순서로 두면 같은 자료로 두 번 진단해도
문서 순서가 달라지고, 그러면 "왜 이 점수가 나왔는가" 에 같은 답을 두 번 줄 수 없다.

## 2. 실측이 잡은 결함 다섯

**전부 테스트가 아니라 실제로 재 보다가 나왔다.** 앞 판의 결론("테스트가 잡은 것보다
그려 보고·재 보고·배포해 보고 잡은 것이 많다")이 다시 확인됐다.

| # | 결함 | 어떻게 드러났나 |
|---|---|---|
| 1 | 콘솔 진단이 사이트맵을 아예 안 읽음 | 코드를 읽다 발견 — 개발 스크립트는 읽는데 제품은 안 읽었다 |
| 2 | `<image:loc>` 을 페이지 주소로 셈 | **실사이트 측정** |
| 3 | 적게 수집하면 점수가 올라감 | **실사이트 측정** (점수가 내려가는 이유를 파다가) |
| 4 | 리다이렉트가 데려온 같은 페이지를 여러 장으로 셈 | **실사이트 측정** |
| 5 | 인용을 못 받는 모델의 "인용 0회" | **실제 API 호출** |

### 2.1 사이트맵 미연결

`router.py` 가 `sitemap_documents={}` 로 빈 값을 넘기고 있었다. 사이트맵 두 MAJOR
항목이 **어떤 사이트를 재도 항상** 측정 불가였다. 개발용 `scripts/diagnose.py` 는
제대로 읽었으므로 **스크립트로 잰 점수와 제품이 내는 점수가 달랐다** — 앞 판의
"실사이트 측정 완료" 는 스크립트로 한 것이었다.

### 2.2 이미지 사이트맵 오탐

`_local_name` 이 네임스페이스 접두어를 떼어 `image:loc` 을 `loc` 과 같게 만들었다.
`seokorea.org` 의 Jetpack 이미지 사이트맵에서 페이지 26 + 이미지 26 을 **52개 페이지로**
셌다. 이미지는 HTML 이 아니므로 sitemap URL 검사가 비정상으로 판정하고, **이미지
사이트맵을 제대로 갖춘 사이트가 그 때문에 감점됐다.** 이미지가 페이지보다 많은
사이트맵은 흔하므로 "sitemap 과반 비정상" 상한(55점)이 걸릴 수도 있었다.

### 2.3 분모가 움직인 네 번째 사례

같은 사이트를 같은 시각에 재도 수집량에 따라 점수가 달랐다.

| 대상 | 1장 | 25장 |
|---|---:|---:|
| veo.seokorea.org | 52.23 | 50.11 |
| www.seokorea.org | 71.69 | 68.07 |

다섯 검사가 "수집한 페이지 중에 대상이 없다" 를 `NOT_APPLICABLE` 로 처리했다. 사유
문구부터 모순이었다 — *"수집한 페이지가 하나뿐이어서 판단할 수 없습니다"* 는 `UNKNOWN`
의 정의다. **덜 재는 편이 유리했다.**

규칙을 하나로 줄였다. **`NOT_APPLICABLE` 은 대상에 대한 사실일 때만 쓴다. 표본에 대한
사실은 `UNKNOWN` 이다.** 판정은 `sample_is_the_whole_site` 한 곳에서만 한다. 자세한
것은 ADR 0016.

고친 뒤에는 방향이 뒤집혔다 — 1장 67.28 → 25장 67.99. **더 많이 볼수록 유리**하다.

### 2.4 같은 페이지를 여러 장으로

25번 가져온 것 중 **15번이 같은 페이지(`/`)** 였다. frontier 는 요청 주소로 중복을
걸렀고 최종 주소로는 걸르지 않았다. 채점기가 실제로 본 것은 11장인데 "25장을 봤다" 고
셌다. 최종 주소로 걸러 내니 같은 예산으로 **유효 페이지가 11 → 23장**이 됐다.

### 2.5 인용 정직성

키를 받아 OpenAI 어댑터를 **처음으로 실제 호출**했다. 어댑터는 실물과 맞았는데,
검색 모드이기만 하면 "제공자가 인용을 알려준다" 고 단정하고 있었다.

    gpt-5         url_citation 6개   ← 돌려준다
    gpt-4o        url_citation 2개   ← 돌려준다
    gpt-4.1       0개                ← 안 돌려준다
    gpt-4o-mini   0개                ← 안 돌려준다 (검색은 실행됨: 입력 토큰 23 → 8,174)

mini 로 재면 "찾아봤지만 인용이 없었다" 로 기록된다. 사실은 "이 모델은 인용을 알려주지
않는다" 다. 고객 화면에서는 **"AI 가 당신을 한 번도 인용하지 않습니다"** 가 된다 —
지어낸 값보다 나쁘다. 지어낸 줄도 모른다.

`gpt-4.1` 이 못 한다는 것은 **문서만 보고는 알 수 없었다.** 확인 절차는
`docs/operations/verifying-citation-support.md`.

## 3. 호스트 예산의 경쟁 상태

병렬화 **전에** 막아야 했다. `InMemoryRateLimiter.acquire` 는 검사한 뒤 청구한다. 그
사이에 다른 스레드가 끼면 둘 다 통과한다.

추측하지 않고 재현했다 — **32스레드·제한 10에서 14개**가 통과했다. 다만
`sys.setswitchinterval(1e-9)` 로 전환을 강제해야 나타났고, **강제하지 않은 200회는
조용히 전부 통과했다.** 통과한 것이 안전하다는 뜻이 아니었다.

깨지는 것은 VEO 가 남의 서버를 두드리는 것을 막는 유일한 통제다. 락을 넣은 뒤 같은
조건 400회에서 정확히 10개만 통과한다.

## 4. 인수인계 문서가 GEO 를 잘못 적어 두었다

앞 판 문서: *"GEO 관측 — 미착수. 제품 이름의 절반이 비어 있다"*

**사실이 아니었다.** 엔진은 약 7,300줄 규모로 이미 있었다 — 제공자 4종, 인용·언급·
경쟁사·동명이인 탐지, 위험 평가, 검수 대기열, 표본 설계, 실행기 612줄, 테스트 29개
파일. DB 모델·마이그레이션·권한도 전부.

없던 것은 **`router.py`·`schemas.py`·`service.py` 세 파일**이었다. 그래서 `src/` 안에서
`ObservationRunner` 를 부르는 코드가 하나도 없었고 완성된 엔진이 테스트에서만 돌았다.

이 판에서 절반을 연결했다 — 엔진 상태 조회와 프롬프트 집합. 관측 실행은 넣지 않았다:
답변 원문·브랜드 식별자·인용/언급 기록을 함께 남겨야 하고, 관측 실행은 immutable
기록이라 **반쯤 저장된 실행이 가장 나쁘다.**

### 관측 연결 2/2 에 필요한 것

1. `ObservationRunner` 조립 — registry + `RecordedAnswerStore` + `MentionDetector`.
   **`build_registry` 에 `price_table` 을 넘겨야 한다.** 지금은 안 넘겨서 비용이 늘
   `NO_PRICE_CONFIGURED` 다. 0원이 아니라 모른다는 뜻이고, §16 비용 관측과 job 의
   `estimated_cost`/`actual_cost` 가 여기 걸려 있다.
2. `RunReport` → DB. **`skipped` 와 `stopped_reason` 을 반드시 함께 저장한다** —
   없으면 부분 실행이 완전한 측정처럼 읽힌다.
3. 7.3 지표. SOV 계산은 `competitors/sov.py` 에 이미 있고 관측 데이터를 입력으로 받는다.
4. 반복 최소 3회 규칙이 runner 에 있다. `allow_below_floor` 를 API 에서 함부로 열지 말 것.
5. 실행 화면에서 **모델별 인용 지원 여부를 표시**해야 한다(2.5 참조).

## 5. 원래 빨간불이던 것

CI 는 `ruff check apps/api` 와 `mypy` 를 실제로 돌리는데, 브랜치에 이미 오류 9개가

## 7. 이 판에서 **일부러 안 한 것**

정직성 때문에 안 한 것들이다. 다음 사람이 "빠뜨렸나" 하고 채워 넣지 않도록 적어 둔다.

- **`CATEGORY_OR_HUB` 자동 분류.** 픽스처에서 `/guide/` 는 허브, `/deep/` 은 콘텐츠인데
  둘 다 1단계 경로다. 사람이 뜻으로 라벨한 것이라 주소 모양에서 나오지 않는다.
  지어내면 절반이 틀리고, 틀린 절반은 조용히 점수를 흔든다.
- **`INTENTIONAL_NOINDEX` 자동 분류.** 배점이 0 이라 분모에서 빠진다. 태그만 보고
  "의도된 것" 이라 하면 **실수로 걸린 noindex 를 우리가 숨겨 주는** 셈이 된다.
  `sitewide_noindex` 픽스처조차 이 값을 쓰지 않고, 검사가 찾아 상한을 건다.
- **확인하지 않은 모델을 인용 가능 목록에 넣기.** 문서에 지원한다고 적혀 있는 것과
  실제로 돌려주는 것은 다른 사실이었다.
