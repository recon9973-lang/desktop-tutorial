# 구글 Lighthouse 대조 — VEO 점수 알고리즘 v2 검토

**작성 2026-08-01. 근거는 전부 실측이다.**
대상 `https://chamsarang1075.com/` · 전략 MOBILE · Lighthouse 13.4.1 ·
PageSpeed Insights API `runPagespeed`, 카테고리 5종 전부 요청.
원본 응답은 이 문서를 쓰는 동안 보관했고, 아래 숫자는 모두 그 응답의
`categories[].auditRefs[].weight` 와 `audits[].score` 를 직접 읽은 것이다.

이 문서는 구글을 정답으로 삼지 않는다. 구글은 **같은 문제를 우리보다 훨씬 오래,
훨씬 큰 표본으로 풀어 온 조직**이고, 그들이 어디에 배점을 줬는지는 근거로 쓸
가치가 있다. 동시에 아래 §5 에서 보듯 구글의 채점에는 우리가 **따라 하면 안 되는**
결함이 있다.

---

## 1. 구글이 실제로 재는 것 — 158개 감사, 배점은 51개에만

| 카테고리 | 점수 | 감사 수 | **배점 있는 감사** | 배점 합 |
| --- | --- | --- | --- | --- |
| 성능 (performance) | 0.60 | 47 | **5** | 100 |
| 접근성 (accessibility) | 0.95 | 76 | 21 | 154 |
| 권장사항 (best-practices) | 0.81 | 21 | 12 | 26 |
| 검색엔진 최적화 (seo) | 0.92~1.00 | 11 | 10 | 13.04 |
| 에이전트형 브라우징 | 0.67~1.00 | 6 | 2~3 | 2~3 |

**감사 158개 중 점수에 영향을 주는 것은 51개다.** 나머지 107개는 화면에 길게
나열되지만 배점이 0 이다 — 진단 정보이지 채점 항목이 아니다.

이 사실 하나가 VEO 화면 설계에 그대로 걸린다. 우리는 "잰 것을 다 보여준다"를
원칙으로 삼았는데, 구글은 **잰 것을 다 보여주되 채점하는 것과 설명하는 것을
시각적으로 분리**한다. 항목마다 `점수에 포함되지 않음` 배지가 붙는다.

---

## 2. 성능 — 구글은 결과만 채점하고 원인은 채점하지 않는다

성능 감사 47개 중 배점이 있는 것은 정확히 5개다.

| 감사 | 배점 | 이 사이트 결과 |
| --- | --- | --- |
| total-blocking-time | **30** | 0.96 (140ms) |
| largest-contentful-paint | **25** | 0.00 (32.4초) |
| cumulative-layout-shift | **25** | 1.00 (0) |
| first-contentful-paint | 10 | 0.59 (2.7초) |
| speed-index | 10 | 0.00 (15.8초) |

배점 0 인 42개에는 `render-blocking-insight`, `unused-css-rules`,
`font-display-insight`, `image-delivery-insight`, `server-response-time`,
`network-dependency-tree-insight` 같은 것들이 들어 있다. **이 사이트에서 그중 11개가
"실패"로 표시되지만 점수는 1점도 깎이지 않는다.**

이것은 실수가 아니라 설계다. **원인을 고치면 결과가 좋아지고, 결과를 채점하면
원인은 자동으로 반영된다.** 원인과 결과를 둘 다 채점하면 같은 문제로 두 번 깎인다.

### VEO v2 와의 대조

v2 의 성능 계열 배점 (총 100점 중 6.8점):

| 검사 | v2 배점 | 성능 안에서의 비중 |
| --- | --- | --- |
| seo.perf.lcp_lab | 3.0 | 44% |
| seo.perf.inp_field | 2.0 | 29% |
| seo.perf.cls_lab | 0.5 | 7% |
| seo.perf.tbt_lab | 0.5 | 7% |
| seo.perf.text_compression | 0.5 | 7% |
| seo.perf.modern_image_format | 0.15 | 2% |
| seo.perf.resource_hints | 0.15 | 2% |

**셋을 나눠 봐야 한다.**

**(가) TBT 를 낮게 준 것은 옳다 — 그리고 구글보다 옳다.**
구글은 TBT 에 30점을 준다. 이유는 **실험실에서는 INP 를 잴 수 없기 때문**이다.
TBT 는 INP 의 대역이다. VEO 는 `inp_field` 로 실사용자 INP 를 직접 읽는다.
대역과 원본에 둘 다 배점을 주면 같은 성질을 두 번 세게 된다. v2 가 INP 2.0 /
TBT 0.5 로 둔 것은 이 중복을 피한 것이고, 근거가 있다.

**(나) 압축·이미지포맷·리소스힌트에 배점을 준 것은 구글 설계와 어긋난다.**
이 셋은 구글 기준으로 전부 **배점 0 인 원인 항목**이다. 압축이 안 되면 LCP 가
나빠지고, LCP 에서 이미 깎인다. v2 는 여기에 0.8점을 더 준다 — 같은 문제로 두 번
깎는 구조다. 다만 금액이 0.8점으로 작아서 실해는 크지 않다.
**판단:** 남겨도 되지만, 이유를 "결과가 아니라 원인이라 배점을 최소로 뒀다"로
명세에 적어야 한다. 지금은 이유가 적혀 있지 않다.

**(다) CLS 0.5 는 다시 봐야 한다. 이건 실제 문제다.**
구글은 CLS 에 **25점**을 준다 — LCP 와 **동등하다**. CLS 는 대역이 아니라
Core Web Vitals 본체이고, 구글이 검색 순위에 쓴다고 공표한 세 지표 중 하나다.
v2 는 이것을 "위생(S6)" 계층에 0.5점으로 뒀다. 성능 안에서 LCP 의 1/6 이다.

구글의 상대 비중과 나란히 놓으면 차이가 분명하다.

| | 구글 (성능 100 기준) | VEO v2 (성능 6.8 기준) |
| --- | --- | --- |
| LCP | 25% | 44% |
| CLS | **25%** | **7%** |
| TBT | 30% | 7% |
| INP | (실험실에서 측정 불가) | 29% |

LCP 를 높인 것과 TBT 를 낮춘 것은 설명이 되지만, **CLS 를 1/3.5 로 줄인 근거는
v2 문서에 없다.** 이 사이트는 CLS 가 0 이라 지금은 차이가 안 나지만, CLS 가 나쁜
사이트에서는 VEO 가 구글보다 크게 관대해진다. 레이아웃이 흔들리는 병원 홈페이지는
드물지 않다 — 광고 배너, 늦게 뜨는 이미지, 팝업이 전형적인 원인이다.

**조치 제안:** CLS 를 위생(S6)에서 경쟁력(S4)으로 올리고 배점을 **2.0** 으로 한다.
근거는 (1) 구글이 공표한 순위 신호 세 개 중 하나, (2) 구글 자신이 LCP 와 동등하게
채점, (3) 사용자가 오탭(誤tap)으로 이탈하는 직접 경로. LCP 3.0 보다는 낮게 두는
것은 유지한다 — LCP 는 콘텐츠가 보이기까지의 시간이라 이탈에 더 직접적이다.

## 3. 검색엔진 최적화 — 구글의 100점은 1페이지 10항목이다

구글 SEO 카테고리 전체 (11개, 배점 합 13.04):

| 감사 | 배점 | VEO 대응 검사 |
| --- | --- | --- |
| is-crawlable | **4.04** | seo.robots.meta_indexable (BLOCKER) |
| document-title | 1 | seo.onpage.title_present_and_unique (CRITICAL) |
| meta-description | 1 | seo.onpage.meta_description_quality (MINOR) |
| http-status-code | 1 | seo.http.status_ok (BLOCKER) |
| link-text | 1 | seo.onpage.descriptive_anchor_text (MINOR) |
| crawlable-anchors | 1 | — **없음** |
| robots-txt | 1 | seo.robots.txt_parses_cleanly (MINOR) |
| image-alt | 1 | seo.onpage.image_alt_coverage (MINOR) |
| hreflang | 1 | — **없음** |
| canonical | 1 | seo.canonical.declared_and_consistent (CRITICAL) |
| structured-data | 0 (수동) | seo.sd.* 5개 |

**구글이 `is-crawlable` 에만 다른 9개를 합친 것의 절반에 가까운 배점을 준 것**은
주목할 만하다. VEO v2 의 게이트 구조(색인이 막히면 곱셈으로 0점)와 같은 판단이며,
서로 독립적으로 도달한 결론이라는 점에서 v2 의 게이트 설계를 뒷받침한다.

### 우리에게 없는 두 가지

**`crawlable-anchors`** — `<a>` 태그가 실제로 크롤 가능한 링크인가.
`<a onclick="...">` 처럼 href 없이 자바스크립트로만 이동하는 링크는 크롤러가
따라갈 수 없다. VEO 의 `seo.crawl.no_orphan_key_pages` 는 "링크로 도달 가능한가"를
보지만, **도달 못 하는 원인이 이 패턴일 때 그 원인을 짚어 주지 못한다.**
국내 병원 홈페이지는 제작 도구가 만든 자바스크립트 메뉴가 흔해서 실제로 자주
걸릴 항목이다. **추가 권장.**

**`hreflang`** — 다국어 사이트에서만 의미가 있다. 국내 병원 대상 제품에서는
대부분 N/A 다. **추가하지 않는다.** (넣으면 N/A 처리 부담만 늘고, ADR 0002 에
따라 분모에서 빠져 점수에 영향도 없다.)

### VEO 에만 있는 것 — 47개

구글 SEO 카테고리에 대응이 없는 VEO 검사가 47개다. 그중 구조적으로 **1페이지
검사로는 불가능한 것들**:

- `seo.onpage.no_duplicate_metadata` — 사이트 내 title 중복. 2페이지 이상 필요
- `seo.content.no_duplicate_bodies` — 본문 근접 중복
- `seo.crawl.no_orphan_key_pages` — 고아 페이지
- `seo.sitemap.urls_valid` — 사이트맵 URL 유효성
- `seo.content.click_depth_reasonable` — 클릭 깊이
- `seo.canonical.declared_and_consistent` **(사이트 전체 기준)** — 구글은 이 사이트에
  통과를 줬다. 1페이지만 봤기 때문이다. VEO 는 100페이지를 훑어 40장에서 문제를
  찾았고 그중 한 페이지에는 canonical 이 2개였다.

**"구글은 100점인데 왜 깎느냐"에 대한 답은 여기 있다. 본 페이지 수가 다르다.**
구글이 틀린 것이 아니다 — 구글은 자기가 본 범위 안에서 맞다.

## 4. 우리가 안 보는 영역 — 접근성·권장사항

### 권장사항(best-practices) 12개 중 VEO 에 없는 것

| 감사 | 배점 | 판단 |
| --- | --- | --- |
| deprecations | 5 | 지원 중단 API 사용. **이 사이트 실패.** 검색 영향은 간접적 |
| third-party-cookies | 5 | 개인정보. SEO 영향 없음 |
| paste-preventing-inputs | 3 | 입력란 붙여넣기 차단. UX |
| errors-in-console | 1 | 헤드리스 필요 (작업 #8) |
| inspector-issues | 1 | 헤드리스 필요 |
| **charset** | 1 | **문자 인코딩 선언. 한글 사이트에서 깨지면 치명적** |
| image-aspect-ratio / image-size-responsive | 1+1 | 이미지 품질 |
| geolocation-on-start / notification-on-start | 1+1 | 권한 요청 UX |

**`charset` 만 추가를 권장한다.** 한글 페이지에서 `<meta charset>` 이 없으면
브라우저와 크롤러가 인코딩을 추측하고, 추측이 틀리면 본문 전체가 깨진 글자로
색인된다. 검사 비용은 거의 0 이고(HTML head 한 줄), 영향은 크다.
VEO 는 이미 `seo.html.doctype_standards_mode` 로 같은 성격의 위생 항목을 보고 있다.
**같은 계층(S6), 배점 0.3 제안.**

나머지는 SEO 제품의 범위 밖이다. 넣으면 "우리는 SEO 를 잰다"는 약속이 흐려진다.

### 접근성(accessibility) 21개

VEO 와 겹치는 것: `image-alt`, `html-has-lang`, `heading-order`, `meta-viewport`,
`document-title`. **이미 다 있다.**

없는 것 중 눈에 띄는 것은 `color-contrast` (배점 7, **이 사이트 실패**),
`button-name`, `link-name`, `target-size`, `landmark-one-main`.

**SEO 점수에는 넣지 않는다.** 접근성은 검색 순위 신호가 아니다. 다만 **§6 에서
보듯 GEO 쪽에서는 이야기가 다르다.**

## 5. 구글이 하는데 우리는 하면 안 되는 것 — 못 잰 것을 실패로 적는다

이번 측정에서 실제로 관측한 것:

```
robots-txt   score=0   "Fetch of robots.txt failed: Timed out fetching resource"
llms-txt     score=0   "Fetch of llms.txt failed: Timed out fetching resource"
```

**구글이 파일을 못 가져와서 0점을 줬다.** 그리고 그 0점은 화면에서
"robots.txt 가 크롤러를 막고 있다"와 **구분되지 않는다.** 같은 빨간 표시다.

같은 URL 을 다른 시각에 재면 두 항목 모두 통과한다. 즉 이 사이트의 SEO 점수는
1.00 과 0.92 사이를, 에이전트 점수는 1.00 과 0.67 사이를 오간다 —
**사이트가 변한 것이 하나도 없는데.**

이것이 VEO 의 ADR 0002 가 존재하는 이유다.

| | 뜻 | VEO 처리 | 구글 처리 |
| --- | --- | --- | --- |
| N/A | 해당 없음 | 분모에서 뺀다 | 분모에서 뺀다 (weight 0) |
| **UNKNOWN** | **못 쟀다** | **분모에 남기고 0점 + 이유를 적는다** | **실패와 동일** |
| FAIL | 실제 결함 | 분모에 남기고 0점 | 0점 |

N/A 처리는 구글도 같다. **UNKNOWN 을 구분하는 것이 VEO 의 차이다.**

주의할 점이 있다. VEO 도 UNKNOWN 을 0점으로 계산한다(ADR 0016). 숫자만 보면
구글과 같다. 다른 것은 **화면에 뭐라고 적히느냐**다. VEO 는 "측정하지 못했습니다 —
사유: …"로 적고 결함 목록에 넣지 않는다. 구글은 결함으로 적는다.
**이 차이를 잃으면 우리가 구글보다 나을 이유가 하나 줄어든다.**

**v2 알고리즘에 대한 함의:** 게이트(S1) 항목에서 UNKNOWN 을 곱수 1로 두기로 한
결정 — 즉 못 잰 것 때문에 사이트 전체를 0점으로 만들지 않는 것 — 은
이 사례로 정당화된다. 오늘 robots.txt 를 못 가져온 것이 그 사이트를 "색인 차단"
으로 만들었다면, 아무 문제 없는 병원 홈페이지가 0점을 받았을 것이다.

## 6. 에이전트형 브라우징 — 구글이 GEO 영역에 들어왔다

카테고리 설명(구글 원문): *"AI 에이전트가 탐색할 수 있는 고품질 웹사이트를
보장하고 WebMCP 통합의 정확성을 검증합니다. **이 카테고리는 아직 개발 중이며
변경될 수 있습니다.**"*

| 감사 | 배점 | 상태 |
| --- | --- | --- |
| agent-accessibility-tree | 1 | 통과 |
| cumulative-layout-shift | 1 | 통과 (성능에서 재사용) |
| llms-txt | 0 또는 1 | 실행마다 다름 |
| webmcp-form-coverage / registered-tools / schema-validity | 0 | 해당 없음 |

**실질 2항목이고, 그중 하나는 레이아웃 안정성(CLS)이다.** AI 에이전트와의
관련성이 얕은 지표를 절반으로 쓰고 있다. 구글 스스로 "개발 중"이라고 적었다.

### llms.txt 를 넣을 것인가

`weight` 가 실행마다 0 과 1 을 오간다. `notApplicable` 일 때 0, fetch 를 시도해
실패하면 1 이다. **즉 llms.txt 가 아예 없으면 감점이 없고, 있는데 못 읽으면
감점된다.** 실패 모드가 거꾸로다.

**판단: 넣되 INFO(감점 0).** 근거 —
(1) llmstxt.org 는 표준이 아니라 제안이고 채택률·효과 근거가 얇다.
(2) 표준 제정자에 가장 가까운 당사자인 구글이 정상 경로에서 배점 0 으로 둔다.
(3) ADR 0012 상 발행하면 되돌릴 수 없다.
VEO 의 `geo.access.training_bot_policy_declared` 가 이미 INFO 이고 성격이 같으므로,
새 검사보다 그 검사의 증거에 `llms_txt` 를 더하는 쪽을 먼저 검토한다.

### agent-accessibility-tree 는 다르다

접근성 트리는 20년 된 웹 표준이고, 구글이 여기에는 배점 1(전체의 절반)을 줬다.
AI 에이전트가 페이지 구조를 읽는 경로 그 자체다. **VEO GEO 의 '답변 추출성'
카테고리와 겹치는지 대조한 뒤, 겹치지 않으면 추가를 권장한다.**

§4 에서 "접근성은 SEO 점수에 넣지 않는다"고 했는데 여기서는 반대인 이유:
**SEO 는 검색엔진이 순위를 매기는 문제고, GEO 는 AI 가 페이지를 읽어 답을 만드는
문제다.** 접근성 트리는 후자에 직접 걸린다. 같은 항목이 한쪽에서는 무관하고
다른 쪽에서는 핵심일 수 있다.

## 7. v2 알고리즘에 반영할 것 — 요약

| # | 조치 | 근거 | 크기 |

유지되는지 확인한 뒤에 명세 1.7.0 으로 발행한다.

## 8. 화면 설계에 걸리는 것

구글은 158개를 다 보여주면서 **채점 항목과 설명 항목을 배지로 가른다**
(`점수에 포함되지 않음`). 성능 화면에서 실패로 표시된 11개 항목은 점수를 1점도
깎지 않는데, 배지가 없으면 사용자는 그 11개를 고치면 점수가 오를 것이라 믿는다.

VEO 도 같은 문제를 갖고 있다. 점수 밖 항목(보안 헤더 등)을 추가하기로 한 결정
(`80 + 1` 분리 표시)이 바로 이 문제의 우리 쪽 답이다. **구글의 배지 방식이
우리가 정한 분리 표시와 같은 결론**이라는 점에서, 그 결정은 근거가 하나 더 생겼다.
