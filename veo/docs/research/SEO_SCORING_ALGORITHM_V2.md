# SEO 점수 알고리즘 v2 — 설계와 검증

> 상태: **설계 확정, 미적용.** 현재 제품은 v1(명세 1.6.0)으로 돌고 있다.
> 적용은 새 명세 버전(1.7.0)을 발행하는 별도 작업이다. ADR 0012 에 따라 기존
> 버전은 고치지 않는다.

## 1. 왜 바꾸는가 — v1 의 결함 두 가지 (실측)

### 결함 A. 검사를 추가하면 점수가 올라간다

v1 공식은 영역 점수를 이렇게 낸다.

```
예산     = Σ 심각도계수  (그 영역에서 해당되는 검사 전부)
감점_i   = 심각도계수 × 상태배수 × 문제비율 × 신뢰도
영역점수 = 100 × (1 − Σ감점 / 예산)
```

**분모가 검사 개수에 따라 늘어난다.** 명세 버전만 바꿔 같은 결함을 채점하면:

| 명세 | 온페이지 검사 | 예산 | title 전면 실패 시 |
|---|---|---|---|
| 1.2.0 | 9개 | 1.80 | **66.7점** |
| 1.6.0 | 11개 | 2.20 | **72.7점** |

같은 사이트, 같은 결함인데 **검사를 2개 추가했더니 6점이 올랐다.**

이미 한 번 고친 결함(#14 "적게 수집하면 점수가 올라간다")의 거울상이다. 그때는
분모가 수집 페이지 수에 따라 움직였고, 이번엔 검사 개수에 따라 움직인다.

근본 원인: 원 설계 문서 `SEO_RECOMMENDED_SCORING_MODEL.md` v0.1 이 공식에
`category_budget` 을 쓰면서 **그 값을 정의하지 않았다.** 구현이 "계수 합"으로
채웠고, 그게 신축 분모가 됐다.

### 결함 B. 색인이 완전히 차단된 사이트가 74점을 받는다

덧셈 모델에서는 검사 배점만큼만 잃는다. 전면 noindex + robots 차단 + 5xx 인
사이트를 v2 초안(순수 덧셈)으로 채점하면 **74점**이 나왔다. 검색에 존재하지 않는
사이트가 "양호" 등급을 받는다.

v1 은 이걸 **상한 규칙**(`max_overall_score: 25`)으로 막는다. 상한은 올바르게
구현돼 있다. 다만 상한은 극단에서만 걸리는 사후 보정이고, 부분 차단(예: 30%
페이지가 noindex)은 잡지 못한다.

## 2. v1 설계 문서 자체의 문제

| 항목 | v0.1 문서 | 평가 |
|---|---|---|
| 카테고리 가중치 25/15/15/15/10/10/5/5 | 값만 있음 | **근거 없음** |
| 심각도 계수 1.0/0.6/0.3/0.1/0.0 | 값만 있음 | **근거 없음** |
| `category_budget` | **정의 없음** | 결함 A 의 원인 |
| 검사별 영향력 | 없음 (심각도 4단계뿐) | CRITICAL 8개가 전부 같은 무게 |
| 근거 인용 | 없음 | 객관성 검증 불가 |

숫자 자체는 업계 관행과 크게 다르지 않아 **틀렸다고 할 수는 없지만, 왜 그 값인지
설명할 수 없다.** 고객이 "왜 title 이 canonical 과 같은 무게냐"고 물으면 답이 없다.

## 3. v2 설계

### 3.1 배점의 근거 — 검색 파이프라인

검색엔진은 순서대로 동작한다.

```
발견 → 크롤 → 색인 → 해석 → 경쟁 → 클릭
```

**앞 단계가 막히면 뒤 단계는 통째로 무의미하다.** noindex 페이지에 완벽한 구조화
데이터를 넣어도 아무 일도 일어나지 않는다. 이건 의견이 아니라 동작 방식이고,
그래서 **객관적인 배점 근거**가 된다.

| 단계 | 실패하면 | 구조 |
|---|---|---|
| **S1 색인 차단** | 검색 결과에 **존재하지 않는다** | **곱셈 게이트** |
| **S2 대표 URL 혼란** | 어느 주소가 대표인지 엔진이 임의 결정 | 21.4점 |
| **S3 해석 불가** | 무엇에 대한 페이지인지 모름 → 노출 자체가 안 됨 | 28.6점 |
| **S4 경쟁력** | 노출은 되나 더 나은 페이지에 밀림 | 28.6점 |
| **S5 클릭·표현** | 순위는 나오나 덜 눌림 | 14.3점 |
| **S6 위생** | 검색 성과 영향이 확인되지 않음 | 7.1점 |
| | | **합 100** |

### 3.2 공식

```
도달률 = Π (1 − 차단검사 실패비율)        검색에 들어갈 수 있는 비율
품질   = 100 − Σ (배점 × 상태배수 × 범위 × 신뢰도)
점수   = 도달률 × 품질
```

**게이트끼리도 곱한다.** 페이지는 모든 관문을 통과해야 하기 때문이다 — robots 가
절반을 막고 상태코드가 20% 실패면 `(1−0.5)(1−0.2) = 0.4`.

상태배수: `실패 1.0 · 주의 0.5 · 통과 0 · 측정불가 1.0`

### 3.3 범위(breadth)를 오목하게 — 지수 0.7

```
범위계수 = 문제비율 ^ 0.7        (40% → 53%, 70% → 78%)
```

결함은 대개 **템플릿 단위**로 생긴다. 40%가 깨졌다면 40개의 개별 실수가 아니라
템플릿 하나의 문제이고, 나머지 60%도 같은 위험에 있다. 선형 비율은 이 구조를
반영하지 못한다.

### 3.4 못 잰 항목 — 게이트와 품질에서 다르게 처리한다

| | 처리 | 근거 |
|---|---|---|
| **게이트(S1)** | 곱하지 않음 (×1), '확인 불가' 표시 | 관측하지 않은 차단을 있다고 하면 **없는 결함을 지어내는 것**(0-A) |
| **품질(S2~S6)** | 배점 상실 | 재지 못한 항목이 분모에서 빠지면 "4개 중 1개 보고 100점"(ADR 0016) |

### 3.5 해당 없음은 같은 단계 안에서 재분배

단계 간 상대 중요도가 고객마다 달라지면 절대 평가가 성립하지 않는다(0-B).
그래서 재분배는 **단계 내부에서만** 한다. 합은 항상 100 이다.

## 4. 검증 — 11개 성질 전부 통과

| | 검증 내용 | 결과 |
|---|---|---|
| 경계 | 전부 통과 = 100점 | 100.0 |
| 경계 | 전부 실패 = 0점 | 0.0 |
| 차단 | 전면 차단 = 0점 | 0.0 (도달률 0) |
| 차단 | 절반 차단 = 절반 점수 | 50.0 (도달률 0.5) |
| 차단 | robots 전역 차단 하나로 0점 | 0.0 |
| **불변** | **검사를 빼도 점수 동일** | **91.42 = 91.42** |
| 단조 | 결함이 늘면 내린다 | 통과 |
| 단조 | 문제 페이지가 줄면 오른다 | 통과 |
| 단조 | 주의 < 실패 | 통과 |
| 비례 | 위생 전부 실패는 7점만 잃음 | 92.9 |
| 재분배 | 해당없음 있어도 만점 100 | 100.0 |

**결함 A·B 가 둘 다 해소됐다.**

## 6. ★ 검증 중 드러난 별개 문제 — 우리 공백이 고객 점수를 깎는다

**8.64점이 "우리가 못 재서" 사라진다.**

```
seo.perf.lcp_lab      측정 불가   ← PageSpeed API 키 없음
seo.perf.inp_field    측정 불가   ← PageSpeed API 키 없음
seo.perf.cls_lab      측정 불가   ← PageSpeed API 키 없음
seo.perf.tbt_lab      측정 불가   ← PageSpeed API 키 없음
seo.content.js_render_parity  확인 불가 ← 헤드리스 렌더러 없음
```

명세 1.3.0 의 변경 사유에 이미 이 원칙이 적혀 있다.

> "절대 평가에서 잴 수 없는 항목을 선언하면 그 배점은 분모에 남은 채 0점이 되어,
> **우리가 아직 만들지 않은 기능 때문에 모든 고객의 점수가 내려간다.**"

그래서 그때 인증서 검사를 **넣지 않았다.** 그런데 성능 4항목은 같은 상태로 선언돼
있다. **자기 원칙을 한 곳에서만 지켰다.**

선택지는 둘뿐이다.

1. **PageSpeed API 키를 발급받아 실제로 잰다** (기존 과제 #30)
2. 잴 수 있을 때까지 **명세에서 뺀다**

지금처럼 두는 것은 안 된다 — 고객이 우리 공백의 대가를 치른다(0-J 위반).

## 7. 적용 시 할 일

1. 명세 **1.7.0** 발행 — 이 배점표를 데이터로 옮긴다. 코드는 안 고친다(ADR 0001)
2. `evaluator.py` 에 게이트 곱셈 지원 추가 — v1 명세는 게이트 없이 그대로 동작해야 함
3. 골든 픽스처로 새 점수 고정(0-H)
4. 성능 4항목 결정 (§6)
5. 점수 구간 재정의 — v0.1 의 90/75/50/25 는 v1 분포 기준이다. v2 는 같은 사이트가
   8.6점 낮게 나오므로 구간도 다시 잡아야 한다

## 부록. 배점표 전문

프로토타입: `scratchpad/algo_v2.py` (`ALLOCATION` 딕셔너리)
각 검사에 `(단계, 배점, 근거 한 줄)` 이 붙어 있다. 예:

```python
"seo.onpage.title_present_and_unique": ("S3_MEANING", 6, "주제를 알리는 1순위 신호. 대체 불가"),
"seo.sd.naver_supported_type":         ("S5_CLICK",   2, "네이버·카카오 공유 미리보기. 국내 병원 핵심 채널"),
"seo.html.doctype_standards_mode":     ("S6_HYGIENE", 0.05, "렌더링 모드"),
```

배점을 바꾸려면 **같은 단계 안에서 다른 검사의 배점을 가져와야 한다.** 합이 고정돼
있으므로 "슬쩍 하나 더" 가 불가능하고, 모든 변경이 명시적 결정이 된다.
