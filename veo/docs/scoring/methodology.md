# VEO 점수 방법론

**방법론:** VEO-LAB · **구현:** VENOM

화면에 보이는 숫자가 어떻게 나오는지를 끝까지 설명한다. **이 주제의 기준 문서는 여기
하나다** — 점수 산식, PageSpeed 연결, 성능이 배점에 들어가는 경로는 다른 문서에서
다시 설명하지 않고 이 문서를 가리킨다. 두 곳에 적으면 반드시 갈라지고, 갈라지면 어느
쪽이 맞는지 아무도 모른다(0-D).

배점 숫자 자체는 문서가 아니라 **데이터**에 있다: `packages/scoring-specs/specs/**`.
아래 표는 그 데이터를 읽는 규칙과, 2026-08-01 기준 발행본(SEO `1.8.0`)의 값이다.
값이 의심되면 문서가 아니라 명세 파일을 봐라.

---

## 1. 무엇을 재는 점수인가

| 지표 | 의미 | 아닌 것 |
|---|---|---|
| SEO 기술 준비도 | 검색엔진이 발견·크롤링·해석·제공할 수 있는 상태인가 | 검색 순위 예측 |
| GEO 준비도 | AI 답변 엔진이 접근·추출·검증할 수 있는 구조인가 | 실제 AI 노출 여부 |
| AI 가시성 | 실제 프롬프트 표본에서 언급·인용됐는가 | 구조 품질 |
| 네이버 키워드 수요 | 공식 API가 보고한 검색량과 경쟁 지표 | VEO의 추정 |
| 기회 점수 | 위 값을 VEO 산식으로 조합한 우선순위 제안 | 공식 데이터 |

이들은 **절대 하나의 총점으로 합치지 않는다.**

## 2. 계산 규칙 (SEO 1.8.0)

### 2.1 검색 여정 여섯 단계

영역을 "무엇을 재는가"가 아니라 **"막히는 순서"**로 묶는다. 앞이 막히면 뒤는 무의미
하므로 앞 단계일수록 손실이 크다.

| 단계 | 뜻 | 원배점 | 가중치 | 검사 | 성격 |
|---|---|---:|---:|---:|---|
| `s1_blocked` | 색인 차단 | 30 | — | 4 | **관문. 곱한다** |
| `s2_identity` | 대표 URL 혼란 | 15 | 21.4 | 4 | |
| `s3_meaning` | 해석 불가 | 20 | 28.6 | 8 | |
| `s4_compete` | 경쟁력 | 20 | 28.6 | 12 | |
| `s5_click` | 클릭·표현 | 10 | 14.3 | 7 | |
| `s6_hygiene` | 위생 | 5 | 7.1 | 14 | |

**관문은 가중 평균에 들어가지 않는다.** 곱해지기 때문이다. 그래서 나머지 다섯의
가중치 합이 정확히 **100.0** 이다(21.4+28.6+28.6+14.3+7.1).

연동이 있어야 잴 수 있는 세 영역은 **점수 밖**이다 — `search_engine_integration`(4),
`observability_outcomes`(3), `offpage_entity`(3). 판정과 보고는 하되 분모에 넣지
않는다. 고객이 서치콘솔을 연결하든 안 하든 **100점의 뜻이 같아야** 하기 때문이다.

### 2.2 검사 하나

```
배점_i    = 명세가 그 검사에 준 points × (단계 고정분모 / 살아 있는 배점 합)
범위_i    = coverage_ratio ^ 0.7          ← breadth_exponent
감점_i    = 배점_i × 상태배수 × 범위_i × 신뢰도_i
```

- **상태배수**: FAIL `1.0` · WARNING `0.5` · PASS `0.0`
- **신뢰도**: 직접 관측 1.0, 공식 API 0.9, 휴리스틱 0.5–0.8, 외부 추정 0.4

**고정 분모가 이 판의 핵심이다.** 예전에는 분모가 "채점된 검사들의 심각도 계수 합"
이라 **검사를 더할 때마다 자랐고**, 같은 사이트·같은 결함인데 온페이지 검사 두 개를
추가하자 66.7 이 72.7 로 올랐다. 이제 단계마다 분모가 상수이고 검사마다 배점이
명시돼 있다. 검사를 추가하려면 **형제에서 덜어내야** 하고, 무엇을 덜어낼지가 근거를
대야 하는 판단으로 드러난다.

**범위 지수 0.7 은 선형이 아니다.** 100장 중 40장의 title 이 깨졌다면 그것은 40개의
개별 실수가 아니라 **템플릿 하나의 문제**이고 나머지 60장도 같은 위험 위에 있다.
40% 를 40% 로 세면 "절반 이상 멀쩡하다"는 그림이 되는데, 고쳐야 할 것은 페이지 40개가
아니라 템플릿 하나다. 0.7 지수가 40% 를 53% 로 올린다.

### 2.3 못 잰 것 — 방향이 반대인 두 규칙

**이 절이 이 문서에서 가장 자주 오해되는 곳이다.**

| | 분모 | 점수 | 근거 |
|---|---|---|---|
| **N/A** (이 사이트엔 해당 항목이 없다) | **뺀다** | — | ADR 0002 |
| **UNKNOWN** — 품질 항목 | **남긴다** | **0점** | ADR 0016 |
| **UNKNOWN** — 관문 항목 | — | **곱하지 않는다** | 0-A |

품질과 관문에서 방향이 반대인 것이 **설계의 핵심**이다.

- 품질은 *"없다고 단정하면 만점을 주는"* 자리다 → 못 잰 것은 배점을 잃는다.
- 관문은 *"있다고 단정하면 사이트를 죽이는"* 자리다 → 못 잰 것은 곱하지 않는다.

관측하지 않은 차단을 있다고 하면 **없는 결함을 지어내는 것**이고, 우리 쪽 네트워크
사정으로 멀쩡한 병원 홈페이지가 0점이 된다. 대신 확인하지 못한 관문의 **이름**을
함께 돌려주어 화면이 "색인 가능 여부를 확인하지 못했다"고 말하게 한다.

> **구글은 여기서 틀린다.** 2026-08-01 실측에서 Lighthouse 는 robots.txt fetch
> 타임아웃을 0점 실패로 기록했고, 화면에서 "크롤러를 막고 있음"과 구분되지 않았다.
> 같은 사이트가 잴 때마다 SEO 1.00 과 0.92 를 오갔다. **이것이 VEO 와 구글의 진짜
> 차이이고, 잃으면 안 된다.**

### 2.4 단계 점수

```
단계분모  = Σ 배점 (채점된 것 + 절대평가에서 UNKNOWN 인 것)
단계점수  = 100 × max(0, 1 − Σ감점 / 단계분모)
```

- 적용 가능한 검사가 하나도 없으면 단계 상태는 `NOT_APPLICABLE`.
- 적용 가능하지만 전부 UNKNOWN 이면 `UNKNOWN`.
- **한 번도 재지 못했으면 0점이 아니라 측정 불가다.** 사이트를 못 가져온 것과 사이트가
  나쁜 것은 다른 사실이고, 0점으로 보고하면 없는 실패를 지어내게 된다.

### 2.5 관문 — 빼지 않고 곱한다

```
도달률 = Π over 관문 검사 ( 1 − 상태배수 × coverage )
```

가산 방식에서는 **색인이 전면 차단된 사이트가 74점**을 받았다. 검색에 존재하지 않는
사이트가 "양호" 등급을 받은 것이다 — 차단 검사들의 배점만큼만 잃기 때문이다.
실제로는 noindex 페이지의 완벽한 구조화 데이터는 아무 일도 하지 않는다.

관문끼리도 곱한다. 페이지는 **모든** 관문을 통과해야 한다 — robots 가 절반을 막고
상태 코드가 20% 실패면 `(1−0.5)(1−0.2) = 0.4`.

### 2.6 종합과 상한

```
종합 = 도달률 × Σ(단계점수 × 가중치) / Σ(채점 가능 가중치)
       그 다음 상한 적용
```

**순서가 중요하다.** 관문을 먼저 곱하고 상한을 건다. 뒤바뀌면 상한이 이미 0 에 가까운
점수를 다시 깎는 시늉만 하고, 어떤 상한이 실제로 걸렸는지 기록이 뒤엉킨다.

| 상한 조건 | 최대 |
|---|---:|
| 사이트 전체 색인 차단 | 25 |
| 주요 템플릿 5xx·렌더 불가 | 35 |
| 대량 외부 canonical | 40 |
| sitemap 과반 비정상 | 55 |
| HTTPS·모바일 중대 실패 | 60 |

상한은 점수를 **올리지 않는다.** 적용 전 점수(`score_before_caps`)와 적용 후를 모두
보존하고 사유·해제 조건을 함께 담는다.

### 2.7 게이트(라벨)는 점수를 바꾸지 않는다

`SpecCategory.is_gate`(위 2.5, 산술)와 `SpecGate`(라벨)는 **다른 것이다.** 후자는
점수 옆에 표시되는 상태일 뿐 숫자를 건드리지 않는다. GEO 에서 4xx/5xx·인증 필요·
noindex·검색용 AI 크롤러 차단이 `노출 차단` 라벨을 만든다. 학습용 크롤러 차단은
사업 선택이므로 감점하지 않고 정보로만 표시한다.

### 2.8 등급 구간

| 등급 | 점수 |
|---|---:|
| 준비 완료 | 90+ |
| 양호 | 75+ |
| 주의 | 50+ |
| 취약 | 25+ |
| 차단 | 0+ |

**절대 평가이므로 구간을 점수 분포에 맞춰 옮기지 않는다.** 옮기는 순간 절대 평가가
아니게 된다.

### 2.9 측정 범위 — 사이트 점수와 페이지 점수

> **이 절은 VEO 의 가장 큰 차별점이자, 가장 쉽게 무너지는 자리다.**

명세는 검사마다 범위를 선언한다: `scope: URL` 또는 `scope: SITE`.

| 범위 | 뜻 | 배점 | 검사 |
|---|---|---:|---:|
| `URL` | 한 장만 봐도 잴 수 있다 | **79.9** | 32 |
| `SITE` | 여러 장을 봐야 잴 수 있다 | **20.1** | 27 |

한 장으로는 **원리적으로** 잴 수 없는 것들:

```
s2_identity   본문 중복 · 메타데이터 중복        ← 다른 페이지와 비교해야 안다
s3_meaning    빈약한 신호
s4_compete    고아 페이지 · 클릭 깊이 · 내부링크 밀도 · HTTPS · 인증서
s5_click      구조화 데이터 선언 · 사이트맵 발견 가능성
s6_hygiene    robots.txt · 사이트맵 URL 유효성 · 깨진 내부링크 · 파비콘 · 빵부스러기
```

#### 왜 랜딩페이지 한 장만 재면 점수가 올라가는가

한 장만 재면 SITE 검사 27개를 잴 수 없다. **그것을 "해당 없음"으로 접는 순간 덜 재는
편이 유리해진다** — 해당 없음은 분모에서 빠지기 때문이다(ADR 0002).

VEO 수집기에 실제로 그렇게 되어 있었고, 실측으로 잡혔다:

```
1장을 재면   52.23점
25장을 재면  50.11점    ← 더 많이 잴수록 점수가 내려갔다
```

**1.8.0 에서는 경로가 하나 더 있다.** 고정 분모(2.2) 때문에 해당 없음의 배점은 분모를
줄이는 대신 **형제 검사로 재분배**된다. 분모는 100 그대로인데 결함은 사라진다:

```
메타데이터가 중복된 사이트
  전체 크롤:  97.15
  한 장만:   100.0     ← 만점. 결함이 없어서가 아니라 볼 수 없어서
```

숫자는 "결함이 없다"와 "그 결함을 볼 수 없었다"를 구분하지 않는다. **그 구분을 잃는
것이 0-A 위반의 실체다.**

실측(참사랑한의원, 2026-08-01):

```
canonical    타사: 통과   ← 홈페이지 1장만 봄. 홈페이지엔 실제로 정상 있음
             VEO:  실패   ← 100장 중 40장에 문제
```

**타사가 틀린 것이 아니라 본 페이지 수가 다르다.** 영업에서도 이 표현을 그대로 쓴다.

#### 해결 — 표본이 전체인지 묻는 질문 하나 (구현됨)

`veo/collect/sample.py` 가 이 규칙만 담당한다. **SEO·GEO 수집기가 같은 함수를 쓴다** —
예전에 규칙이 `seo/collectors/base.py` 안에 있어서 GEO 수집기 두 곳이 같은 실수를
그대로 갖고 있었다(0-D).

```
표본이 사이트 전체인가?
  아니다  → 측정 불가(UNKNOWN).  분모에 남고 0점.  덜 재서 이득 볼 수 없다.
  맞다    → 해당 없음(N/A).      분모에서 빠진다.
```

**"전체"라고 말하려면 두 가지가 모두 필요하다.**

1. 크롤이 상한·예산이 아니라 **더 찾을 것이 없어서** 멈췄다.
2. 페이지를 둘 이상 가져왔거나, **sitemap 이 "페이지가 하나"라고 선언**해 준다.

2번이 없으면 안 되는 이유: 메뉴를 자바스크립트로만 그리는 사이트는 원본 HTML 에 링크가
없어 크롤이 "더 볼 것이 없다"고 판단하지만 실제로는 페이지가 많다. 그때 해당 없음으로
접으면 **링크를 숨긴 사이트가 유리해진다.**

| 상황 | 판정 |
|---|---|
| 공개 무료 진단 · 1장만 봄 | **측정 불가** |
| 링크를 못 찾아 1장 (JS 메뉴 의심) | **측정 불가** |
| 진짜 1장짜리 사이트 (sitemap 이 확인해 줌) | 해당 없음 |
| 사이트 전체 크롤 · 여러 장 | 해당 없음 |

측정 불가 문구에는 **무엇을 하면 판정되는지**를 함께 적는다. "측정 불가"만 띄우면
고장으로 읽힌다(0-J).

#### 1.9.0 — 측정 범위가 명세로 올라갔다 (2026-08-02)

지금까지 크롤 상한은 서버 설정에만 있었다. "몇 장을 봤는가"는 점수의 분모이고,
분모가 무엇이었는지는 점수의 일부다 — 그래서 명세가 선언한다(`measurement_scope`):

```
max_pages: 200        한 진단이 가져오는 페이지 상한
max_depth: 4          시드에서 몇 번 이동까지
template_group_sample: 12   상한 초과가 예상될 때만, 게시판형 그룹당 표본
truncated_absence: UNKNOWN  잘린 크롤에서 부재 주장은 측정 불가
```

같은 값이 명세와 서버 설정 두 곳에 있으므로 시험이 둘을 묶는다
(`tests/scoring/test_not_sampled.py::test_the_declared_scope_matches_the_server_settings`).

같은 판이 **NOT_SAMPLED** 를 신설했다 — 명세의 표본 정책이 재지 않기로 한 대상
(성능 7개 검사, `sampling.*.check_ids`)의 페이지 판정. 분모·측정 범위 모두에서
빠지고 "표본 밖 — 요청 시 측정"으로 표기된다. 우리 정책으로 안 잰 것이 그 페이지의
감점이 되면 못 하는 이유를 고객 탓으로 돌리는 것이다(0-J). 절대평가의 예외이므로
경계를 평가기가 지킨다: 선언된 7개 밖의 검사에 붙이면 오류다. 사이트 점수에는 이
상태가 등장하지 않는다 — **1.9.0 은 숫자를 하나도 바꾸지 않았다.**

그리고 전 영역 해당 없음 모서리를 재정규화로 통일했다(연구 프로토타입 §6 모순 해소
— 실코드 평가기는 처음부터 재정규화였으므로 발행 점수는 그대로다).

#### 방법 — 두 점수를 따로 낸다. 합치지 않는다

서로 다른 질문에 답하기 때문이다.

| | **사이트 점수** | **페이지 점수** |
|---|---|---|
| 질문 | 이 홈페이지가 검색에 준비됐나 | 이 페이지를 고치면 뭐가 좋아지나 |
| 검사 | 전체 (URL + SITE) | 그 페이지의 **URL 범위만** |
| 용도 | **대표 숫자.** 리포트에 나가는 것 | 고칠 대상 특정 |

- **전체 크롤은 그대로 유지한다** — 사이트 점수의 근거다.
- **페이지 점수는 이미 수집한 자료로 계산한다.** 재크롤이 필요 없다. 재크롤은
  *고친 뒤 재검증*할 때만 의미가 있다.
- **페이지별 측정 상태를 저장해야 한다.** 지금 `scan_runs` 에는 사이트 단위만 남아
  재로그인하면 페이지별로 이어볼 수 없다. (미구현 — HANDOFF §4)

> **절대 하면 안 되는 것: 페이지 점수를 사이트 점수처럼 보이게 그리는 것.**
> 두 숫자는 분모가 다르므로 나란히 놓고 비교할 수 없다. 섞는 순간 우리가 타사에서
> 잡아낸 바로 그 결함이 된다.

## 3. PageSpeed 연결 — 성능은 어떻게 재고 배점에 어떻게 들어가는가

> 이 절이 "페이지스피드 연결 / API / 배점" 질문의 **유일한 답이다.** 어댑터 세부는
> `apps/api/src/veo/providers/google/pagespeed.py` 의 모듈 문서에 있다.

### 3.1 한 번 부르면 성격이 다른 두 가지가 온다

`runPagespeed` 응답 하나에 둘이 함께 온다. **절대 섞지 않는다.**

| | `lighthouseResult` | `loadingExperience` |
|---|---|---|
| 무엇 | **실험실** — 구글이 정한 회선으로 크롬을 띄워 잰 시뮬레이션 | **실사용자** — 크롬 사용자에게서 28일간 모은 값(CrUX) |
| 답하는 질문 | "이런 회선의 방문자라면 어떨까" | "방문자가 실제로 무엇을 겪었나" |
| 표본 문제 | **있다** (아래 3.3) | **없다** — 사이트 전체 값이 함께 온다 |

VEO 는 둘을 다른 타입·다른 `DataSource`·다른 검사 id 로 둔다.

**CrUX 단독 API 키는 켤 필요가 없다.** 실사용자 값은 PageSpeed 응답에 함께 온다.

**범위를 섞지 않는다.** 사이트 전체 값은 방문 많은 페이지가 지배하므로, 특정 URL 에
붙이면 그 URL 이 겪지도 않은 트래픽으로 그 페이지를 칭찬하게 된다.

### 3.2 어느 검사가 여기서 나오는가

| 검사 | 단계 | 배점 | 출처 |
|---|---|---:|---|
| `seo.perf.lcp_lab` | 경쟁력 | 3 | 실험실 |
| `seo.perf.cls_lab` | 경쟁력 | 2 | 실험실 |
| `seo.perf.inp_field` | 경쟁력 | 2 | **실사용자** |
| `seo.perf.tbt_lab` | 위생 | 0.5 | 실험실 |
| `seo.perf.text_compression` | 위생 | 0.5 | 실험실 |
| `seo.perf.modern_image_format` | 위생 | 0.15 | 실험실 |
| `seo.perf.resource_hints` | 위생 | 0.15 | 실험실 |

**CLS 가 위생이 아니라 경쟁력에 있는 이유**: 구글은 CLS 에 LCP 와 동등한 배점을 준다.
CLS 는 다른 지표의 대역이 아니라 Core Web Vitals 본체이고 구글이 순위에 쓴다고 공표한
셋 중 하나다. 위생에 두면 광고 배너와 늦게 뜨는 이미지로 버튼이 밀려나는 홈페이지가
그대로 통과한다.

**반대로 TBT 는 위생에 남겼다**: 구글이 TBT 에 큰 배점을 주는 것은 실험실에서 INP 를
못 재서 쓰는 **대역**이기 때문이고, VEO 는 INP 를 실사용자 값으로 직접 읽는다.
둘 다 채점하면 같은 성질을 두 번 센다.

### 3.3 표본 정책 — 왜 다 재지 않는가

실험실 측정은 **한 장에 16~60초**다(2026-08-01 실측: 16.0/24.1/28.3/59.8초).
100장을 다 재면 한 시간이 넘어 진단이 끝나지 않는다.

```
sampling.perf_lab.max_urls             5      중요도 상위 몇 장
sampling.perf_lab.min_measured_ratio   0.6    계획한 표본 중 최소 이만큼
sampling.perf_field.prefer_origin_scope true  사이트 전체 값 우선
```

**문턱을 못 넘으면 그 검사는 측정 불가이고 배점을 잃는다 — 덜 재서 이득 볼 수 없다.**

이 문턱이 없으면 **너무 느려서 로드에 실패한 페이지가 분모에서 빠져 사이트가 더 빨라
보인다.** 실제로 Lighthouse 가 `FAILED_DOCUMENT_REQUEST` 로 페이지를 못 여는 사례가
나왔고, 못 여는 이유는 대개 느려서다 — **편향이 우리에게 유리한 쪽으로 걸린다.**

표본을 고르는 함수는 `lab_sample` **하나뿐**이다. 재는 쪽과 채점하는 쪽이 각자 고르면
"잰 페이지"와 "재려던 페이지"가 어긋나고, 그 어긋남은 조용히 점수를 올린다.

방문자가 적어 구글이 실사용자 값을 공개하지 않는 사이트에서는 값이 비어 있다.
그것은 **해당 없음이지 느리다는 뜻이 아니다.**

### 3.4 한도 — 세는 것은 돈이 아니라 횟수다

PageSpeed 는 하루 **25,000회** 무료다. 돈은 안 든다. `cost_krw = 0` 은 **정말 0원**
이라는 뜻이며, 값을 모르는 제공자는 `None` 으로 둔다 — 0 과 None 을 섞으면 "공짜라서
0"과 "몰라서 0"이 같은 자리에 앉는다.

**진짜 위험은 하루가 사라지는 것이다.** 넘기면 그날의 모든 고객 진단에서 성능이 측정
불가가 된다. 진단 한 번에 최대 `CALLS_PER_SCAN`(= `sampling.perf_lab.max_urls` = 5)
회이므로 이론상 하루 5,000회 진단이 한계다.

> **조직이 쓴 몫은 남은 양을 말해 주지 않는다.**

한도는 API 키 하나에 걸리고 키는 하나다. 한 조직이 태우면 모든 조직이 함께 막힌다.
조직별 숫자는 "누가 많이 썼나"용이고, "남았나"는 전체로만 답할 수 있다.

조회: `GET /api/usage/pagespeed-quota` · 화면: `/console/usage` 상단.
실패한 호출도 센다(요청은 나갔고 한도를 썼다). 경고는 넘기 **전에** 나온다(80%).
초기화는 구글이 태평양 시간 자정에 하고 우리는 UTC 로 세므로 최대 몇 시간 어긋난다 —
정확한 척하면 경계 근처에서 틀린 답을 확신 있게 말하게 된다.

### 3.5 실패했을 때 화면이 말하는 것

구글은 **400 하나에 정반대인 두 원인**을 담아 보낸다. 가르지 않으면 둘 다 "응답 형식이
다릅니다"로 나가고, 그 문장은 읽는 사람을 구글 변경 이력으로 보낸다.

| 원인 토큰 | 누구 문제인가 | 화면 문구의 요지 |
|---|---|---|
| `API_KEY_INVALID` | **우리** — 고객은 할 게 없다 | "사이트의 문제가 아니라 VEO 설정 문제" |
| `FAILED_DOCUMENT_REQUEST` | **대상 사이트** | "페이지를 열지 못했습니다" |
| 한도 초과 | **우리** | "사이트의 문제가 아니라 우리 한도입니다" |

셋 다 0-J(못 하는 이유를 고객 탓으로 적지 않는다)의 사례다. 성능이 통째로 빠진
보고서를 받은 고객은 **자기 사이트부터 고치려 든다.**

구글의 오류 문장은 한 글자도 고객에게 가지 않는다 — 거부된 키를 그대로 되돌려 주기
때문이다(`API key not valid. Please pass a valid API key`). 본문에서 꺼내는 것은
원인 토큰 하나뿐이고, 산문은 통과하지 못한다.

## 4. 결과에 반드시 함께 나가는 것

하나라도 빠지면 그 숫자는 VEO 점수가 아니다.

- 명세 id, 버전, SHA-256 체크섬
- 적용된 분모(`effective_weight_total`)와 단계별 분모
- **도달률(`reach`)과 확인하지 못한 관문(`gate_unverified`)**
- coverage 와 confidence
- 단계별 상태, N/A·UNKNOWN·실패 검사 목록
- 적용된 상한과 사유·해제 조건
- 올라온 게이트(라벨)
- 검사 단위까지 내려가는 `calculation_trace`(계수·배수·범위·신뢰도·감점·산식 문자열)

`POST /api/scoring/evaluate` 로 같은 입력을 넣으면 같은 점수가 재현된다.

## 5. 명세 버전 관리

| 상태 | 의미 |
|---|---|
| DRAFT | VEO-LAB 작성 중 |
| REVIEW | 검토 중 |
| APPROVED | 승인, 미발행 |
| PUBLISHED | 운영 사용. **수정 불가** |
| RETIRED | 폐기, 과거 결과 해석용으로만 유지 |

발행본은 바꾸지 않는다(ADR 0012). 변경은 새 버전이며, 과거 결과를 새 산식으로
재계산할 때는 원래 점수와 재계산 점수를 모두 남긴다. **1.7.0 이하로 매긴 과거 점수는
앞으로도 그때의 규칙으로 설명된다.**
