# VEO 화면 쇄신 — 리서치 · 브레인스토밍 · 기획 보고서

**2026-08-09** · 대상: 공개 진단(`/tools/*`) + 콘솔(`/console/*`) 전체
**성격:** 기능은 건드리지 않는다. 화면만 다시 그린다.

---

## 0. 한 장 요약

**문제는 "예쁘지 않다" 가 아니다. 화면이 사용자에게 아무 일도 시키지 않는다.**

VEO 는 정직하게 재는 일에 전부를 걸었고 그건 성공했다. 기획서 스스로도 그렇게 판정한다:

> "완성도 판정: 엔진은 상용 수준 이상, **소비 표면(화면)이 미달.**"
> (`veo/docs/PLAN-2026-08-total-review.md:10`)

그런데 같은 문서 §114 는 **"UX 는 전반 양호 판정"** 이라고 적었다. 이 둘은 모순이 아니라
**서로 다른 것을 잰 결과**다. §114 가 센 것은 로딩 표시·빈 상태·aria·대비 시험이다 —
그건 **위생**이지 설계가 아니다. "화면이 있는가 / 접근 가능한가" 는 쟀고,
**"화면이 사람을 움직이는가" 는 재지 않았다.** 이 보고서가 재는 것이 그것이다.

**핵심 실측 하나로 말하면:**

| | VEO `/tools/geo` | NXT 같은 목적 화면 |
| --- | ---: | ---: |
| 결과 나오기 전 본문 글자 수 | **83자** | **3,612자** |
| 문서 높이 | 뷰포트 한 장 | **4,663px** (6.5장) |

[실측] 2026-08-09, 브라우저 1280×720, `main.innerText` 길이. VEO 는 로컬 dev 서버,
NXT 는 `https://next-t.co.kr/geo/entity-check/`.

83자의 전문은 이것이 전부다 — **이게 첫 화면의 100% 다.**

> "SEO·GEO 점수 체크 / 주소 하나면 됩니다 — 검색엔진과 AI 답변 엔진이 이 페이지를
> 읽을 수 있는지 확인합니다 / 진단하기 / SEO 점수 / GEO 점수"

**제안:** `veo-design/` 에서 방향 **3안 × 화면 4장**을 같은 가짜 데이터로 만들어
나란히 놓고 고른다. `veo/` 코드는 0줄 수정.

## 1. 무엇을 근거로 썼나

지어낸 말을 줄이려고, 쓴 것은 전부 아래 넷 중 하나에서 나왔다.

| 근거 | 방법 |
| --- | --- |
| **VEO 현재 화면** | dev 서버(`localhost:3200`)를 실제로 띄워 화면 촬영 · DOM 측정 · 진단 1회 실행 |
| **VEO 코드** | `apps/web/src` 의 CSS 28개 · 내비게이션 정의 · 토큰 파일을 직접 세었다 |
| **VEO 문서** | 기획서 · 화면 설계(`architecture/screen-plan.md`) · 전수조사(`audit/2026-08-08-server-ui-gap.md`) |
| **참고 두 곳** | 넥스트티 `next-t.co.kr` (실제 접속 + 사장님 제공 결과 화면 2장) · 어크로스 GPTO `gpto.kr` (실제 접속 + 사장님 제공 대시보드 화면 5장) |

**못 한 것 하나** — 로컬에 API 서버가 없어 **진단 결과 화면은 렌더되지 않았다.**
`POST /api/public-scan` 이 응답 없이 대기했다. 그래서 결과 화면에 대한 판단은
화면 촬영이 아니라 **코드 읽기**(`PublicChecker.tsx` 756줄, `ScanReport.tsx` 510줄)에
근거한다. 이 보고서에서 결과 화면을 말할 때는 그렇게 표시했다.

## 2. 현재 상태 — 실측 9건

### 2-1. 첫 화면이 비어 있다 · 본문 83자 [실측]

입력창 하나와 안내 한 줄이 전부다. 아래는 푸터까지 빈 면이다.

**무엇이 없나** — ① 결과가 어떻게 생겼는지 ② 무엇을 근거로 채점하는지
③ 왜 믿을 만한지 ④ 이걸 받고 나면 뭘 하면 되는지.

**아이러니 하나.** GEO(AI 답변 엔진 대비) 진단 도구인데 **그 도구 페이지 자체에
AI 가 읽을 본문이 83자다.** 우리가 파는 기준으로 우리를 재면 낮은 점수가 나온다.

### 2-2. GEO 페이지의 제목이 "SEO·GEO" 다 [실측]

`/tools/geo` 의 H1 이 `SEO·GEO 점수 체크`. 상단 메뉴는 "GEO 점검" 인데 들어가면
제목이 다르다. `PublicChecker.tsx` 는 `kind: 'SEO' | 'GEO'` 를 받아 라벨은 가르는데
(`COPY` 상수, 79~96줄) **제목만 공용**이다.

### 2-3. 길 안내가 두 벌이다 [실측]

같은 목적지로 가는 길이 한 화면에 두 개 있다.

```
상단 메뉴:   SEO 점검 → /tools/seo      GEO 점검 → /tools/geo
페이지 안 탭: SEO 점수 → /tools/seo      GEO 점수 → /tools/geo
```

접근성 트리(`read_page`)에서 `link[/tools/geo]` 와 `tab[/tools/geo]` 가 동시에 잡힌다.
사용자는 "이 둘이 다른 건가" 를 한 번 생각해야 한다 — 그 생각은 공짜가 아니다.

### 2-4. 모바일에서 머리가 세 줄로 접힌다 [실측]

375×812 에서 헤더가 ① 로고 ② 메뉴 3개 ③ 콘솔 버튼 으로 세 줄이 된다.
첫 화면의 위쪽 **40% 를 머리말이 먹는다.**

### 2-5. 10~30초를 기다리는 동안 화면이 아무 말도 안 한다 [실측]

진단을 눌렀을 때 나오는 것은 회색 13px 문장 한 줄이 전부다.

> "페이지를 가져와 검사하는 중입니다 — 보통 10~30초 걸립니다."

코드로 확인: `.progress` 는 `<p>` 하나이고 `public-checker.module.css:41` 에
애니메이션도 단계 표시도 없다. **50초를 기다려도 같은 문장이었다** (API 미기동 상태).
안내된 30초를 넘겼다는 것을 화면이 모른다.

> 기획서 §114 의 "로딩 진행 링" 은 콘솔 쪽 이야기다. **공개 진단에는 없다.**

### 2-6. 콘솔 메뉴가 15개, 묶음 없이 평면이다 [실측]

`lib/navigation.ts` 의 `CONSOLE_NAV` 항목 15개.

```
대시보드 · 업체 관리 · 진단 · AI 가시성 · AI 답변 검수 · 키워드 · 브랜드 식별
· 이슈 · 리포트 · 원고 표현 검수 · 사용량·비용 · 채점 기준 버전 · 팀원 관리
· 변경 이력 · 내 계정
```

직원의 하루는 **"업체 고른다 → 잰다 → 문제를 본다 → 리포트를 낸다"** 인데,
메뉴는 그 흐름과 다른 순서로 늘어서 있다. 그리고 15개는 사람이 한눈에 훑는 한계를 넘는다.

주의 — 이 목록의 **이름들은 이미 여러 번 고쳐졌고 잘 골라져 있다.**
`navigation.ts` 주석에 그 흔적이 남아 있다("위험 검수와 의료광고 검수는 이름이 비슷해
같은 일로 읽혔다"). 문제는 이름이 아니라 **15개가 한 줄에 있다는 것**이다.

### 2-7. 디자인 시스템이 있는데 화면이 안 쓴다 [실측]

토큰 파일(`packages/ui/src/tokens.css`)은 글자 크기를 9단계로 정의한다.
그런데 화면 CSS 28개가 실제로 쓴 `font-size` 값은 **32종**이고, 그중 **20종이
토큰이 아닌 직접 쓴 px** 이다.

```
쓰인 값 상위:  var(--veo-font-size-200) 175회   ← 13px, "칩·배지용" 이라 정의된 크기
              var(--veo-font-size-100) 105회   ← 12px, "메타데이터용"
              11.5px 15회 · 13px 14회 · 12.5px 12회 · 11px 12회
              10.5px 8회 · 9.5px 3회 · 14.5px 3회 …
```

두 가지가 보인다.

* **반 픽셀 크기(11.5 · 12.5 · 10.5 · 9.5)** 가 있다. 이건 눈으로 맞춰가며
  조금씩 줄인 흔적이다 — 자리가 모자라서 글자를 줄인 것이지 위계를 정한 게 아니다.
* **가장 많이 쓰인 두 크기가 13px 과 12px**, 즉 토큰이 "칩·배지·메타데이터용"
  이라고 적어 둔 크기다. 본문 크기(`400` = 16px)는 **8회**뿐이다.
  화면 전체가 각주 크기로 쓰여 있다.

색도 같다. 화면 CSS 5개 파일에 **직접 쓴 색 25종**이 들어 있다.

### 2-8. 정의되지 않은 변수 6곳 — 그 줄은 아무 일도 안 한다 [실측]

`competitors.module.css` 여섯 줄이 존재하지 않는 토큰을 부른다.

```
competitors.module.css:255, 261, 276, 291, 300   font-size: var(--veo-font-size-sm);
competitors.module.css:308                        font-size: var(--veo-font-size-xs);
```

`--veo-font-size-sm` · `--veo-font-size-xs` 는 토큰 파일에 **없다**(있는 것은
`-100`~`-900` 숫자 체계다). 폴백값도 안 적혀 있다. 그래서 이 여섯 줄은
**CSS 가 무시한다** — 크기를 정해 놓았는데 적용이 안 된 상태로 지금 돌고 있다.

(같은 종류의 다른 3곳 — `--veo-color-danger` · `--veo-color-ink` · `--veo-radius-full` —
은 폴백이 적혀 있어 동작한다. 문제는 아니지만 토큰을 우회한 것은 같다.)

### 2-9. 원래의 2색 체계가 덮여 한 색이 되었다 [실측]

토큰 파일 머리말은 VEO 의 정체성을 이렇게 적어 두었다.

> "a single teal **signal** colour for measurement, and a violet **beam** accent
> reserved for GEO/AI surfaces **so readiness and observation never visually
> collapse into one another**." (`tokens.css:6~9`)

**"준비도" 와 "관측" 이 시각적으로 섞이지 않게** 색을 둘로 갈라 둔 것이다.
그런데 `stripe-theme.module.css` 가 액센트를 인디고 하나(`#533afd`)로 덮었고,
그 파일이 **공개 화면과 콘솔 양쪽에 함께 적용**된다(파일 주석 3~6줄).

그 결정 자체는 근거가 있다 — 주석에 "한 제품이 두 얼굴을 갖는 것보다 확정을
갱신하는 편이 낫다" 고 판단 경위가 남아 있고, 사용자 지적("메인화면도 톤앤매너 적용")
이 계기였다. **다만 그때 함께 사라진 것이 두 눈금을 가르던 색이다.**
지금은 SEO 준비도와 AI 가시성이 화면에서 같은 색이다.

## 3. 참고 두 곳 — 무엇을 잘하나

### 3-1. 넥스트티(NXT) — **결과 화면의 문법**

사장님이 주신 결과 화면 2장과 실제 접속으로 확인한 것.

| 무엇 | 어떻게 |
| --- | --- |
| **할 일을 맨 위에** | "100점까지 — 개선 할 일" 카드가 결과 최상단. 각 항목에 **+42점 · +21점** |
| **점수가 따라다닌다** | 오른쪽 사이드바에 큰 점수 + 등급 6단계 **전체 표**(현재 등급만 강조) |
| **분모를 보여준다** | 카테고리를 `55/55` `30/30` `15/15` 로. 항목도 `5/5` |
| **고칠 코드를 그대로** | SEO 화면에 수정 대상 HTML 을 코드 박스로. 복사해서 쓰면 된다 |
| **감지한 것을 그림으로** | 엔티티마다 칩, 충족/누락 속성을 색으로 갈라 늘어놓음 |
| **빈 화면이 일한다** | 결과 전에 채점 기준 · "엔티티 점수, 왜 중요한가요?" 3단계 그림 · FAQ · 결과 예시 |
| **다음 곳으로 보낸다** | 하단 "함께 보면 좋은 도구·서비스" 4칸 |

빈 화면 본문 **3,612자** [실측]. 그중 상당 부분이 검색·AI 가 읽을 콘텐츠다 —
**진단 도구가 동시에 유입 페이지 노릇을 한다.**

### 3-2. 어크로스 GPTO — **서사와 증명의 문법**

| 무엇 | 원문 |
| --- | --- |
| **결과를 헤드라인에** | "ChatGPT가 당신의 제품을 1위로 추천하도록" |
| **제품을 4단계 이야기로** | Monitoring → Diagnostics → Strategy → Distribution |
| **규모를 4칸 숫자로** | "10대 LLM 추적 / 500+ 배포 채널 / 18+ 최적화 언어 / 주 1회 오토 사이클" |
| **증명을 숫자로** | "223,882회 누적 모니터링 데이터" · "+15% AI 브랜드 노출률 평균 성장" · 100+ 도입사 |

[실측] 위 문구는 `gpto.kr` 에서 그대로 인용.

**그리고 화면 자체를 마케팅 자산으로 쓴다.** 사장님이 주신 대시보드 화면 5장에서
읽히는 것:

* **질문 하나하나에 `19% → 55%`** 가 붙는다 — 상태가 아니라 **변화**를 판다
* **`전체 언급률: 10.8% (+31.4%p) → 42.2%`** — 한 줄로 성과가 끝난다
* 주차별 추이 곡선 · AI 모델별 레이더(기존 vs 현재) · 언급 브랜드 30여 개를 색 점으로
* 왼쪽 질문 목록 / 오른쪽 결과 — **2단 고정 구성**

**한 문장으로:** GPTO 는 **before → after** 를 판다. VEO 는 **지금 상태**만 보여준다.

## 4. 진단 — 왜 모자란가 (근본 원인 5)

### 원인 1. 정직함이 결론을 가렸다

VEO 문서 전체를 관통하는 원칙이 있다 — 분모를 보여준다, N/A 를 0으로 처리하지 않는다,
출처와 수집 시각을 함께 적는다, 못 잰 값을 0처럼 그리지 않는다.
**이 원칙들은 옳고, 버리면 안 된다.**

문제는 **그것들이 결론과 같은 크기로 나란히 놓여 있다는 것**이다.
정직함은 **신뢰의 조건**이지 **사용의 이유**가 아니다. 사용자는 "무엇을 먼저 고치나" 를
알러 온다. 근거는 그 답을 의심할 때 펼쳐 보는 것이다.

> **처방:** 근거를 지우지 않는다. **접는다.** 기본은 결론, 펼치면 근거.

### 원인 2. 화면이 "잰 것의 목록" 이지 "할 일" 이 아니다

NXT 는 결과를 열면 **"할 일 4개, 각각 +42/+21/+21/+17점"** 이 먼저 온다.
VEO 는 체크리스트가 먼저 온다. 47개 항목의 통과/실패는 **측정 결과**이지
**작업 지시**가 아니다.

기획서 `screen-plan.md:57` 이 이미 이걸 적어 놨다 — "④ 개선 할 일에 **+N점** /
채점기가 계산 가능(SEO) / **VEO 현재: 없음**". **1년 전에 알고 있었고 아직 없다.**

### 원인 3. 빈 화면·기다리는 화면·끝난 화면을 설계하지 않았다

제품 화면은 네 가지 상태가 있다 — **비어 있음 · 기다림 · 결과 · 오류**.
VEO 는 **결과와 오류만 설계**했다. 앞의 둘은 "아직 없음" 상태로 남아 있다.
그런데 사용자가 처음 만나는 것은 **비어 있음**이고, 두 번째가 **기다림**이다.
**첫 40초를 설계하지 않은 셈이다.**

### 원인 4. 콘솔이 "기능 목록" 이지 "업무 흐름" 이 아니다

15개 메뉴는 **서버가 가진 능력의 목록**에 가깝다. 사람이 하는 일의 순서가 아니다.
이건 우연이 아니다 — 전수조사 문서(`audit/2026-08-08-server-ui-gap.md`)의 관점 자체가
"엔드포인트마다 화면이 있는가" 다. 그 관점은 **구멍을 찾는 데는 정확하지만
화면을 묶어 주지는 않는다.** 끝까지 밀면 엔드포인트 수만큼 메뉴가 생긴다.

### 원인 5. 화면끼리 서로를 모른다 — 그래서 규칙이 화면마다 다시 생긴다

CSS 5,757줄이 29개 파일에 흩어져 있고, 화면마다 자기 글자 크기(32종)와 자기 색(25종)을
다시 정했다. **디자인 시스템이 없어서가 아니다 — 있는데 화면이 그걸 거치지 않고
지나갈 수 있어서**다. 반 픽셀 크기와 정의 안 된 변수 6곳이 그 증거다.

## 5. 설계 원칙 7 — 샘플이 지킬 것

| # | 원칙 | 이유 |
| --- | --- | --- |
| **1** | **결론 → 근거 순서로 접는다** | 정직함을 버리지 않으면서 결론을 보이게 하는 유일한 방법 |
| **2** | **첫 화면은 점수가 아니라 "할 일 3개"** | 점수만 있으면 불안만 남는다. 할 일에는 `+N점` 을 붙인다 |
| **3** | **숫자 하나에 세 가지를 붙인다 — 분모 · 시각 · 변화량** | 앞의 둘은 이미 한다. **변화량이 없다.** GPTO 가 파는 것이 그것이다 |
| **4** | **두 눈금은 색으로 가른다** | `tokens.css:6~9` 의 원래 의도 복구. 준비도=signal, AI 관측=beam |
| **5** | **네 가지 상태를 다 그린다 — 빈 · 기다림 · 결과 · 오류** | 사용자가 만나는 순서대로. 기다림에는 단계와 경과 시간 |
| **6** | **콘솔 15개를 4묶음으로** | 대상(업체) → 측정(진단·AI가시성·키워드) → 처리(이슈·검수) → 산출(리포트) · 설정은 접는다 |
| **7** | **화면은 토큰을 거치지 않고 색·크기를 정할 수 없다** | 원인 5의 재발 방지. 규칙은 글이 아니라 관문이어야 한다 |

**원칙 7 은 구현 방식까지 정한다** — 샘플에서는 화면 CSS 에 hex 색과 px 글자 크기를
**아예 쓰지 않는다.** 다 쓰고 나서 `grep '#[0-9a-f]\{3\}' samples/` 가 0줄이면 지킨 것이다.
글로 적힌 규칙은 안 지켜진다는 것이 §2-7·2-8 에서 이미 증명됐다.

## 6. 기획 — 샘플링 프로젝트

### 6-1. 무엇을 만드나

**방향 3안 × 화면 4장 = 12장.** 전부 **같은 가짜 데이터** 한 벌로 그린다 —
데이터가 다르면 디자인이 아니라 데이터를 비교하게 된다.

**화면 4장** (사용자가 만나는 순서대로 골랐다)

| # | 화면 | 왜 이걸 고르나 |
| --- | --- | --- |
| 1 | **공개 진단 — 빈 화면** | 지금 83자. 가장 크게 벌어진 자리 |
| 2 | **공개 진단 — 결과** | 영업이 실제로 보여주는 화면. `+N점` 과 근거 접기가 여기서 판가름 난다 |
| 3 | **콘솔 대시보드** | 직원이 매일 여는 첫 화면. 메뉴 4묶음이 여기서 시험된다 |
| 4 | **이슈 상세 한 건** | "문제 → 근거 → 고칠 코드 → 재측정" 한 바퀴. VEO 의 진짜 값어치가 여기 있다 |

**가짜 데이터 한 벌** — `good-tour.kr` 을 대상으로, SEO 78점 / GEO 41점, 이슈 6건,
그중 3건이 `+N점` 을 가진 개선 항목. (숫자는 **지어낸 것이고 화면에 그렇게 적는다.**)

### 6-2. 방향 3안

세 방향은 **"무엇을 파는가"** 가 다르다. 색이나 폰트가 아니다.

---

#### A안 — **관제탑 (Control Tower)** · *변화를 판다*

GPTO 계열. 어두운 바탕, 큰 숫자, 추이 곡선이 주인공.

* 첫 화면에 **`42% → 61%` 같은 변화 한 줄**이 제일 크게 온다
* 점수는 원형 게이지가 아니라 **시간 축 위의 선**
* 콘솔 대시보드 = 업체별 추이 카드가 격자로
* SEO(teal) / GEO(violet) 두 색이 차트에서 확실히 갈린다

**강점** — 계약 고객에게 매달 보여줄 것이 생긴다. 재계약 근거가 화면에 있다.
**약점** — VEO 는 지금 **이력을 거의 안 쌓는다.** `screen-plan.md:59` 가 적어 둔
"⑥ 측정 이력 격자 — 테이블(`scan_runs`)만 있고 저장 안 함" 이 걸린다.
A안은 **데이터가 먼저 필요하다.**
**리스크** [추정] — 한 번만 재고 마는 잠재 고객에게는 빈 차트가 보인다.

---

#### B안 — **진단서 (Clinical Report)** · *신뢰를 판다*

NXT 계열 + VEO 의 정직함. 밝은 바탕, 문서형, 근거가 주인공.

* 맨 위 **"100점까지 — 할 일 3건"**, 각 `+12점` `+8점` `+5점`
* 그 아래 접힌 항목들. 펼치면 **판정 → 근거(원자료 인용) → 고칠 코드 → 재측정 규칙**
* 오른쪽에 따라다니는 점수 + **등급 6단계 전체 표**(현재만 강조)
* 빈 화면이 채점 기준·예시·FAQ 로 채워진다 (§3-1 의 3,612자에 대응)

**강점** — VEO 가 이미 가진 것(47항목·근거·`fix_example`·재검증 규칙)을 **그대로 쓴다.
새로 만들 데이터가 없다.** 병원 상대 영업에서 "진단서" 라는 은유가 그대로 통한다.
**약점** — 정적이다. 매달 보여줄 새것이 없다.
**리스크** [추정] — NXT 와 닮아 보일 수 있다. `screen-plan.md:6` 이 인용한 기획서 §12.1
("NXT 화면을 복제하지 않는다") 과 **부딪히지 않게 색·형태를 확실히 갈라야 한다.**

---

#### C안 — **작업대 (Workbench)** · *속도를 판다*

Linear·Stripe 계열. 밀도 높은 실무 도구. 목록과 단축키가 주인공.

* 콘솔이 중심. 왼쪽 좁은 메뉴 4묶음, 가운데 목록, 오른쪽 상세 — **3단 고정**
* 이슈를 목록에서 바로 처리(담당자 지정·재측정 요청)하고 화면을 안 떠난다
* 공개 진단은 **얇게** — 입력 → 결과 한 장
* 색은 거의 안 쓴다. 위계는 여백과 굵기로

**강점** — 직원 15개 메뉴 문제(§2-6)를 정면으로 푼다. 하루에 업체 20곳을 도는
사람에게 가장 빠르다.
**약점** — 공개 화면에서 잠재 고객을 설득하는 힘이 A·B 보다 약하다.
**리스크** [추정] — 밀도가 높으면 비전문가 고객에게 보여주기 어렵다.

---

### 6-3. 세 안을 어떻게 볼 것인가

**섞을 수 있다.** 실제로는 이렇게 갈릴 가능성이 높다 [추정]:

```
공개 진단(잠재 고객·영업)  →  B안 (진단서)
콘솔(직원 실무)            →  C안 (작업대)
계약 고객 월간 보고        →  A안 (관제탑)   ※ 이력이 쌓인 뒤
```

그래서 샘플을 **한 안만 만들지 않는다.** 12장을 다 만들어야 이 갈래가 보인다.

## 7. 판정 기준 — 무엇으로 고를 것인가

"예뻐 보인다" 로 고르면 다음 달에 또 뒤집힌다. 셋으로 판정한다.

| 기준 | 재는 법 | 통과선 |
| --- | --- | --- |
| **1. 5초 안에 다음 할 일을 말할 수 있나** | 결과 화면을 5초 보여주고 "지금 뭘 하면 되나" 를 묻는다 | 3명 중 3명이 같은 답 |
| **2. 새로 만들 데이터가 있나** | 각 안이 요구하는 값을 서버가 이미 주는지 대조 | 없을수록 좋다 (B안이 유리) |
| **3. 토큰을 우회한 자리가 0인가** | `grep -E '#[0-9a-fA-F]{3,8}\|font-size:\s*[0-9]' samples/` | **0줄** |

기준 3 은 §5 원칙 7 의 관문이다. 이건 사람 판단이 아니라 **명령 한 줄이 판정**한다.

## 10. 정정 대장에 올릴 것

§2-8 에서 나온 것은 **디자인 의견이 아니라 지금 돌고 있는 결함**이다.

```
competitors.module.css:255,261,276,291,300  font-size: var(--veo-font-size-sm)  ← 미정의
competitors.module.css:308                   font-size: var(--veo-font-size-xs)  ← 미정의
```

토큰에 없고 폴백도 없어 **여섯 줄이 적용되지 않은 채 배포되어 있다.**
샘플링과 무관하게 `veo/` 에서 고쳐야 한다 — 다만 **이 보고서는 코드를 안 건드리므로
여기 적어 두고 넘긴다.** (`veo/docs/CORRECTIONS.md` 에 올릴 항목)
