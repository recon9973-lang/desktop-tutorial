> 성격: 반자동(휴먼인더루프) 데스크톱 RPA. **민감정보(주민번호) 처리**가 최대 쟁점.

## 1. 목적

사용인이 카톡/문자/이미지로 받은 고객정보를 사람이 GA 화면에 일일이 타이핑하는 반복작업을 줄인다. 입력 오류(특히 주민번호·전화번호)를 검증으로 낮춘다.

**1차 목표는 자동 제출이 아니라**, 필드 자동입력까지 하고 **제출 직전 사람 확인**을 남기는 반자동 도구다.

### KPI
- 건당 입력시간 수기 대비 50%+ 단축
- 주민번호·전화번호 형식/검증 오류 0건(제출 전 게이트 기준)
- 민감정보 로컬 영구저장 0건

---

## 2. ⚠️ 최대 쟁점 — 주민등록번호(고유식별정보) 처리

주민번호는 개인정보보호법상 **고유식별정보**로 처리가 원칙적으로 제한되며, 별도 법령 근거·안전조치가 요구된다. (보험업은 계약 인수·유지 목적의 법령상 처리 근거가 있으나, 그와 별개로 **안전조치 의무**는 그대로 적용.)

**필수 안전조치(설계에 강제 반영):**
- **온디바이스 OCR만 사용.** 주민번호 이미지를 클라우드 OCR(Google/OpenAI 등)로 **전송 금지.**
- **최소보관·즉시파기.** 메모리에서만 다루고, 입력 완료 후 즉시 폐기. **로컬 영구저장·로그 기록 절대 금지.**
- **화면 마스킹.** 확인 화면에서 뒤 6자리 마스킹(예: `900101-1******`), 필요 시에만 일시 노출.
- **암호화.** 처리 중 불가피한 임시 보관은 메모리 암호화, 디스크 저장 금지.
- **클립보드 금지/즉시 클리어.** 자동입력에 클립보드를 쓰면 사용 직후 비운다.
- **주민번호 검증(체크섬).** 주민번호 검증번호 알고리즘으로 OCR 오인식을 즉시 검출 → 잘못된 번호가 GA에 들어가는 것을 원천 차단.
- **접근통제.** 개인 PC 전용·화면잠금 전제(v1).

> 로그 정책: 주민번호는 **어떤 형태로도 로그에 남기지 않는다.** 처리 이력에는 이름·마스킹된 식별자·성공/실패만.

---

## 3. 자동 로그인 재검토 (1번 문서의 '수동 로그인' 원칙과 조정)

사용자 요청에 따라 **자동 로그인을 도입**하되, 안전을 위해 **반자동**으로 설계한다.

- **자동 가능**: 로그인 ID/PW를 OS 보안저장소(keyring)에서 불러와 자동 입력.
- **자동 불가(수동 유지)**: **간편비밀번호는 셔플 키패드**라 자동 클릭이 불안정·위험 → 사용자 직접 입력. 캡차·추가 인증도 사용자 이관.
- 즉, **"ID/PW 자동입력 → 사용자 간편PW 입력 → 이후 자동화 재개"** 형태.
- 무인(백그라운드) 자동 로그인은 하지 않는다. **반드시 사용자 세션 하에서** 실행.
- 자격증명은 코드·평문 저장 금지, keyring 사용. 자동 로그인 on/off 토글을 사용자에게 제공.

## 4. 워크플로우

```text
프로그램 실행
→ 고객정보 입력(카톡 텍스트 붙여넣기 / 이미지 업로드 / 직접 입력)
→ 온디바이스 OCR·파싱: 이름 · 전화번호 · 주소 · 주민번호
→ 검증
     · 주민번호: 형식 + 체크섬
     · 전화번호: 형식 정규화(010-####-####)
     · 주소: 우편번호/도로명 정규화
→ 사용자 확인 게이트(주민번호 마스킹 표시)
→ GA 자동 로그인(ID/PW 자동) → 사용자 간편PW 입력
→ 대상 입력 화면 이동(고객등록/계약입력 등)
→ 필드 자동 입력(셀렉터 매핑)
→ ★ 제출 직전 사용자 최종 검토(민감정보 제출 게이트)
→ 제출
→ 결과 확인 + 처리 로그(주민번호 제외·마스킹)
```

## 5. 필드 매핑 & 데이터 처리

| 필드 | 처리 | 검증 |
|------|------|------|
| 이름 | 텍스트 정규화(공백/한자 처리) | 필수 존재 |
| 전화번호 | 숫자 추출·`010-####-####` 정규화 | 자리수·형식 |
| 주소 | 도로명/지번·우편번호 분리 | 우편번호 매칭(주소검색 API 검토) |
| 주민번호 | 앞7+뒤7, **마스킹 표시** | **체크섬**·생년월일 정합성 |

- **주소 정규화**: 행안부 도로명주소 API 또는 우편번호 서비스 검토. 단 주소도 개인정보이므로 **필요 최소 전송**, 가능하면 로컬 사전/캐시 우선.
- 폼 입력은 **HTML 셀렉터 우선**, 좌표 클릭 최후. 입력 후 값 재확인(입력 검증).

## 6. 시스템 구성 (1번과 공통 모듈 재사용)

- **입력/OCR 모듈**: 온디바이스 OCR(Tesseract/PaddleOCR) + 텍스트 파서. (주민번호 클라우드 전송 차단)
- **웹 자동화 모듈**: Playwright, 반자동 로그인 + 필드 입력. UI 변경 감지·수동 이관.
- **보안 저장 모듈**: keyring(자격증명). 주민번호는 저장 대상 아님(메모리·즉시파기).
- **상태·중복방지**: SQLite에 처리 이력·중복 고객 등록 감지 키(주민번호는 **해시·마스킹**만, 원문 금지).
- **UI**: 입력·검증·마스킹 표시·제출 게이트가 있는 업무 패널.

## 7. 예외 처리

- OCR 주민번호 오인식 → **체크섬 실패 경고**, 진행 차단
- 전화/주소 형식 오류 → 사용자 수정 요청
- 자동 로그인 실패/세션 만료/캡차·추가인증 → 사용자 이관
- 대상 입력 화면·필드 셀렉터 변경 → 자동화 중단·수동 이관
- 중복 고객 등록 감지 → 사용자 확인 후에만 진행
- 제출 후 검증 실패 → 재시도/보정

## 12. 확정 필요 결정사항

1. 자동 로그인 범위: **ID/PW 자동 + 간편PW 수동(권장)** 확정 여부.
2. 주소 정규화: 외부 API 사용 vs 수기 입력(개인정보 최소전송 관점).
3. 주민번호 확인 화면 마스킹 수준(뒤 6자리 vs 뒤 7자리 전체 마스킹).
4. 제출 방식: **제출 직전 사람 확인(권장)** vs 조건부 자동 제출(비권장, 리스크 큼).
5. 중복 감지 키 방식: 주민번호 해시 vs 이름+생년월일.
6. 배포: 개인 PC 전용(권장, v1).

## 13. 1차 권장 결론

```text
고객정보 입력(카톡/이미지/직접)
→ 온디바이스 OCR·파싱(이름·전화·주소·주민번호)
→ 검증(주민번호 체크섬 · 전화 형식 · 주소 정규화)
→ 사용자 확인(주민번호 마스킹)
→ GA 반자동 로그인(ID/PW 자동, 간편PW 수동)
→ 대상 화면 필드 자동 입력
→ ★ 제출 직전 사람 최종 확인
→ 제출 → 결과 확인 → 로그(주민번호 제외)
```

민감정보를 다루는 만큼 **온디바이스 처리·즉시파기·제출 전 사람 확인**을 기본값으로 하고, 실사용 병목이 확인되면 자동화 범위를 넓힌다.
