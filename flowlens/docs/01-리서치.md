# FlowLens 리서치 (구현 관점)

작성일: 2026-07-14
목적: 사업계획서는 "무엇을/왜"까지 정리되어 있음. 이 문서는 **"어떻게 만들 것인가"** 를 위한 기술·구현 리서치를 정리한다. 초기 타깃은 **대행사(다중 고객)**.

---

## 1. 사업계획서에서 확정된 전제 (재확인)

- 포지션: 무료 Clarity와 기능 수로 싸우지 않고, **국내 설치 편의 + 한국어 개선 리포트 + 개인정보 보호 기본값 + 대행사 운영 자동화**로 차별화.
- 초기 타깃을 대행사로 잡으면 자연스럽게 **멀티테넌시(대행사 → 고객사 → 사이트)** 구조가 제품의 뼈대가 된다.
- MVP는 A/B 테스트, 모바일 앱, 폐쇄형 플랫폼 자동설치, SSO를 제외한다.

## 2. 행동 데이터 수집은 어떻게 동작하는가

웹 행동 분석 도구는 공통적으로 아래 흐름을 쓴다.

1. **추적 스크립트(SDK)** 를 고객 사이트 `<head>` 또는 `<body>`에 한 줄 삽입.
2. 스크립트가 브라우저 이벤트(click, scroll, pointermove, resize, form focus 등)를 리스닝.
3. 이벤트를 **배치(batch)** 로 모아 일정 주기 또는 페이지 이탈 시 `navigator.sendBeacon()`으로 수집 서버에 전송.
4. 서버는 site key로 사이트를 식별하고 이벤트를 저장.
5. 집계 워커가 히트맵/세션/지표를 계산, 대시보드가 시각화.

핵심 기술 포인트:

- **좌표 정규화**: 화면 크기가 제각각이므로 절대 픽셀이 아니라 **상대 좌표(0~1)** 또는 문서 폭 대비 비율로 저장해야 히트맵을 합칠 수 있다.
- **전송 방식**: `sendBeacon`은 페이지가 닫혀도 전송을 보장한다. 실패 대비로 `fetch(keepalive:true)` 폴백.
- **샘플링**: pointermove는 초당 수십~수백 이벤트가 발생 → 그대로 저장하면 비용 폭발. **throttle(예: 100~200ms)** 로 샘플링.
- **세션 식별**: 쿠키 없이도 가능하도록 `sessionStorage` 기반 세션 ID + 30분 무활동 시 만료. 개인 식별이 아니라 세션 구분용.
- **봇 제외**: `navigator.webdriver`, 알려진 봇 UA, 비정상 이벤트 패턴 필터.

## 3. 개인정보 보호 — 제품의 핵심 기능 (법무 아님)

사업계획서 9장을 구현 규칙으로 번역:

| 원칙 | 구현 방법 |
|---|---|
| 입력값 미수집 | SDK가 `input/textarea/select`의 value를 **절대 읽지 않음**. click 대상이 입력요소면 좌표만 기록. |
| 민감정보 자동 마스킹 | 텍스트 수집이 필요한 경우(예: 클릭된 버튼 라벨) 전송 **전** 정규식으로 이메일/전화/카드/주민번호 패턴을 `***`로 치환. |
| 비밀번호 필드 | `type=password` 근처 이벤트는 좌표·라벨 모두 수집 제외. |
| IP 원본 미저장 | 서버가 IP를 저장하지 않거나, 저장 시 즉시 해시/절단(anonymize). MVP는 **미저장**. |
| 민감 페이지 제외 | 사이트 설정에서 URL 패턴(예: `/checkout`, `/mypage`) 녹화 제외 목록. |
| 보관기간 | 요금제별 원본 이벤트 보관기간 제한(예: 30/90/180일), 초과분은 집계값만 유지. |

> MVP 구현 원칙: **"수집하지 않으면 유출도 없다."** 폼 입력값·비밀번호는 아예 코드 경로에 존재하지 않게 만든다.

## 4. 히트맵/세션 리플레이 구현 옵션

- **클릭 히트맵**: 상대 좌표 click 이벤트를 캔버스에 방사형 그라디언트로 누적 → 열지도. 라이브러리 없이 canvas만으로 구현 가능(MVP 채택).
- **스크롤 히트맵**: 각 세션의 최대 스크롤 도달 깊이(%)를 구간별로 집계 → "X% 지점까지 도달한 방문자 비율" 막대.
- **세션 리플레이**: 정석은 `rrweb`(DOM 스냅샷 + 변경 기록 재생). 강력하지만 저장 비용·민감정보 리스크가 큼. **MVP에서는 "이벤트 타임라인"(클릭/스크롤/이탈을 시간순으로 나열)만 제공**하고, 완전한 DOM 리플레이는 2단계로 미룬다.

## 5. 저장소 선택 (MVP는 단순하게)

- 사업계획서 권장: PostgreSQL(메타) + ClickHouse/BigQuery(이벤트) + Kafka(큐).
- **MVP 현실론**: 이벤트도 초기에는 PostgreSQL 한 곳에서 처리 가능. 트래픽이 커지면 이벤트 테이블만 ClickHouse로 이관.
- 본 코드베이스는 **개발 편의를 위해 SQLite + Prisma**로 즉시 실행되게 만들고, `provider`만 바꾸면 PostgreSQL로 전환되도록 설계. (Prisma는 SQLite↔PostgreSQL 전환이 스키마 한 줄 수정 수준)

## 6. 멀티테넌시(대행사) 데이터 모델의 핵심

대행사 타깃이므로 권한/격리 구조가 1순위.

```
Agency (대행사 워크스페이스)
  └─ User (대행사 멤버, 역할: OWNER/MEMBER)
  └─ Client (대행사의 고객사)
        └─ Site (고객사의 웹사이트, siteKey 보유)
              └─ Session
                    └─ Event
              └─ Report / Suggestion
        └─ ShareLink (고객 공유용 읽기전용 화이트라벨 리포트)
```

- 모든 조회 쿼리는 **로그인한 유저의 Agency 범위**로 자동 필터 → 다른 대행사 데이터 격리.
- 고객 공유는 계정 없이 볼 수 있는 **토큰 기반 읽기전용 링크**(화이트라벨).

## 7. 개선 제안 = 룰 엔진 + 신뢰도 (AI는 나중)

사업계획서 8장의 로직을 그대로 코드화. 초기에는 LLM 단독 판단이 아니라 **결정론적 룰 엔진**이 안전하다.

예시 룰:
- `CTA 노출률 < 40% AND 모바일 이탈률 높음` → "모바일 첫 화면 고정 CTA 검토"
- `클릭 불가 요소 반복 클릭 발생` → "해당 이미지에 상세보기/확대 기능 추가"
- `폼 시작 대비 제출률 < 30%` → "폼 필드 축소 또는 단계 분리 검토"

신뢰도: 세션 수 500+ → 높음 / 100~499 → 보통 / <100 → 낮음(경고 표시).

## 8. 경쟁사 대비 MVP가 반드시 가져야 할 "대행사 무기"

무료 Clarity에 없는 대행사 전용 가치:

1. **한 화면에서 모든 고객사 사이트 지표** (Clarity는 사이트마다 별도 프로젝트, 대행사 뷰 없음)
2. **고객사별 월간 리포트 자동 생성 + 대행사 로고 화이트라벨**
3. **고객에게 보내는 읽기전용 공유 링크** (계정 없이 열람)
4. **한국어 개선 과제 자동 도출** (데이터가 아니라 "무엇을 고칠지")

MVP는 이 4가지를 반드시 데모 가능한 수준으로 구현한다.

## 9. 리서치 결론

- 기술적으로 MVP는 **추적 SDK + 수집 API + Postgres/SQLite + Next.js 대시보드 + 룰 엔진**으로 충분히 동작 가능.
- 가장 큰 리스크는 개인정보와 저장 비용 → **미수집·샘플링·보관기간 제한**으로 설계 단계에서 차단.
- 대행사 타깃은 곧 멀티테넌시. 이 구조를 처음부터 데이터 모델에 박아두면 이후 확장이 쉽다.
