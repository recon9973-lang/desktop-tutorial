# 판 번호 충돌 — 왜 나고, 무엇이 이미 막고 있고, 어디가 뚫려 있나

> 사장님 오더(2026-09-19): «판 번호 충돌 방지 방법 정리해줘».
>
> **먼저 밝힐 것**: 이 저장소에는 **이미 막는 장치가 있다.** 새 방법을 지어내기 전에
> 있는 것부터 읽었다. 남은 것은 «방법이 없다»가 아니라 «있는 길을 안 타는 자리»다.

## 1. 왜 나나

방이 셋인데 **서로 직접 말을 못 한다**(사장님이 전달자). 각 방이 일을 시작할 때 판
번호를 잡으면, 그 번호는 main 에 닿을 때까지 남의 것이 될 수 있다.

```
[실측 2026-09-07~08 · scripts/claim_version.py 머리말] 이틀에 열한 번 부딪혔다
  0.3.531~0.3.536 · 0.3.540 두 번 · 0.3.541 · 0.3.542 · 0.3.543 두 번 · 0.3.545
[실측 2026-09-01 · 이 방] 하루에 두 번
  0.3.455(ANSEO 방과) · 0.3.460~0.3.463(특허 이식 방과)
```

**앞질러 잡는 것은 이미 해 봤고 안 통했다.** 0.3.540 을 미리 잡고 537~539 를 비워
두었는데 닿기 전에 집혔다. 구간을 나눠 예약하는 방식도 같은 이유로 샌다 — 번호는
**main 에 먼저 닿는 쪽이 갖기** 때문이다.

## 2. 이미 막고 있는 것

| 무엇 | 어디 | 하는 일 |
|---|---|---|
| **판을 나갈 때 정한다** | `scripts/deploy.sh` (295~318줄) | main 판을 읽어 내 판이 막혔으면 **main+1 로 물린 뒤** 후보 가지로 민다 |
| 기계가 고치는 네 곳 | `make bump-version` | 판 · 계약 · 생성 클라이언트 · 계약 관문 |
| **사람이 쓴 글 세 곳** | `scripts/claim_version.py` | `changelog.ts` 맨 위 항목 · `WORKLIST.md` 머리말과 대기 표의 내 줄 · `WORKLIST-HISTORY.md` 그 판의 절 제목 |
| 통째 치환 금지 | 같은 파일 | 옛 판 번호는 **그때의 진실**이라 자리를 하나씩 짚어 바꾸고, 못 찾으면 조용히 넘어가지 않고 **선다** |
| 나간 기록을 덮지 않기 | `_refuse_to_relabel` | 새 항목을 안 쓰고 물리면 **이미 나간 항목**에 새 번호를 달아 준다 — main 맨 위 기록과 같으면 멈춘다 (2026-09-15 에 실제로 네 판이 그렇게 이름을 갈았다) |
| 대기 표에 번호를 미리 안 적기 | `WORKLIST.md` 739줄 | 미리 적으면 `claim_version` 이 고칠 자리를 못 찾아 **배포가 선다**(2026-09-10 실제 발생) |
| 대장 관문 | `worklist.test.ts` | 머리말 범위 = 대기 표, changelog 맨 앞 = APP_VERSION 등 |

**즉 `make deploy` 로 나가면 충돌은 구조적으로 안 난다.**

## 3. 그런데도 또 겹친 이유 — 구멍 둘

### 구멍 ① `make deploy` 를 **안 타는 배포 경로**가 있다

`git push origin <sha>:main` 으로 손으로 미는 길이다. 그 경로에는 물림 단계가 없다.

```
[실측 2026-09-11 · WORKLIST.md 693줄] GEO 진단기 세 건
  "이 방은 make deploy 권한이 막혀, 후보 가지에서 CI 초록을 받은 뒤 그 커밋을
   손으로 main 에 올렸다. 그 경로에는 claim_version 이 없다."
  → 다른 방이 잡아 둔 0.3.563 안에 얹혀 나갔다
[실측 2026-09-01 · 이 방] 0.3.464~0.3.466 도 같은 경로였다 — 손으로 두 번 재번호했다
```

### 구멍 ② CI 가 도는 **6~8분 사이에 main 이 움직인다**

지금 `deploy.sh` 는 후보 가지로 밀기 **전에 한 번만** main 을 본다. CI 7잡이 도는
동안 다른 방이 main 에 닿으면 그 물림은 낡은 값이 된다.

```
[실측 2026-09-01 · 이 방] 한 배포에서 두 번 겪었다
  ① 후보 푸시 → CI 초록 → main 밀기 시도 → "main 이 또 움직였다"(0.3.460~463 도장)
  ② 합치고 다시 CI → 그 사이에 또
```

## 4. 처방 — 둘이면 된다

### 처방 A — 배포 경로를 **하나로** 모은다 (구멍 ①)

`main` 직접 푸시를 막고, 모든 배포가 `make deploy` 를 지나게 한다.

- **지금 당장 되는 것**: GitHub 의 `main` 브랜치 보호로 직접 푸시를 막는다. 그러면
  손으로 미는 길이 **기술적으로** 닫힌다. 규칙은 이미 글로 있었고(「배포 담당은 ANSEO
  방」), 글로만 있으면 바쁜 판에서 제일 먼저 밀린다는 것을 이 저장소가 두 번 겪었다.
- **권한이 막힌 방은**: 가지 이름을 대기 표에 적고 넘긴다 — 이미 정해진 규칙이다.

### 처방 B — main 에 밀기 **직전에** 다시 물린다 (구멍 ②)

`deploy.sh` 에 한 단계를 더한다. CI 초록을 받은 뒤, **main 에 밀기 직전에** main 판을
다시 읽는다.

```
지금:  main 읽기 → 물림 → 후보 푸시 → CI(6~8분) → main 밀기
바꿈:  main 읽기 → 물림 → 후보 푸시 → CI(6~8분) → main 다시 읽기
                                                  → 움직였으면 물림 한 번 더 → CI 재확인 → main 밀기
```

물림이 한 번 더 일어나면 CI 를 다시 받아야 한다(판 파일이 바뀌므로). 그 비용이 아까우면
**밀기 직전 검사만** 두고 사람에게 알리는 것으로도 족하다 — 지금은 `git push` 가 거부되어
무슨 일인지 알아내는 데 시간이 든다.

## 5. 안 할 것 — 그리고 왜

| 방법 | 왜 안 하나 |
|---|---|
| 방마다 번호 구간 예약(x00~x33 / x34~x66 …) | **이미 해 봤고 샜다.** 0.3.540 을 미리 잡고 비워 뒀는데 닿기 전에 집혔다. 구간이 마르면 같은 문제가 돌아오고, changelog 가 내림차순이 아니게 된다 |
| 판 번호를 날짜·연번으로 바꾸기 | 화면·리포트·계약·도장 기록이 전부 `0.3.x` 를 쓴다. 바꾸면 지난 기록과 끊긴다 |
| 겹침을 CI 관문으로만 잡기 | 감지는 되지만 **해결은 사람 손**이다. 오늘 두 번 그렇게 손으로 풀었다 — 자동으로 물리는 길이 이미 있는데 관문만 세우는 것은 뒤로 가는 것이다 |

## 6. 한 줄 요약

> **이미 «나갈 때 정한다»로 풀려 있다. 남은 일은 그 길을 지나지 않고 나가는 두
> 경우를 닫는 것뿐이다 — 손으로 main 밀기(A) · CI 도는 사이의 움직임(B).**
