# 판 번호 충돌 — 왜 나고, 무엇이 이미 막고 있고, 어디가 뚫려 있나

> 사장님 오더(2026-09-19): «판 번호 충돌 방지 방법 정리해줘».
>
> **먼저 밝힐 것**: 이 저장소에는 **이미 막는 장치가 있다.** 새 방법을 지어내기 전에
> 있는 것부터 읽었다. 남은 것은 «방법이 없다»가 아니라 «있는 길을 안 타는 자리»다.

## 1. 왜 나나

방이 셋인데 **서로 직접 말을 못 한다**(사장님이 전달자). 각 방이 일을 시작할 때 판
번호를 잡으면, 그 번호는 main 에 닿을 때까지 남의 것이 될 수 있다.

```
[실측 2026-09-07~08 · scripts/claim_version.py 머리말] 이틀에 열한 번 부딪혔다
  0.3.531~0.3.536 · 0.3.540 두 번 · 0.3.541 · 0.3.542 · 0.3.543 두 번 · 0.3.545
[실측 2026-09-01 · 이 방] 하루에 두 번
  0.3.455(ANSEO 방과) · 0.3.460~0.3.463(특허 이식 방과)
```

**앞질러 잡는 것은 이미 해 봤고 안 통했다.** 0.3.540 을 미리 잡고 537~539 를 비워
두었는데 닿기 전에 집혔다. 구간을 나눠 예약하는 방식도 같은 이유로 샌다 — 번호는
**main 에 먼저 닿는 쪽이 갖기** 때문이다.

## 2. 이미 막고 있는 것

| 무엇 | 어디 | 하는 일 |
|---|---|---|
| **판을 나갈 때 정한다** | `scripts/deploy.sh` (295~318줄) | main 판을 읽어 내 판이 막혔으면 **main+1 로 물린 뒤** 후보 가지로 민다 |
| 기계가 고치는 네 곳 | `make bump-version` | 판 · 계약 · 생성 클라이언트 · 계약 관문 |
| **사람이 쓴 글 세 곳** | `scripts/claim_version.py` | `changelog.ts` 맨 위 항목 · `WORKLIST.md` 머리말과 대기 표의 내 줄 · `WORKLIST-HISTORY.md` 그 판의 절 제목 |
| 통째 치환 금지 | 같은 파일 | 옛 판 번호는 **그때의 진실**이라 자리를 하나씩 짚어 바꾸고, 못 찾으면 조용히 넘어가지 않고 **선다** |

**~~즉 `make deploy` 로 나가면 충돌은 구조적으로 안 난다.~~**

> **2026-09-19 정정 — 이 문장은 틀렸다.** 이 방은 이날 **정문으로만** 다녔는데
> **아홉 번** 겹쳤다. 물림 단계가 있어도 **번호가 굳는 시각**이 이르면 소용이 없다.
> 아래 «구멍 ③» 이 그 자리다.

## 3. 그런데도 또 겹친 이유 — 구멍 둘

### 구멍 ① `make deploy` 를 **안 타는 배포 경로**가 있다

`git push origin <sha>:main` 으로 손으로 미는 길이다. 그 경로에는 물림 단계가 없다.

```
[실측 2026-09-11 · WORKLIST.md 693줄] GEO 진단기 세 건
  "이 방은 make deploy 권한이 막혀, 후보 가지에서 CI 초록을 받은 뒤 그 커밋을
   손으로 main 에 올렸다. 그 경로에는 claim_version 이 없다."
  → 다른 방이 잡아 둔 0.3.563 안에 얹혀 나갔다
[실측 2026-09-01 · 이 방] 0.3.464~0.3.466 도 같은 경로였다 — 손으로 두 번 재번호했다
```

### 구멍 ② CI 가 도는 **6~8분 사이에 main 이 움직인다**

지금 `deploy.sh` 는 후보 가지로 밀기 **전에 한 번만** main 을 본다. CI 7잡이 도는
동안 다른 방이 main 에 닿으면 그 물림은 낡은 값이 된다.

```
[실측 2026-09-01 · 이 방] 한 배포에서 두 번 겪었다
  ① 후보 푸시 → CI 초록 → main 밀기 시도 → "main 이 또 움직였다"(0.3.460~463 도장)
  ② 합치고 다시 CI → 그 사이에 또
```


### 구멍 ③ 물림을 **건너뛰는 분기**가 있다 — 그리고 진짜 값은 「번호가 굳는 시각」

`[1/4]` 의 판단은 이랬다.

```
HERE_V > MAIN_V  →  "물릴 것 없습니다"      ← 건너뛴다
HERE_V ≤ MAIN_V  →  MAIN_V+1 로 물린다
```

첫 줄이 **«앞질러 잡기» 를 되살린다** — §1 이 「이미 해 봤고 안 통했다」고 적어 둔 그것이다.
앞선 시도에서 잡았다 물러난 번호는 **그때의 main** 기준이라 이미 낡았는데, 그 줄이
그대로 통과시킨다.

**그런데 더 큰 값은 다른 데 있다.** 판을 손으로 미리 박아 두면 이 분기가 매번 첫 줄로
빠져, **번호가 점검(15분)이 시작되기도 전에 확정된다.** 겹칠 확률은 「번호가 굳은 뒤
main 에 닿기까지의 시간」으로 정해지므로, 이 창이 두 배가 되면 확률도 따라 뛴다.

```
번호가 굳는 시각 ─────────────────────────────── main 에 닿는 시각
                        이 사이에 남이 닿으면 내 번호가 낡는다

설계대로:   [1/4] 물림 ──── CI 9분 ──── main        노출  9분
미리 박으면: 손으로 박음 ── 점검 15분 ── CI 9분 ── main   노출 24분
```

[실측 2026-09-19 06:00~08:14] main 도착 간격 **평균 19.1분**(7번 관측).

| 방식 | 노출창 | 겹칠 확률 | 평균 시도 | 예상 총시간 |
|---|---:|---:|---:|---:|
| 미리 박기(구멍 ③) | 24분 | **71%** | 3.5회 | 91분 |
| 나갈 때 정하기 | 9분 | **38%** | 1.6회 | 42분 |

이 방은 0.3.620 부터 여섯 번 시도해 **다섯 번 물러났다** — 표의 「평균 시도」와 맞는다.
**운이 아니라 확률을 두 배로 만들어 놓고 들어간 것**이다.

### 처방 D — 규칙을 하나로 줄인다 (구멍 ③)

`version_to_claim` 이 **언제나 main+1** 을 찍는다. 건너뛰는 분기를 없앤다.

```
이미 main+1 이면    → 바꿀 것 없다
뒤처져 있으면       → 올린다
손으로 높게 박았으면 → **끌어내린다**    ← 오늘 아홉 번을 만든 자리
main 을 못 읽으면   → 건드리지 않는다
```

검사: `test_deploy_always_claims_from_main.py` 8건. 옛 판단을 되살려 **3건이 빨개지는
것까지 확인**했다 — 시험이 실제로 무언가를 잰다는 증거다.

**남는 몫은 있다.** CI 9분 창은 못 줄인다(확률 38%). 그러나 그것은 **구조상 남는 것**이고,
앞의 24분은 **안 만들어도 되는 것**이었다. 두 가지를 같은 「겹침」으로 뭉뚱그리면 고칠
자리를 못 찾는다.

### 더 줄이려면 — 안 한 것과 그 까닭

| 방법 | 효과 | 왜 지금은 안 하나 |
|---|---|---|
| **[0/4] 를 줄 세우기로** — 남이 채점 중이면 기다린다 | 정문끼리는 겹침 ≈ 0 | 방들이 줄을 서야 한다. 쪽문(구멍 ①)으로 나가는 판은 여전히 샌다 |
| **CI 뒤에 다시 물리고 그대로 밀기** | 노출 몇 초 | **금기다**(오류 135) — CI 가 채점한 커밋과 다른 것이 나간다 |
| **판 번호를 커밋에서 빼기** (나갈 때 찍기) | 겹침 원천 소멸 | 여섯 자리 관례와 도구를 통째로 바꿔야 한다. 값은 크지만 판을 따로 잡아야 한다 |

## 4. 처방 — 셋이면 된다

### 처방 A — ~~`main` 보호를 켠다~~ → **취소. 그럴 필요가 없었다** (구멍 ①)

**2026-09-19 정정.** 처음에 「GitHub 에서 `main` 직접 반영을 막으면 된다」고 적었다.
확인해 보니 **두 가지 면에서 틀렸다.**

1. **기능이 막혀 있다.** 이 저장소는 비공개 + 무료라 GitHub 이 거절한다 —
   *"Upgrade to GitHub Pro or make this repository public"* (`gh api .../rulesets` 403).
2. **막으면 정문까지 막힌다.** `deploy.sh` 도 `git push "$SHA:refs/heads/main"` 으로
   똑같이 올린다. 문을 잠그면 배포가 통째로 선다.

**그런데 확인하다 더 나은 것을 찾았다 — 쪽문을 쓸 이유가 애초에 없다.**

대장에 「이 방은 `make deploy` 권한이 막혀」라고 적혀 있었지만, [실측 2026-09-19]
`make preflight` 를 돌려 보니 **①나무 ②계약을 통과하고 ③관문까지 돈다**(9분 넘게 걸려
중간에 끊었다 — 느린 것이지 막힌 것이 아니다). 그리고 마지막 [5/5] 「운영에 닿았나」는
바깥길이 막혀도 **「못 쟀습니다」로 적고 넘어간다. 배포를 죽이지 않는다**(소스 주석이
직접 「둘 다 죽을 일이 아니다」라고 적어 두었다).

**즉 쪽문을 쓴 이유는 권한이 아니라 「정문을 쓸 수 있다는 것을 몰라서」다.** 이 방이
2026-09-01 에 그랬고, 2026-09-11 의 그 방도 같은 오해였을 가능성이 크다.

→ **할 일은 설정이 아니라 「정문이 된다」는 사실을 못 박는 것**, 그리고 글이 밀릴 때를
대비해 **빈 기록을 찾아 주는 점검**이다(아래 처방 C).

### 처방 B — main 에 밀기 **직전에** 다시 물린다 (구멍 ②)

`deploy.sh` 에 한 단계를 더한다. CI 초록을 받은 뒤, **main 에 밀기 직전에** main 판을
다시 읽는다.

```
지금:  main 읽기 → 물림 → 후보 푸시 → CI(6~8분) → main 밀기
바꿈:  main 읽기 → 물림 → 후보 푸시 → CI(6~8분) → main 다시 읽기
                                                  → 움직였으면 물림 한 번 더 → CI 재확인 → main 밀기
```

물림이 한 번 더 일어나면 CI 를 다시 받아야 한다(판 파일이 바뀌므로). 그 비용이 아까우면
**밀기 직전 검사만** 두고 사람에게 알리는 것으로도 족하다 — 지금은 `git push` 가 거부되어
무슨 일인지 알아내는 데 시간이 든다.

### 처방 C — 빈 기록을 찾아 준다 (구멍 ① 의 실제 처방)

글로 적힌 규칙은 바쁜 판에서 제일 먼저 밀린다 — 이 저장소가 두 번 겪었다. 그래서
**나간 판 중 배포 오더 기록이 없는 것**을 기계가 세어 준다: `make audit-deploys`.

```
나간 판   = 변경 이력에 있는 판  −  대장 대기 표에 있는 판(아직 안 나간 것)
빈 기록   = 그중 DEPLOY-ORDER-LOG.md 에 한 번도 안 나오는 판
```

**CI 관문으로 세우지 않았다.** 한 오더로 여러 판이 나가기도 하고 옛 기록은 형식이
제각각이라, 관문으로 만들면 헛울린다 — 헛울리는 관문은 무시하게 만든다(대장 §
「못 재는 것은 못 잼이라고 적는다」와 같은 자리). 사람이 부를 때만 센다.

## 5. 안 할 것 — 그리고 왜

| 방법 | 왜 안 하나 |
|---|---|
| 방마다 번호 구간 예약(x00~x33 / x34~x66 …) | **이미 해 봤고 샜다.** 0.3.540 을 미리 잡고 비워 뒀는데 닿기 전에 집혔다. 구간이 마르면 같은 문제가 돌아오고, changelog 가 내림차순이 아니게 된다 |
| 판 번호를 날짜·연번으로 바꾸기 | 화면·리포트·계약·도장 기록이 전부 `0.3.x` 를 쓴다. 바꾸면 지난 기록과 끊긴다 |
| 겹침을 CI 관문으로만 잡기 | 감지는 되지만 **해결은 사람 손**이다. 오늘 두 번 그렇게 손으로 풀었다 — 자동으로 물리는 길이 이미 있는데 관문만 세우는 것은 뒤로 가는 것이다 |

## 6. 한 줄 요약

> **이미 «나갈 때 정한다»로 풀려 있다.**
>
> - **구멍 ②**(채점 도는 사이의 움직임) → 0.3.615 로 막았다.
> - **구멍 ①**(정문을 안 지나는 배포) → **설정으로 막을 일이 아니었다.** 정문은
>   이 방에서도 돈다. 할 일은 그 사실을 못 박고, 빠진 기록을 세어 주는 것뿐이다.
> - **구멍 ③**(물림을 건너뛰는 분기) → 0.3.627 로 막았다. **정문으로 다녀도 겹친다**는
>   것을 이날 아홉 번으로 배웠다. 핵심은 물림이 있느냐가 아니라 **번호가 언제 굳느냐**다.
>
> **판 번호에 손대지 마라.** 고쳐 주는 자리가 이미 있고, 손대면 그 자리가 꺼진다.

## 7. 나중에 배운 것 둘 (2026-09-19 밤)

### ① 「판 번호에 손대지 마라」는 **너무 넓었다**

§6 에 그렇게 적었으나 그대로 하면 배포가 선다. 관문이 하나 더 있다 —
`changelog-numbers-are-unique.test.ts`: **변경이력에 같은 판 번호가 둘이면 안 된다.**

main 을 합치면 main 의 항목이 내 나무로 들어온다. 그러니 이 방 항목이 main 과 같은
번호면 **그 순간 중복**이고, 점검에서 잡힌다.

```
맞는 규칙:  낼 직전에 main+1 로 맞춘다. 그리고 [1/4] 가 다시 검증하게 둔다.
틀린 것:    미리 박아 두고, 물러난 뒤 낡은 번호 그대로 다시 낸다.
```

앞서 겹친 여덟 번은 「번호를 박아서」가 아니라 **박아 둔 채 낡히고 재시도해서**였다.
0.3.628 의 `version_to_claim` 이 그 재검증이므로, main+1 로 맞춰 두어도 `[1/4]` 가
바로잡는다.

### ② 한 번 재고 「뒤처졌다」고 적지 않는다

[실측 2026-09-19 22:16 KST] 삼중 실측에서 **셋이 달랐다** — 진단 서버 0.3.628
(가동 9,655초) · 워커 0.3.629 · 웹 0.3.629. 「서버만 안 올라갔다」로 적을 자리였다.

**다시 쟀다**: 서버 가동 16초 → 26초, 판 0.3.629. **롤아웃 한복판을 잡은 것**이었다.

한 번 재고 적었으면 **없는 고장이 기록에 남고** 다음 사람이 그것을 쫓는다. 재시작
직후의 가동 시간이 그 증거다 — 값이 어긋나면 **가동 시간을 함께 본다.**

### ③ 내기 전에 «아직 필요한가»를 묻는다
