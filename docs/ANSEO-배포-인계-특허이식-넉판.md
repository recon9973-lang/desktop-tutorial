## 0-A. 그때의 기록 — **물리기·합치기는 끝났다 (2026-09-01)**

> **§2·§3 은 이미 실행했다.** 넉 판을 **0.3.460~0.3.463** 으로 물리고 main 을 합쳤다 —
> 가지 `claude/seo-geo-aeo-content-report-omspqb` 커밋 **`25d00feb`**.
> 합친 나무에서 전 관문을 다시 돌려 초록이다(§3 아래의 검증 줄과 같은 명령).
> **§5 부터 하면 된다.** §2·§3 은 그때 무엇을 왜 했는지의 기록으로 남긴다.
>
> 다만 main 이 또 움직였으면 §3 을 다시 한 번 돌린다 — 그때는 판 번호도 다시 본다.

### 그때 무엇이 겹쳤나

**이 넉 판은 그대로는 배포할 수 없었다.** 내가 작업하는 동안 다른 방이 main 에
0.3.456~0.3.459 를 먼저 올렸다.

```
[실측 2026-09-01]
  origin/main       f4b991e2 · __version__ = 0.3.459
  main 의 456~459   검수 화면 한글 · 목표선 이름표 · SEO·GEO 그림 배치 · 영역별 추이
                    (커밋 6b7880ba «ANSEO 방 0.3.455 를 합치고 이 방 네 판을
                     0.3.456~0.3.459 로 물린다»)

  이 방 가지        claude/seo-geo-aeo-content-report-omspqb · e51caa05
  이 방의 456~459   콘텐츠 탭 · 관문 C2·원장 · 환경 대조 · 두 판·부록
```

**같은 번호에 다른 내용이 둘 있다.** 이대로 합치면 changelog 가 한 판을 두 번 말하고,
`__version__` 과 화면이 서로 다른 판을 가리킨다. 그래서 §2 에서 **이 방 것을 뒤로
물린다**(0.3.460~0.3.463). 판 번호가 겹치는 것은 이 저장소에서 처음이 아니다 —
대장(§2)에 같은 사고가 세 번 적혀 있고, 매번 나중 것이 물러났다.

## 2. 판 번호 물리기 — ✅ 완료 (`25d00feb`)

고칠 자리는 **넷**이다. 커밋 메시지는 고치지 않는다(이력은 그때 그대로 둔다).

```
apps/api/src/veo/__init__.py        __version__ = "0.3.459" → "0.3.463"
apps/web/src/lib/changelog.ts       맨 앞 네 항목의 version 을 460~463 으로
apps/api/openapi.json               재발행 (아래 명령)
docs/WORKLIST.md §2                 미배포 목록의 「0.3.456~0.3.459」 → 「0.3.460~0.3.463」
docs/WORKLIST-HISTORY.md            이 방 항목 네 개의 판 번호
```

물린 뒤 **반드시** 계약을 다시 찍는다 — `__version__` 이 바뀌면 저장된
`openapi.json` 이 낡고, `check-contracts` 가 그것을 잡는다.

```bash
cd veo-platform
.venv/bin/python apps/api/scripts/export_openapi.py
pnpm --filter @veo/api-client generate
make check-contracts        # 5종 전부 「일치」여야 한다
```

> **왜 물리는 쪽이 이 방인가.** 저쪽이 먼저 main 에 닿았다. 나중 것이 물러나는 것이
> 이 저장소의 관례이고(대장 §2 의 세 사고 전부), 이미 나간 판을 되돌리면 운영이
> 흔들린다.

## 3. main 합치기 — ✅ 완료 (`25d00feb`)

main 은 내가 갈라진 뒤 움직였다(0.3.455 → 0.3.459). **합치고 나서** 배포한다.

```bash
cd veo-platform
git checkout claude/seo-geo-aeo-content-report-omspqb
git fetch origin main
git merge origin/main          # rebase 말고 merge — 남의 가지 이력을 다시 쓰지 않는다
```

부딪힐 만한 자리는 셋이고, 전부 §2 에서 이미 손대는 파일이다.

| 파일 | 왜 부딪히나 | 어떻게 |
| --- | --- | --- |
| `changelog.ts` | 양쪽이 맨 앞에 항목을 넣었다 | 저쪽 456~459 를 위에, 이 방 460~463 을 그 위에 — **번호 내림차순** |
| `__init__.py` | 양쪽이 `__version__` 을 올렸다 | `0.3.463` |
| `WORKLIST*.md` | 양쪽이 대장에 적었다 | 둘 다 남긴다 |

합친 뒤 **전 관문을 다시 돌린다.** 합치기 자체가 새 나무를 만들기 때문이다.

```bash
make ci-local                          # api·worker lint·typecheck·계약·DB 포함 전체
cd apps/web && pnpm verify             # typecheck·lint·test·build·smoke
```

## 4. 마이그레이션 — 자동으로 돈다

`railway.json` 의 `preDeployCommand` 가 `alembic upgrade head` 다. **새 판이 서비스를
시작하기 전에** 마이그레이션이 먼저 돈다 — 손으로 돌릴 것이 없다.
(이 불변은 시험이 지킨다: `tests/release/test_migrations_ship_with_the_image.py`
`test_railway_migrates_before_the_new_version_serves`.)

이번 마이그레이션은 **칸 하나를 더하는 것뿐**이고 기본값이 없다:

```
20260901published : counterfactual_experiments.published_at (timestamptz, NULL 허용)
```

- **되돌릴 수 있다.** `downgrade()` 가 칸을 지운다. 실 PostgreSQL 16 에서
  올리기·내리기·다시 올리기를 실측했고, DB 시험 245건(모델↔마이그레이션 드리프트 포함)
  통과했다.
- **지난 실험을 건드리지 않는다.** 기본값을 두지 않았으므로 기존 행은 전부 `NULL`
  (= 「아직 안 올림」)이다. 화면은 그 자리를 0 이나 「효과 없음」이 아니라 **못 잼**으로
  그린다.

## 5. 배포

### 5.1 먼저 — **나갈 나무에 서 있나**

[실측 2026-09-01] 이 자리에서 한 번 헛돌았다. 맥의 저장소는 `veo-platform` 이 아니라
**`~/Desktop/desktop-tutorial/veo`** 이고, 거기 로컬은 다른 가지(`work/…`)의 0.3.455 였다.
그대로 `make deploy` 를 돌려 CI 까지 통과했고, **main 밀기에서 non-fast-forward 로 거부**됐다
— 관문이 막아 준 것이지 통과한 것이 아니다.

```bash
cd ~/Desktop/desktop-tutorial/veo          # veo-platform 아님

git fetch origin
git switch claude/seo-geo-aeo-content-report-omspqb

git log --oneline -1                       # 25d00feb 여야 한다
grep __version__ apps/api/src/veo/__init__.py   # 0.3.463 이어야 한다
```

두 줄이 다르면 **거기서 멈춘다.** 「미배포 N 커밋 · main 0.3.4xx → 0.3.4yy」 의 뒤 숫자가
곧 지금 나무의 판이다 — 그것이 0.3.463 이 아니면 다른 것을 내보내는 것이다.

> **가지를 못 옮기면**(`Your local changes … would be overwritten`) 십중팔구
> `docs/DEPLOY-ORDER-LOG.md` 다. 배포가 시작될 때 오더 한 줄을 거기 적기 때문이고,
> 실패한 배포의 그 줄은 **버리는 것이 맞다**: `git checkout -- docs/DEPLOY-ORDER-LOG.md`.
>
> **붙여 넣을 명령에 `#` 주석을 섞지 않는다.** 맥 zsh 는 대화형에서 `#` 를 주석으로
> 읽지 않는 설정이 흔해 `command not found: #` 로 떨어진다 — 실제로 이 자리에서
> `git log --oneline -1 # 25d00feb` 가 통째로 실패했다. 확인값은 명령 **바깥**에 적는다.

### 5.2 배포

```bash
VEO_DEPLOY_ORDER="여기에 사장님이 실제로 쓰신 문장" make deploy
```

**꺾쇠는 자리 표시다 — 그대로 붙여 넣으면 안 된다.** `<사장님 배포 오더 원문>` 이 그대로
로그에 적히면 이 관문이 있는 이유가 사라진다(실제로 한 번 그렇게 적혔다). 요약도 짐작도
아닌, 사장님이 쓰신 그 문장이어야 한다.

**`VEO_DEPLOY_ORDER` 가 없으면 시작되지 않는다.** 「고쳐줘」·「진행해」 같은 코드 수정
오더는 배포 오더가 아니다. 넣은 문장은 `docs/DEPLOY-ORDER-LOG.md` 에 남는다.

`make deploy` 가 하는 일:

```
preflight  ① 나무가 깨끗한가 (미커밋 0)
           ② 서버·계약·생성 클라이언트가 같은 판인가
           ③ CI 가 돌리는 그 명령을, 나갈 바로 그 커밋에서 다시 돌린다
           ④ 리눅스에서만 터지는 것 (파일 이름 대소문자)
           ⑤ GitHub 잡이 뜰 수 있나 (지출 한도)
   ↓ 하나라도 빨간불이면 여기서 멈춘다
deploy     후보 가지(deploy-candidate)로 먼저 민다 — main 은 아직 안 건드린다
           CI 가 그 커밋을 채점할 때까지 기다린다 (3~4분, 20분 넘으면 실패로 본다)
           **초록불일 때만** 같은 커밋을 main 으로 민다
           운영 도달 확인: /api/health 의 판 · /api/queue 의 worker_versions
```

**하루 배포 상한**은 기본 2회다(무료 Actions 분을 지키는 관문). 상한 해제일이
`2026-09-01` 로 적혀 있어 오늘부터는 한 줄 알림만 남기고 통과한다. 그래도 막히면
`VEO_DEPLOY_LIMIT_PER_DAY=99 make deploy`.

> [실측 2026-09-02] 이번 배포에서 실제로 그 알림이 떴다 — *"배포 상한 기간(2026-09-01)이
> 지났습니다 — 세지 않습니다."* **지금은 상한 없이 나간다.** 다시 둘지는 돈 판단이라
> 대장 §5「사장님 몫」에 한 줄로 올려 두었다.

## 6. 배포 뒤 실측 — 셋을 따로 본다

`make deploy` 가 **진단 서버와 워커 둘**의 도달까지 확인하고 끝난다. **웹 번들은 확인
하지 않는다** — Vercel 이 따로 배포하므로 한 박자 늦을 수 있다. 그래서 셋째는 손으로 본다.

```bash
curl -s https://veo-platform-production.up.railway.app/api/health | grep -o '"version":"[^"]*"'
curl -s https://veo-platform-production.up.railway.app/api/queue  | grep -o 'worker_versions[^}]*'
# 웹은 로그인 후 계정 메뉴의 판 표시 또는 변경 이력 화면에서 0.3.463 확인
```

셋 다 `0.3.463` 이면 마감이다. 대장 §2 에 **삼중 실측 도장**을 한 줄 남긴다
(형식은 그 문단의 앞선 줄들과 같게).

> **✅ 이 회차는 마쳤다** — [실측 2026-09-02 01:38 KST] 서버·워커·웹 셋 다 `0.3.463`.
> 워커 1대·뒤처진 워커 0. 도장은 `docs/WORKLIST.md` §2 와 `WORKLIST-HISTORY.md` 넉 절에.
>
> 이 방 프록시는 운영 주소를 403 으로 막는다. 그래서 실측은 **바깥 샌드박스 curl** 로
> 우회했다(RESUME 의 도구 메모와 같은 길). 맥에서는 위 명령이 그대로 돈다.

화면에서 눈으로 볼 것 넷:

1. 거래처 상단 탭이 **일곱** — 진단 · SEO · GEO · AEO · **콘텐츠** · 이슈 · 리포트
2. 콘텐츠 탭 머리에 **특허출원중** 칩, 그 아래 기여도 실험 절
3. 실험 하나를 열어 **「어떻게 쟀는지 보기」**가 펴지는지
4. 리포트 한 판을 열어 맨 아래 **「다시 세우려면 — 측정 방법」**

## 7. 되돌리기

CI 가 빨간불이면 main 은 **애초에 안 밀린다** — 운영은 옛 판을 계속 서비스한다.
나간 뒤에 되돌려야 하면:

```bash
git revert --no-commit <이 넉 판의 커밋들>   # 새 커밋으로 되돌린다, 이력은 안 지운다
VEO_DEPLOY_ORDER="<되돌리라는 사장님 문장>" make deploy
```

**마이그레이션은 되돌리지 않아도 된다.** 칸 하나가 남아 있을 뿐이고, 옛 코드는 그
칸을 읽지 않는다. 굳이 지우려면 `make migrate-down` 이지만, **먼저 되돌린 판이 운영에
도달한 것을 확인한 뒤**에 한다 — 순서가 바뀌면 새 코드가 없는 칸을 읽는다.

## 8. 이 판들이 안 하는 것 (배포해도 안 바뀌는 것)

- **자동 발행 없음.** 콘텐츠 탭은 원고를 대신 올리지 않는다.
- **실험이 저절로 돌지 않는다.** 월 예산 상한이 **0(기본)** 이라, 올리기 전까지 실행
  창구는 언제나 거절한다 — 배포만으로 돈이 나가지 않는다.
- **「올렸습니다」는 사람이 누른다.** 누르기 전에는 환경 대조가 「아직 못 잼」이다.
- **특허 번호는 어디에도 없다.** 「특허출원중」 문구만이고, 「특허등록」이라 말하지
  않는다 — 출원과 등록은 다른 사실이다.
