## 2. 기술 스택

| 계층 | 선택 | 비고 |
|---|---|---|
| 백엔드 | **FastAPI**(Python 3.14) | ASGI, `uvicorn --proxy-headers` |
| ORM/마이그레이션 | **SQLAlchemy 2.x** + **Alembic** | `postgresql+psycopg`(psycopg3) 드라이버 |
| DB | **PostgreSQL**(Neon 매니지드) | 60개 테이블 |
| 작업 큐 | **Celery** + **Redis** | 브로커 없으면 API 프로세스 배경 스레드로 폴백(개발용) |
| 프론트엔드 | **Next.js**(App Router) + **TypeScript** | `output: "standalone"` |
| 패키지 매니저 | **pnpm**(workspace) | `packageManager: pnpm@10.0.0`, Node ≥20 |
| API 계약 | **OpenAPI**(FastAPI 자동 생성) → TS 클라이언트 생성 | drift 검사 있음 |
| 인증 | JWT(access/refresh) + httpOnly 쿠키 | 자체 구현, 서드파티 Auth 서비스 없음 |
| 암호화 | AES-256-GCM(표준 라이브러리 구현, `cryptography` 있으면 우선) | 자격증명 전용 |
| 컨테이너 | Docker(멀티스테이지, 비루트 실행) | Railway가 `DOCKERFILE` 빌더로 직접 빌드 |
| CI | **GitHub Actions** | `deploy-candidate`·PR에서만 실행, `main`은 제외 |
| 배포 | Vercel(웹) · Railway(API+워커+Redis) · Neon(DB) | `make deploy` 스크립트가 전체 관문 |

## 3. 테스트·품질 관문 (`Makefile`)

```makefile
make setup            # 로컬 환경 준비
make test-api         # FastAPI 테스트(pytest) — 골든 케이스 포함
make test-worker       # Celery 워커 테스트
make lint-api / lint-worker       # ruff 등
make typecheck-api / typecheck-worker
make test-contract     # OpenAPI 계약 drift 검사
make check-contracts    # 명세-발행표 등 각종 계약 정합성
make test-all           # DB 초기화 + 전체 테스트
make ci-local           # lint+typecheck+check-contracts+test-all — CI와 동일한 관문을 로컬에서
make preflight          # 배포 직전 전체 재확인
make deploy             # preflight → deploy-candidate 푸시 → CI 대기 → main 반영
make db-test-create / -reset / -drop
make migrate / migrate-down / migrate-history / migrate-revision
make smoke-web          # 빌드물을 띄워 콘솔이 실제로 뜨는지(비번 안 씀, 운영 안 닿음)
make providers          # 외부 제공자 연결 상태 표(값은 절대 출력 안 함)
make import-credentials # 다른 프로젝트 .env에서 제공자 키 임포트(값 미출력)
```

## 6. 재구현 시 체크리스트

- [ ] 백엔드를 "화면 단위"가 아니라 "도메인 단위"(라우터=패키지 1:1)로 나눌 것 —
      한 화면이 여러 도메인 데이터를 합쳐 보여줘도 백엔드 경계는 도메인을 따른다.
- [ ] CI 트리거에서 `main`을 빼고 후보 브랜치+PR에만 걸 것(무료 플랜에서 분 절약).
      단, 이 경우 `main`으로 가는 유일한 길이 검증된 배포 스크립트뿐이어야 한다.
- [ ] "메뉴에서 안 보이는 화면 = 죽은 화면인지"를 검사하는 테스트를 처음부터 둘 것.
- [ ] 개발/이미지/CI 세 곳의 런타임 버전(Python/Node)이 일치하는지 자동 대조하는
      테스트를 둘 것 — 안 그러면 "아무도 안 쓰는 버전에서 관문이 도는" 상태를
      아무도 알아채지 못한다.
- [ ] 브랜치 보호가 비공개+무료 플랜에서 실질적으로 무력하다는 것을 전제하고,
      관문을 깃허브 설정이 아니라 배포 스크립트 자체에 코드로 둘 것.
