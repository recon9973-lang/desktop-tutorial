# 저장 방식 — DB 스키마 · 자격증명 볼트 · 답변 원문 · 채점 명세

## 1. 기본 원칙 — "저장은 코드가 아니라 데이터가 결정한다"

이 프로젝트에서 "저장 방식"은 세 갈래로 완전히 분리돼 있고, 이 분리 자체가 설계
결정이다.

```
① 일반 데이터        Postgres(Neon) 60개 테이블 — SQLAlchemy ORM + Alembic 마이그레이션
② 채점 규칙(명세)    packages/scoring-specs/ 의 YAML 파일 — 코드가 아니다(ADR 0001)
③ 자격증명(API 키)   Postgres 안에 있지만 AES-256-GCM으로 암호화된 컬럼 — 절대 평문 저장 안 함
④ AI 답변 원문       기본은 Postgres(전용 테이블), 파일시스템 모드는 개발용 한정
```

## 3. 자격증명 볼트 — AES-256-GCM (`credentials/cipher.py`)

외부 API 키(`provider_credentials` 테이블)는 평문으로 저장되지 않는다. 설계의
핵심 3가지(코드 주석 원문 그대로, 재구현 시 그대로 지킬 것):

1. **AES-256-GCM, 쓸 때마다 새 96비트 난스(nonce)**. GCM은 인증형 암호라 변조된
   암호문은 "그럴듯한 쓰레기"로 복호화되지 않고 **큰 소리로 실패**한다.
2. **연관 데이터(AAD)가 암호문을 그 행(row)에 결속시킨다** — 조직 ID·제공자·필드·
   키 버전을 AAD에 담아서, DB 유출·잘못된 복원·버그로 어느 암호문이 다른 조직의
   행으로 복사돼도 복호화가 안 된다.
3. **지문(fingerprint)은 평범한 SHA-256이 아니라 HMAC** — 고객 ID나 짧은 API 키를
   단순 해시하면 오프라인 사전 대입 공격이 가능해서, 반드시 키 있는 HMAC을 쓴다.

- 마스터 키는 `VEO_CREDENTIAL_ENCRYPTION_KEY`(base64 32바이트) 환경변수. 키 회전은
  `credential_key_version` + `credential_previous_encryption_keys`(옛 버전 키 목록,
  "버전:base64키" 형태) — 회전 시 **재암호화**하는 것이지 평문으로 되돌렸다가
  다시 암호화하는 경로는 없다.
- `cryptography` 패키지가 설치돼 있으면 그 하드닝된 백엔드를 자동으로 쓰고, 없으면
  표준 라이브러리만으로 구현한 AES-GCM으로 **바이트 단위로 동일한 출력**을 낸다 —
  즉 의존성 유무와 무관하게 항상 진짜 암호화이지, "설치 안 하면 가짜로 대충
  암호화한 척"하지 않는다.
- `assert_vault_startup_ready()` — 앱 기동 시 마스터 키가 없거나 형식이 틀리면
  **그 자리에서 기동을 거부**한다(운영에 조용히 평문 저장 모드로 뜨는 사고 방지).

## 4. AI 답변 원문 저장

```
observation_answer_store: "database" (기본) | "filesystem"(개발 전용)
observation_answer_store_root: "var/observations/answers"  (filesystem일 때만)
```

- **"database"가 기본값인 이유가 코드에 명시돼 있다**: "VEO가 보고하는 모든 언급·
  인용은 그것이 나온 답변으로 뒷받침된다. 답변을 잃으면 남는 것은 확인할 수 없는
  주장뿐이고, 그것은 측정이 아니다."
- `filesystem` 모드는 **재배포에서 살아남지 못한다**(컨테이너가 stateless이므로) —
  운영에서 이 값을 바꾸면 다음 배포 때 모든 근거 원문이 사라지고, 남은 `ai_answers`
  행은 가리킬 대상이 없는 해시만 남는다. 개발 장비 전용으로만 써야 한다.
- 운영의 정답은 객체 저장소(S3 호환)이지만 **그 어댑터는 아직 없다** — 지금은
  파일시스템/DB 두 프로토콜만 있고, 프로토콜이 같아서 나중에 바꾸는 건 생성자
  인자 하나로 가능하게 설계돼 있다.

## 5. 채점 명세 — YAML, 코드가 아니다 (ADR 0001)

```
packages/scoring-specs/
  veo.seo.readiness/  v1.10.0 (2026-08-12 발행) — 영역 9개(채점 6개), 검사 59개, 분모 100.0
  veo.geo.readiness/  v1.4.0  (2026-08-11 발행) — 영역 7개(채점 6개), 검사 37개, 분모 100.0
  golden/             결정적 회귀 테스트용 골든 픽스처
```

- 배점·심각도·상한·게이트·구간을 **전부 이 YAML 안에** 둔다. "숫자를 바꾼다"는
  행위는 코드 배포가 아니라 **새 버전 YAML을 발행**하는 것이다.
- **버전·체크섬이 항상 함께 다닌다** — 모든 점수 결과 레코드에
  `scoring_spec_id` + `version` + `checksum`이 붙어서, "이 점수가 왜 이렇게 나왔나"에
  항상 답할 수 있다(같은 입력+같은 명세로 재계산하면 같은 점수가 나와야 함 —
  결정론적 evaluator).
- **발행된 방법론은 불변**(ADR 0012) — 한번 발행된 버전의 배점을 나중에 조용히
  고치지 않는다. 지난 리포트가 "그때 규칙"으로 항상 설명 가능해야 하기 때문.
- 관문(gate): `test_published_specs_say_why.py`가 **발행본 전부**를 검사한다 —
  ① 판마다 무엇을 왜 바꿨는지 요약이 있는가 ② 결과를 움직였으면 근거(ADR 인용·
  실측·지시 인용)를 댔는가 ③ "숫자는 안 바꿨다"는 주장을 앞 판 YAML과 실제로
  대조. 이 관문이 생기기 전에는 코드 파일의 상수 8개만 검사해서, 실제로 v0.3.125가
  점수 상한 5개를 조용히 없앴는데도 관문을 통과한 사고가 있었다.

## 6. 모델 가격/우선순위/능력 표 — 이것도 데이터다

```
packages/model-prices/         날짜가 붙은 모델별 단가표 (통화·모델·시각당 버전)
packages/model-priorities/     "엔진:auto" 선택 시 쓸 우선순위 표
packages/model-capabilities/   엔진별로 어떤 모델이 인용을 반환하는지 등 능력 표
```

세 표 모두 배포 이미지에 반드시 함께 COPY되어야 하는 데이터다(05번 문서 §5) —
셋 중 하나라도 빠지면 "배포는 성공, 관측만 조용히 0건"이라는 같은 패턴의 사고가
세 번 반복됐다.

## 7. 재구현 시 체크리스트

- [ ] "코드가 아니라 데이터"로 둘 것: 배점·가격·우선순위·능력표. 이 넷을 코드
      상수로 박으면 나중에 "숫자를 바꾸려면 배포해야 하는" 구조가 되고, 배포마다
      회귀 위험이 커진다.
- [ ] 자격증명은 처음부터 AES-GCM(또는 동급) + 행 단위 AAD 바인딩 + HMAC 지문으로
      설계할 것 — "일단 평문으로 넣고 나중에 암호화"는 마이그레이션 비용이 크다.
- [ ] `NULL`/`0`/`UNKNOWN`을 하나의 열거형으로 명시적으로 구분해서 저장할 것.
      나중에 이 셋을 구분하려면 스키마 변경 + 과거 데이터 백필이 필요해진다.
- [ ] "답변 원문 없이는 인용/언급을 주장하지 않는다"처럼, 각 측정값이 **그 근거
      원문을 반드시 함께 저장**하도록 스키마 단계에서 강제할 것(nullable로 두면
      언젠가 비게 된다).
- [ ] 명세/가격표처럼 자주 바뀌는 숫자 뭉치는 처음부터 "버전 + 체크섬 + 발행일 +
      변경 이유"를 갖는 포맷으로 설계할 것.
