# 인프라 · 배포 — Neon · Vercel · Railway · (Supabase는 안 씀)

## 0. 먼저 정정 — Supabase는 실제로 쓰지 않는다

사용자 요청에 "supanoba"(오타, supabase로 추정)가 있어 확인했다: **이 프로젝트는
Supabase를 운영 DB로 쓰지 않는다.** 실제 프로덕션 DB는 **Neon**이다. Supabase는
딱 한 곳, `apps/api/src/veo/db/session.py`의 `normalized_database_url()` 함수 주석에
"Neon·Railway·Supabase가 복사 단추로 주는 접두사들(`postgresql://`, `postgres://`)이
전부 같은 모양이라 드라이버 접두사(`postgresql+psycopg://`)를 자동으로 붙여준다"는
**호환성 언급**으로만 등장한다 — 즉 "이 URL 정규화 함수는 Supabase에서 복사한
연결 문자열을 붙여넣어도 동작한다"는 뜻이지, Supabase 프로젝트가 실제로 존재하는
것은 아니다. 재구현 시 Supabase를 쓰고 싶다면 이 정규화 함수 덕분에 **연결 문자열만
바꾸면 그대로 붙는다**(같은 Postgres 프로토콜이므로) — 하지만 지금 구조상 그럴
이유가 없다(아래 §1 리전 이유 참고).

## 1. 3사 배치와 리전 — "어느 하나만 옮기면 오히려 느려진다"

출처: `docs/operations/hosting-regions.md` (veo-platform).

| 조각 | 서비스 | 리전 | 이유 |
|---|---|---|---|
| DB | **Neon** (PostgreSQL) | `ap-southeast-1` 싱가포르 | 자매 프로젝트(FlowLens)와 같은 Neon 계정을 공유해서 시작한 리전 그대로 |
| API | **Railway** | `asia-southeast1` 싱가포르 | **DB 바로 옆.** API 요청 1개가 DB 질의를 여러 번 하므로 이 두 개가 가장 가까워야 함 |
| 콘솔(웹) | **Vercel** | `icn1` 서울 | 실제 사용자(VENOM 직원) 바로 옆. 콘솔→API 사이는 한 번만 태평양을 건넘 |

**실측(2026-07-29, 개선 전 — Vercel `iad1` 미국 동부·Railway 미국·Neon 싱가포르)**:

```
GET  /api/health          (DB 안 씀)   0.21초
POST /api/auth/login      (DB 씀)      1.8~2.5초
```

화면 렌더링 자체는 0.3초로 빨랐고, 느린 건 전부 DB 왕복이었다 — 탭을 누를 때마다
콘솔이 세션을 API에 되묻고, API가 그 답을 태평양 건너 싱가포르에서 가져왔기 때문.
**교훈**: 리전을 옮길 땐 "한 요청이 DB를 몇 번 부르는가"부터 재야 한다. Railway를
그대로 두고 Vercel만 서울로 옮기면(실제로 이 순서로 했었다면) 오히려 느려졌을
것이다 — 그때는 Vercel-Railway 구간이 같은 대륙(미국)이라 공짜였는데, 콘솔만 빼면
그 구간이 태평양이 된다. 그래서 **DB-API를 먼저 붙이고, 그다음 사용자-콘솔을
붙이는 순서**로 옮겼다.

## 4. Neon 연결 세부사항 (재구현 시 실수하기 쉬운 지점들)

1. **드라이버 접두사 자동 보정**(`db/session.py`) — Neon 콘솔의 "복사" 버튼은
   `postgresql://...`를 주는데, SQLAlchemy는 이걸 보면 (설치돼 있지 않은) `psycopg2`를
   찾아서 실패한다. 증상이 "비밀번호가 틀렸다"처럼 보여서 실제로 시간을 허비한 적이
   있었다(2026-08-17). 그래서 `normalized_database_url()`이 `postgresql://`/`postgres://`
   를 `postgresql+psycopg://`로 자동 치환한다.
2. **IPv4 강제 연결**(`db/ipv4.py`) — 일부 호스트명이 IPv6로만 풀려서 나가는 길이
   없어 연결 실패한 사고가 배포 중 두 번 있었다. 이름을 IPv6로 강제할 수 없는
   환경에서는 `connect_args`를 비워 예전과 동일하게 동작.
3. **연결 풀 상한을 명시적으로 건다** — 이 Neon 프로젝트는 **최대 연결 112개를
   VEO·FlowLens·실제 영업용 ERP(neondb) 세 제품이 나눠 쓴다.** SQLAlchemy 기본값
   (pool_size 5 + max_overflow 10 = 프로세스당 15개)을 그대로 두면 VEO가 뜨는
   순간 사용량이 5~20배로 뛰고, **VEO가 연결을 다 먹으면 ERP(실제 영업)가 먼저
   죽는다.** 그래서 `db_pool_size=5`, `db_max_overflow=5`로 명시(설정값, 코드 상수
   아님 — 필요시 늘릴 근거를 남길 수 있게).
4. **연결 재활용 900초** — Neon이 유휴 연결을 스스로 끊는데, 끊긴 걸 모르고 쓰면
   첫 질의가 실패한다. `pool_pre_ping=True`가 대부분 잡아주지만 왕복이 한 번 더
   드므로 재활용 주기도 함께 짧게 둔다.
5. 사전배포 명령(`preDeployCommand`)이 **`alembic upgrade head`** — 새 코드가
   뜨기 전에 마이그레이션이 먼저 실행됨.

## 5. 컨테이너 이미지 (`infra/docker/*.Dockerfile`)

### API (`api.Dockerfile`)
- 2단계 빌드: `python:3.14-slim` 빌더(빌드 도구 포함) → 런타임(가상환경만 복사).
- 비루트 실행(uid/gid `10001`), `EXPOSE 8000`.
- **비밀값을 이미지에 굽지 않는다** — 전부 런타임 환경변수 주입.
- **런타임에 필요한 데이터 폴더 전부를 이미지에 명시적으로 COPY** — 이게 세 번
  사고가 난 자리다: 채점 명세(`packages/scoring-specs`), 모델 우선순위표
  (`packages/model-priorities`), 모델 능력표(`packages/model-capabilities`), 모델
  가격표(`packages/model-prices`), 심평원 정리본(`apps/api/data`), 마이그레이션
  파일(`apps/api/alembic`). **매번 "배포는 성공했는데 화면만 조용히 틀리게" 나왔다**
  (예: 모델 목록이 비어서 진단 화면에 "사용 가능한 AI 엔진 0개"). 지금은
  `test_image_carries_every_package_the_code_looks_for` 테스트가 코드가 참조하는
  `packages/*` 전부를 이미지 COPY 목록과 자동 대조한다 — **재구현 시 이 종류의
  테스트를 반드시 가져갈 것.** "필요한 파일을 안 넣었는데 배포는 성공한다"는
  이 아키텍처(런타임에 venv로 설치되어 소스 경로 기준 상대경로 추론이 깨짐) 자체의
  구조적 위험이라 사람이 매번 기억하는 방식으로는 못 막는다.
- 포트는 플랫폼이 주입하는 `PORT` 환경변수를 우선하고 없으면 `VEO_API_PORT`(기본
  8000)로 폴백 — Railway/Render류가 `PORT`를 주입하므로, 헬스체크가 다른 포트를
  보면 "배포는 되는데 계속 재시작"하는 증상이 났었다.

### 웹(`web.Dockerfile`)
- `node:22-alpine` 3단계: deps → build(standalone 출력) → runtime.
- Next.js `output: "standalone"` 전제 — `.next/standalone`만 추려서 담는다.
- **`NEXT_PUBLIC_*`는 빌드 시점에 클라이언트 번들에 그대로 박힌다** — 서버 전용
  비밀값은 `ARG`로 받지 않고 런타임 `ENV`로만 주입(빌드 인자 히스토리에 남지 않게).
- 비루트 실행(uid/gid `10001`), `PORT=3000`.

### 워커(`worker.Dockerfile`)
Celery 워커 이미지 — Redis를 브로커로 씀, concurrency 4.

## 6. 배포 파이프라인 — `make deploy` 하나뿐

핵심 스크립트: `scripts/deploy.sh`. 순서:

```
1. 지금 커밋(HEAD)을 잡는다
2. 후보 브랜치(deploy-candidate)로 민다 — main은 아직 안 건드림
3. CI(GitHub Actions)가 그 커밋을 채점할 때까지 기다림(타임아웃 1200초)
4. 초록불일 때만 같은 커밋을 main으로 민다 → main 자동배포(Vercel/Railway)
```

- **이 관문을 코드로 두는 이유**: 비공개 저장소 + 무료 GitHub 요금제에서는 브랜치
  보호 규칙이 **적용되지 않는다**(`gh api .../rules/branches/main` → 403, GitHub
  Pro 필요). 화면엔 "Active"로 보여도 실제로는 아무것도 안 막는다. 그래서 관문을
  사람의 기억이 아니라 배포 스크립트 자체에 박았다.
- **main에서 CI를 다시 안 돌린다** — 후보 브랜치에서 이미 초록불 받은 그 커밋
  SHA를 그대로 main에 올리므로, main에서 또 돌리는 건 "같은 답을 두 번 받는" 낭비.
  실제로 중복 실행이 GitHub Actions 무료 분(2,000분/월)을 8일 만에 다 쓴 사고가
  있었고(2,155분 중 1,500분이 중복), 그 뒤로 CI 트리거에서 `main`을 뺐다.
- **하루 배포 횟수 상한**(2026-08 한정, `VEO_DEPLOY_LIMIT_PER_DAY`, 기본 2회) —
  같은 이유(무료 Actions 분 절약)로 배포 스크립트 자체가 카운트하고 넘기면 막는다.
  2026-09-01부터 자동 해제.
- 사람이 `main`에 직접 푸시하는 것은 이 관문을 우회하는 일이라 아예 안 한다.
- 저장소 자체가 원래 `desktop-tutorial`의 하위 디렉터리였다가(`git subtree split`)
  특허 출원 대상이 되며 독립 비공개 저장소로 분리됐다(2026-08-10). **"옛 문서에
  나오는 `git subtree push`는 지금 동작하지 않는다."**

## 7. 로컬 개발 환경

```bash
python3 -m venv .venv
.venv/bin/pip install -e "apps/api[dev]"
createdb veo && createdb veo_test
cd apps/api && VEO_DATABASE_URL="postgresql+psycopg://localhost:5432/veo" \
  ../../.venv/bin/python -m alembic upgrade head
pnpm install
make ci-local     # lint+typecheck(api/worker)+계약검사+전체 테스트
```

Docker Compose(`docker-compose.yml` → `infra/docker/docker-compose.yml`)로 전체
스택(API+워커+웹+Redis+Postgres)을 띄우는 정의도 있으나, 개발 당시 장비에 Docker가
없어 **빌드 자체가 검증되지 않은 상태**로 저장소에 남아 있다 — 재구현 시 그대로
믿지 말고 처음부터 다시 검증할 것.

## 8. 재구현 시 체크리스트

- [ ] DB(Neon)-API(Railway) 리전을 먼저 맞추고, 그다음 사용자-콘솔(Vercel) 리전을
      맞출 것. 순서를 반대로 하면 중간에 더 느려지는 구간이 생긴다.
- [ ] Postgres 연결 문자열은 `postgresql://` 접두사를 그대로 받아들이되 드라이버
      접두사로 정규화하는 함수를 처음부터 둘 것(Neon/Railway/Supabase 어디서
      복사해도 동일).
- [ ] DB 풀 상한을 명시적으로 설정할 것 — 특히 DB를 다른 프로젝트와 공유한다면.
- [ ] 배포 이미지에 런타임이 참조하는 데이터/설정 폴더 전부가 들어갔는지 자동
      검증하는 테스트를 CI에 둘 것(사람이 기억하는 체크리스트로는 반드시 샌다).
- [ ] 브랜치 보호가 유료 플랜에서만 동작한다는 전제를 두지 말고, 배포 스크립트
      자체에 "그 커밋이 CI를 통과했는가"를 강제하는 관문을 둘 것.
