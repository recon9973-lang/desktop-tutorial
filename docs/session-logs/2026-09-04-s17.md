## 발견한 문제·결정사항

### 문제: SerpAPI 시간당 상한 오분류

`_says_out_of_searches()` 의 셋째 힌트 `"exceeded your searches"` 가 SerpAPI 의 시간당 상한 문구 *"You have exceeded your searches per hour rate limit."* 를 부분 문자열로 잡음. 파일 머리말 주석은 「시간당은 넣지 않는다」로 못박아 뒀는데 힌트 목록이 자기 규칙을 어긴 자리.

### 결정 1: 반증 힌트로 수정 (배포됨)

`_NOT_MONTHLY_QUOTA_HINTS = ("per hour", "hourly", "concurrent", "rate limit")` 를 두고 `_says_out_of_searches()` 가 반증 힌트를 먼저 봄. 하나라도 있으면 몫 소진 아님. 두 어댑터(네이버·구글)가 같은 함수를 공유하므로 한 자리 수정으로 둘 다 낫음.

### 결정 2: 자체 상한(레이트 리미터) 안 걸음

`RetryPolicy` (`providers/naver/errors.py:325-360`) 가 이미 exponential backoff + Retry-After 헤더 우선. 시간당 429 는 이제 `PROVIDER_RATE_LIMITED` (`retryable=True`) 로 가서 3회 재시도가 자연스레 부하를 다듬음. 하드코딩 상한은 등급 상향 시 걸림돌.

### 결정 3: 판 번호 충돌 규율 재확인

다른 방(입지 방 s15·s16)이 같은 하루에 두 번 밀며 판을 올렸음. 우리는 v0.3.499 를 잡으려다 다른 방과 충돌 → 물러남. 우리 fix 는 그 판에 자연스레 실려 나감 — 별도 판 상승 필요 없음.

## 이 세션에서 배운 것 (다음 세션이 겪지 말라)

- **오분류 힌트가 자기 주석 규칙을 어기는지** 늘 대조. 이번 자리는 주석이 「시간당은 넣지 않는다」 였는데 목록에 시간당을 잡는 힌트가 있었음
- **재시도 정책이 있다면 하드코딩 상한을 새로 추가하지 말 것.** SerpAPI 같은 유료 창구는 Retry-After 헤더를 준다. 그 값을 존중하는 게 우리 짐작보다 정확
- **툴팁이 정답 창구** — `recent_failure_reason_ko` 필드가 서버에서 실시간으로 매핑돼 나옴. 툴팁 문구를 그대로 옮기면 top_code 특정 가능
- **판 번호 충돌은 이제 흔한 일** — 여러 방이 같은 하루 여러 판을 미는 게 정상. 늦게 밀면 물러나되, 코드는 남의 판에 자연스레 실려 나감
- **veo-platform Python 3.12 필요** — pyproject 상한이 `>=3.12` 라, 시스템 기본 3.11 로 `make setup` 하면 실패. `PYTHON=python3.12 make setup` 로
