## 나간 판 셋

**0.3.541 — 자동 다시받기를 축마다 다르게.** 0.3.538 은 세 축에 같은 12·25·45초를 썼는데
축이 걸리는 시간은 자릿수가 다르다(상권 몇 초 · 인구 이동 수십 초 · 방문자 몇 분). 축마다
시간표를 두고 **받는 중인 축 가운데 가장 느린 쪽**의 것을 쓴다. 상권 3번 40초 · 인구 이동
4번 100초 · 방문자 5번 300초. 오래 걸리는 축은 까닭을 띠에 적는다.

**0.3.542 — 방문자를 「하루 몇 명」으로 읽게.** 사장님 지적이 옳았다. 다만 틀린 것은 숫자가
아니라 **자리**였다 — 관광공사의 달 값은 하루 순방문자를 달로 더한 **연인원**이라, 상주인구
17만인 마산합포구가 두 달 683만으로 나온다. 하루 112,075명이라는 뜻이다. 큰 숫자를 하루
평균(달 값 ÷ 날수 · **자른다**)으로 바꾸고 누계는 밑에 작게 남겼다. 좁은 화면에서 숫자가
「6,836,6 / 12」 로 끊기던 것(`overflow-wrap: anywhere`)도 같이 고쳤다.

**0.3.547 — 캡처가 잡아낸 두 가지.**

1. **상권 축은 한 번도 산 적이 없었다.** 0.3.534 로 붙인 뒤 늘 「아직 못 받았습니다」였다.
   실패 문장이 `no response object` 였는데, XML 이면 앞에서 「JSON 이 아니다」로 걸렸을 테니
   **JSON 인데 `response` 칸이 없다** = 소상공인 sdsc2 는 `header`/`body` 를 맨 위에 준다는
   뜻이었다. 0.3.534 는 HWP 활용가이드만 보고 만들었고 실호출을 못 재 봤다. 이제 두 꼴을 다
   받고, 어긋나면 **응답의 맨 위 칸 이름을 그대로 적어** 다음 사람이 한 번에 읽게 했다.
2. **방문자 마지막 막대가 폭락해 보였다**(다른 달 7만대 · 마지막 14,777). 며칠치만 온 달을
   달의 날수로 나눈 탓. **받은 날수**를 통로→`days` 열→계약→화면으로 끝까지 들고 가서 그
   날수로 나눈다. 덜 찬 달은 막대에 **「덜 참」**이라 적어 조용히 섞지 않는다. 옛 행에는 그
   날수가 없어 마이그레이션이 표를 비운다 — 다음에 열면 열두 달을 다시 받는다.

## 걸린 것 · 배운 것

- **판 물림 다섯 번**(0.3.540→543→544→545→546→547). 규칙대로 **먼저 main 에 닿은 쪽을 두고
  이 방이 물러났다.** 마지막 물림에서 rebase 가 중첩 충돌을 냈다 — 그때는 **rebase 를 접고**
  `git diff --name-only $BASE origin/main -- <우리 파일>` 로 main 이 우리 파일을 하나도 안
  건드렸음을 확인한 뒤, 새 가지를 main 에서 떠서 우리 파일만 `git checkout <sha> --` 로
  얹는 편이 깨끗했다. 문서는 새로 썼다.
- **내 실수**: rebase 중 일부만 풀고 `git add -A` 를 해서 충돌 표시(`<<<<<<<`)를 커밋에
  들여보냈다. `grep -rln '^<<<<<<< |^>>>>>>> '` 로 잡아 갈랐다. 이후 커밋 전 이 grep 을 돌린다.
- **PostgreSQL 이 두 번 죽어 있었다**(컨테이너 재시작 · OOM). `pg_ctlcluster 16 main start`.
  이건 시험 실패가 아니라 DB 가 안 뜬 것 — 그렇게 말하고 넘어갔다.
- `deploy.sh` 는 `VEO_DEPLOY_ORDER` 에 **사장님 문장 그대로**가 없으면 서지 않는다.
- 운영 API 는 `veo-platform-production.up.railway.app` 이다. `veo.seokorea.org/api/health` 는
  Next.js 화면을 돌려준다.
- ANSEO 방의 **문서만 바뀐 판**(0.3.545·0.3.546)이 번호를 하나씩 먹는다. 물림이 잦은 까닭의
  하나 — 「문서만 바뀐 판은 번호를 올리지 않는다」 는 규칙은 두 방이 같이 정할 일이라 남겨 뒀다.
