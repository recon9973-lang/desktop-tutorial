## 2. 무엇이 나가나 — 두 가지

### ① 배포가 **나가기 직전에** main 을 한 번 더 본다 (`scripts/deploy.sh`)

판을 물릴 때 읽은 main 은 **후보 가지로 올리기 전의** main 이다. 채점이 도는 6~8분
사이에 다른 방이 닿으면 그 물림이 낡고, 그 커밋은 더 이상 main 의 자손이 아니다.
지금까지는 그때 `git push` 가 **영어 한 줄로 거절**하고 끝나, 판 겹침인지 무엇인지
알아내는 데 시간이 들었다.

```
전:  main 읽기 → 판 물림 → 후보 가지 → CI(6~8분) → main 반영
후:  main 읽기 → 판 물림 → 후보 가지 → CI(6~8분) → main 다시 읽기 → 관문 → main 반영
```

바뀌었으면 이렇게 적고 **선다**(main 은 안 건드린다):

```
✗ CI 가 도는 사이에 main 이 움직였습니다. main 을 건드리지 않았습니다.
  이 커밋이 잡은 판: 0.3.620
  지금 main 의 판:   0.3.622 (a1b2c3d4)
  → 판 0.3.620 는 이미 집혔습니다. 다시 돌리면 그 자리에서 물립니다.

  다음 한 걸음:  git merge origin/main   그리고   make deploy
```

**저절로 합치지 않는다.** 합치다 부딪히면 어중간한 나무가 남는다 — 못 푸는 것을 푸는
척하지 않는다. 다시 `make deploy` 를 돌리면 판은 그 자리에서 새 main 기준으로 다시 물린다.

### ② 배포 기록에 **판 번호**를 남기고, 빠진 기록을 센다

지금까지 오더 기록은 `- 날짜 · sha · "오더"` 까지였다 — **어느 판이 이 오더로 나갔나가
없었다.** [실측 2026-09-19] 변경 이력 602 판 중 기록에 판이 나오는 것은 130개뿐이고,
그나마 사람이 본문에 덧붙인 것이다.

- `deploy.sh` 가 판 확정 뒤 그 줄 끝에 `· 판 0.3.xxx` 를 적는다
- `make audit-deploys` 가 **나간 판 중 기록이 빠진 것**을 센다
- **옛 줄은 「못 잼」으로 적고 넘어간다**(경계 `FIRST_MARKED = (0, 3, 615)`) — 그대로
  세면 472개가 「빔」으로 나와 아무것도 말하지 않는 숫자가 된다
- **관문으로 세우지 않았다** — 한 오더로 여러 판이 나가기도 해 헛울린다

## 3. 배포 절차 — 평소와 같다

```bash
cd veo-platform
git fetch origin claude/anseo-console-port
git checkout claude/anseo-console-port      # 또는 그 커밋으로
VEO_DEPLOY_ORDER="ANSEO 방에 배포 인계 넘겨" make deploy
```

`make deploy` 가 알아서 한다 — 판이 막혔으면 물리고, 후보 가지에서 CI 를 받고,
**나가기 직전에 main 을 다시 보고**(이번에 새로 생긴 것), 초록일 때만 main 에 닿는다.

**판 번호는 손대지 않는다.** 지금 `0.3.620` 으로 적혀 있지만, 그 사이 main 이 더
가 있으면 `make deploy` 가 알아서 물린다. 손으로 고치면 `claim_version` 이 자리를
못 찾아 배포가 그 자리에서 선다.

## 4. 나간 뒤 — 확인할 것

```bash
make audit-deploys        # 오더 기록에 판이 남았는지 (「셀 수 있는 판 1개 · 빠짐 0」이면 정상)
```

삼중 실측은 평소대로:

```
API=https://veo-platform-production.up.railway.app
curl -fsS "$API/api/health" | grep -o '"version":"[^"]*"'
curl -fsS "$API/api/queue"  | grep -o '"worker_versions":\[[^]]*\]'
curl -fsS https://veo.seokorea.org/login | grep -oE '0\.3\.[0-9]+' | sort -u
```

## 5. 알아 두실 것 — 이 방이 찾은 것

**쪽문(손으로 main 에 올리기)을 설정으로 막을 수는 없다.** [실측 2026-09-19]
이 저장소는 비공개+무료라 GitHub 이 룰셋을 거절하고(«Upgrade to GitHub Pro», 403),
게다가 정문도 같은 방식으로 올리므로 막으면 배포가 통째로 선다.

**그리고 막을 필요도 없다 — 정문은 바깥길이 막힌 방에서도 돈다.**
`make preflight` 를 돌려 보니 ①나무 ②계약을 통과하고 ③관문까지 돈다(9분 넘게 걸려
중간에 끊었다 — 느린 것이지 막힌 것이 아니다). 마지막 `[5/5]`(운영에 닿았나)는
바깥길이 막혀도 **「못 쟀습니다」로 적고 넘어가지 배포를 죽이지 않는다**(소스 주석이
직접 「둘 다 죽을 일이 아니다」라고 적어 두었다).

→ **`make deploy` 를 못 쓴다고 판단하기 전에 한 번 돌려 보시라.** 이 방이 2026-09-01 에,
그리고 2026-09-11 의 그 방이 그 오해로 쪽문을 썼고, 그래서 판 번호가 겹치고 기록이 비었다.


그 물러남을 **나가기 직전까지** 미뤄 준다.
